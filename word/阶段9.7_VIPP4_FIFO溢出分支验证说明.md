# 阶段9.7：VIPP4 FIFO溢出独立分支验证说明

## 1. 目标与当前状态

分支：`diagnostic/vipp4-fifo`；起点：`main`的`affce61`。
目标是区分VIPP4溢出是否依赖LCD逐帧处理，而不是宣称已找到硬件根因。
主机回归、AddressSanitizer和真实SDK的ARM目标语法检查已通过。
本机为Windows，没有运行Linux ARM完整链接或直接操作V853。
用户已提供板端A/B日志；结果及新的C组对照见第9节，C组尚待板端验证。

该分支不自动修改开发板启动脚本、不调整时钟、不修改厂商SDK/内核文件、
不切换NPU模型、不改变VIPP4分辨率/帧率/5帧缓冲。
测试结果明确前，不合并main；main原有提交保持不变。

## 2. 两组测试到底改变了什么

| 项目 | A：`--vipp4-timing` | B：`--vipp4-capture-only` |
| --- | --- | --- |
| VIPP4 | 1920×1080 NV21、20fps、5缓冲 | 相同 |
| VO/G2D/MMZ初始化 | 保留 | 保留，帧池仍分配 |
| 每帧流程 | GetFrame→G2D→VO SendFrame→ReleaseFrame | GetFrame→ReleaseFrame |
| LCD实时摄像头画面 | 应正常显示 | 无新摄像头画面，黑屏/旧画面均可能 |
| VIPP4 ORL区域 | 保留 | 保留，但不送显，LCD看不到实时框 |
| VIPP0编码、OSD、RTSP、MP4 | 保留 | 相同 |
| NPU、越线、区域、音频报警 | 保留 | 相同 |

B不是关闭VIPP4，也不是“只启动一个摄像头模块”。保留其他服务才能
检验相同整机负载下LCD逐帧链路的影响。
VO初始化仍可能改变显示状态，硬件扫描状态不保证与A完全一致；
该实验只能收窄方向，不能单独区分G2D和VO谁有问题。

## 3. 技术实现

`main.c`解析两个可选参数，写入`VideoCaptureContext`。
`--vipp4-capture-only`自动启用耗时统计。
支持与`--npu-model MODEL.nb`组合，参数顺序可交换；
独立NPU/音频自检仍单独运行，不混入此整机对照。

采集线程在成功GetFrame后检查capture-only标志：

- 正常诊断组调用`video_display_submit_timed()`。
- 只取还帧组不调用显示提交，直接进入ReleaseFrame。
- 显示失败或输出帧池全忙也不能跳过ReleaseFrame。
- GetFrame失败时没有取得源帧，不调用ReleaseFrame。

显示模块原`video_display_submit()`作为兼容包装，传入NULL计时参数。
因此不带诊断参数的默认模式不读取诊断时钟，也不打印新诊断汇总。
有计时参数时，在G2D函数和VO SendFrame调用前后记录时间。
统计保存在采集线程的局部结构中，VO异步释放回调不访问它，不引入新共享锁。

时钟采用`clock_gettime(CLOCK_MONOTONIC)`，不使用日期时间或MPP PTS计算耗时，
避免NTP调整系统日期造成负耗时/巨大耗时。MPP PTS只用于对应源图像。
耗时包含函数调用期间的线程调度/抢占，并不等同于纯硬件计算时间。

诊断模式的采集汇总日志在ReleaseFrame之后输出，源帧PTS提前保存为标量；
归还后不会读取像素内存。显示函数内部原有日志及SDK日志仍保留。

## 4. 日志字段怎么读

每100个成功取到的帧打印一次累计统计（20fps下约5秒），首次及退出也打印。
所有avg/max从本次线程启动累计计算，不是最近100帧窗口。

| 字段 | 测量范围/含义 |
| --- | --- |
| get | 成功GetFrame调用的等待时间；失败调用只进入get_fail |
| hold | 成功GetFrame返回，到ReleaseFrame返回；不包含在SDK内部此前排队的时间 |
| display | 整次显示提交函数，包含找空闲缓冲、G2D、送显和内部日志 |
| g2d | `g2d_convert_frame()`整体调用，不是单独测量DMA或GPU占用 |
| vo_send | VO SendFrame函数调用；**不包含异步显示完成时间** |
| release | VI ReleaseFrame函数调用 |
| samples | 实际执行且时钟有效的G2D/送显样本数；跳过的调用不计入平均值 |
| get_fail / release_fail | 对应VI API失败次数，含退出边界发生的失败 |
| display_fail / display_drop | 显示处理失败/应用输出池忙时跳过的次数 |
| slow_hold | hold≥一帧周期的次数；20fps时阈值50000us |

`Slow hold`打印同一帧的G2D/送显/归还耗时，前3次以及每累计100次慢帧告警，
避免连续刷屏。各字段的累计max可能来自不同帧，**不能把这些max相加**。
时钟失败/逆序样本不计入时长统计。B组G2D/VO samples应该都是0。

50000us只是慢处理观察线，不是厂商硬件FIFO的容量或触发阈值。
超过该线不证明一定溢出；没有慢帧也不能排除短时总线竞争。
软件统计不自动读取VIN硬件溢出计数，必须同时保留内核日志。

## 6. 板端A/B验证步骤

两组使用同一固件、模型、网络、场景和报警活动，串行运行，不能同时启动两份程序。
LVGL在两组都保持相同状态。如果继续暂停LVGL，先用ps确认当前实际PID，
只暂停`lv_examples`，不要暂停NPU驱动线程或其他系统进程。
测试完成按实际PID执行`kill -CONT PID`恢复。

先A后B，各运行至少15分钟，跨过多个MP4分段，并主动触发几次报警。
条件允许时再重复A，以减少网络/场景随机变化造成的误判。

在开发板创建唯一日志目录，避免覆盖以前的证据：

```sh
cd /mnt/UDISK
vipp4_ab_dir=$(mktemp -d /mnt/UDISK/vipp4-ab.XXXXXX)
echo "$vipp4_ab_dir"
cat /proc/uptime > "$vipp4_ab_dir/A_start_uptime.txt"
dmesg > "$vipp4_ab_dir/A_kernel_before.txt"
./sample_strip --vipp4-timing 2>&1 | tee "$vipp4_ab_dir/A_app.log"
```

A组运行15分钟后Ctrl+C，回到提示符再执行：

```sh
dmesg > "$vipp4_ab_dir/A_kernel_after.txt"
cat /proc/uptime > "$vipp4_ab_dir/A_end_uptime.txt"
cat /proc/uptime > "$vipp4_ab_dir/B_start_uptime.txt"
dmesg > "$vipp4_ab_dir/B_kernel_before.txt"
./sample_strip --vipp4-capture-only 2>&1 | tee "$vipp4_ab_dir/B_app.log"
```

B组运行15分钟后Ctrl+C，回到提示符再执行：

```sh
dmesg > "$vipp4_ab_dir/B_kernel_after.txt"
cat /proc/uptime > "$vipp4_ab_dir/B_end_uptime.txt"
grep 'video4 fifo overflow' "$vipp4_ab_dir/A_kernel_after.txt"
grep 'video4 fifo overflow' "$vipp4_ab_dir/B_kernel_after.txt"
```

如果当前有效模型不是/lib/yolov8n.nb，两组命令都追加同一个
`--npu-model /mnt/UDISK/实际模型.nb`，不要比较不同模型。
上述pipeline的shell退出码通常属于tee，不代表sample_strip；
判断应用退出使用日志里的`Application exited with code`。

tee仅保存应用stdout/stderr，内核串口消息不保证进入该文件。
dmesg快照可能包含之前运行的错误，应按`*_start_uptime.txt`、
`*_end_uptime.txt`区间筛选内核方括号时间戳，只统计本组新增事件。
内核日志环形缓冲可能覆盖旧行；有覆盖时保留完整串口记录，不用快照总行数相减。
测试期间不要`dmesg -c`，不要自动删除录像或修改时间/频率来混入额外变量。

两组退出都检查：NPU失败数、MP4 pending/释放数、RTSP应用丢弃、
报警failed、应用退出码；同时用VLC确认RTSP和MP4播放。
B组LCD没有实时画面不是失败。日志目录也不属于循环录像的删除对象。

## 7. 怎样判定下一步

| 结果 | 可以得出的结论 | 仍不能断言什么 |
| --- | --- | --- |
| A反复溢出、B明显减少或消失 | LCD逐帧处理是重要触发条件 | 不能直接证明DDR不足或G2D驱动错误 |
| A慢hold与错误时间相近，B持帧很短 | 源帧归还延迟值得进一步定位 | 相关性不等于因果，需重复测试/驱动证据 |
| A/B溢出接近，B无G2D/VO调用 | 问题不依赖这两项应用逐帧调用才能发生 | 初始化/显示扫描、其他负载及驱动仍未排除 |
| 两组均无溢出 | 本轮未复现 | 不能宣布修复成功，需要重复和延长测试 |

根据结果再选择：拆分G2D/VO负载、调整仅预览的尺寸进行对照、
或继续核查厂商VIN DMA中断/地址/总线配置。不要一次改变多个参数。
取得完整A/B证据并完成有针对性的修复、回归与长期压力测试后，再评估合并main。
单纯加入诊断开关不算完成FIFO修复。

## 9. A/B已收证据与C组ISP 3DNR对照

### 9.1 已发生的问题和当前判断

用户提供的A组片段：最终3113帧，约2分36秒，出现1条
`video4 fifo overflow`；hold最大12392us、G2D最大12298us、VO调用最大203us，
slow_hold为0，显示失败/丢弃为0。该次没有发现Get成功后长时间持帧，
但统计不包含Get返回之前SDK内部等待/驻留，不能排除所有缓冲问题。
Ctrl+C到退出码0约2.29秒。

用户提供的B组完整日志：12222帧，采集约10分17秒，G2D/VO逐帧调用为0，
hold最大4377us，没有记录到`video4 fifo overflow`；但并非无错误：

```text
isp0 rdma fifo full
isp0 rdma fifo of d3d rec fifo overflow
__sunxi_isp_reset_v2:isp0 reset!!!,ISP frame number is 7527
isp0 lbc decompress error
isp0 the data for LBC decode is error
__sunxi_isp_reset_v2:isp0 reset!!!,ISP frame number is 7528
```

两次ISP复位之间约一帧。Ctrl+C到退出码0约2.09秒，NPU推理失败0，
MP4最终pending=0，RTSP应用丢弃0，报警播放失败0。这些计数不证明网络端
每帧均收到，也不证明ISP复位附近录像完全无异常，仍需查看对应MP4片段。
A/B长度及画面/编码负载并未严格一致，应重复同场景A→C→A，而非只比较总次数。

用户提供的厂商驱动源码进一步确认：

- `vin-video/vin_core.c`的`video4 fifo overflow`对应CSI DMA缓冲溢出状态。
- `vin-isp/sunxi_isp.c`先检查`RDMA_FIFO_FULL_PD`，再检查
  `RDMA_D3D_REC_FIFO_UV`，然后主动调用两个ISP复位函数。
- ISP600头文件中`RDMA_D3D_REC_FIFO_UV`为bit10；日志统一写overflow，
  不能仅由日志文字推断具体读侧状态含义，仍需寄存器说明确认。
- `CONFIG_D3D`未定义时，驱动代码会禁用D3D模块；这不证明当前运行固件的
  实际编译配置，也不证明有该配置时运行中始终开启D3D。

因此两个错误位置不同；目前怀疑共享图像处理负载、D3D/LBC缓冲或时序，
不能宣布DDR带宽不足、G2D驱动故障或应用帧泄漏就是唯一根因。
后续LBC错误是否由前次复位的恢复状态引起也只是待验证假设。

### 9.2 C组改变什么

```sh
./sample_strip --isp-3dnr-off
```

C组保留正常LCD/G2D/VO处理，自动启用VIPP4耗时统计；VIPP0编码、NPU、
RTSP、MP4、OSD、ORL、音频及报警都保留，不修改分辨率/帧率/缓冲数。
不要追加`--vipp4-capture-only`来冒充C组；虽然程序允许组合，那属于另一组实验。
若使用候选模型，A/C均追加相同的`--npu-model MODEL.nb`。

控制的是共享ISP0原生`isp_test_enable_cfg.tdf`，不是VENC参考帧LBC，
也不是把`Set3NRAttr`的强度设成0。所有VIPP完成ISP_Run后才执行：

1. `isp_get_cfg(ISP0, HW_ISP_CFG_TEST, HW_ISP_CFG_TEST_ENABLE, ...)`
   读取并保存原生配置；失败时不写配置。
2. 完整复制原配置，只设置`manual=1`、`tdf=0`，保留其他模块开关。
3. `isp_set_cfg`写入、`isp_update`通知更新后立即Get读回，要求manual=1且
   tdf=0；原生Get/Set成功返回33字节，update成功返回0；否则中止并回滚。
4. 主循环每约5秒只读核对一次；被覆盖或读取失败时中止测试。
5. cleanup在任何NPU/VENC/VI的ISP_Stop之前恢复原manual/tdf并读回。
   正常恢复保留其他开关当前值；当前Get失败时回退到原始完整快照。
   恢复失败会打印RESTORE错误并返回失败退出码，不宣称恢复成功。

重要限制：原manual=0时，设置manual=1不仅关闭tdf，也改为手动模块开关控制。
其他开关虽保留读取值，自动模式下可能动态变化，因此不是无条件的严格单变量。
若C组改善，仍可能需要“相同manual=1但tdf=1”的额外对照才能排除控制模式影响。
原tdf已是0时会告警；不能把这种结果称为从硬件3DNR开启到关闭的有效对照。
API读回只说明SDK报告的配置，无法独立证明寄存器及D3D/LBC访存已经关闭。

新配置在所有采集通路启动后才写入，启动初期的帧仍可能使用原设置。
仅从`Configuration verified`之后统计C组有效运行区间；退出恢复之后不计入C组。
全程累计VIPP4统计仍包含启动/退出阶段，应结合日志时间阅读。
SIGKILL、断电或崩溃无法执行恢复；发现RESTORE失败时不要接着比较A组，
先重启开发板恢复环境。此选项不写启动脚本/永久配置，也不调整RTC或系统时间。

### 9.3 如何测试和保存证据

在虚拟机确认当前是`diagnostic/vipp4-fifo`，获取已提交到该分支的最新代码再编译；
未提交/推送的本机改动不会通过虚拟机git pull自动出现。使用相同编译产物比较各组：

```sh
git branch --show-current
sh build.sh
```

把新`output/sample_strip`复制到开发板；先做C组短测，检查以下日志出现：

```text
[ISP3DNR-DIAG] Original: isp=0 manual=... tdf=...
[ISP3DNR-DIAG] Configuration verified: isp=0 manual=1 tdf=0
[ISP3DNR-DIAG] Periodic configuration check OK: isp=0 manual=1 tdf=0
[ISP3DNR-DIAG] Restored: isp=0 manual=原值 tdf=原值
[Main] Application exited with code: 0
```

只要设置/核对/恢复失败，先提供该错误日志，不把该次计入通过结果。
配置verified之前失败的启动不能算有效C组；LCD应仍有实时画面及检测框。

与第6节相同，保存内核和应用两份证据，不清空dmesg：

```sh
cd /mnt/UDISK
isp3dnr_test_dir=$(mktemp -d /mnt/UDISK/isp3dnr-diag.XXXXXX)
echo "$isp3dnr_test_dir"
cat /proc/uptime > "$isp3dnr_test_dir/C_start_uptime.txt"
dmesg > "$isp3dnr_test_dir/C_kernel_before.txt"
./sample_strip --isp-3dnr-off 2>&1 | tee "$isp3dnr_test_dir/C_app.log"
```

运行至少15分钟，Ctrl+C退出后：

```sh
dmesg > "$isp3dnr_test_dir/C_kernel_after.txt"
cat /proc/uptime > "$isp3dnr_test_dir/C_end_uptime.txt"
grep -Ei 'video4.*fifo|isp0.*(fifo|lbc)|isp0 reset' "$isp3dnr_test_dir/C_kernel_after.txt"
```

grep可能包含旧运行记录，必须按本次uptime和配置生效区间筛选；tee不保证
包含内核串口日志，也不能用pipeline的$?冒充应用退出码。保留完整串口记录。
维持相同摄像头方向/场景、模型、VLC连接方式、Wi-Fi和LVGL状态，重复
`--vipp4-timing`→`--isp-3dnr-off`→`--vipp4-timing`，各组同样时长。
同时核对LCD/RTSP/MP4音视频、NPU/报警和Ctrl+C退出。

- C减少/消除相关错误：支持ISP 3DNR配置或其关联负载参与触发；
  不单独证明D3D驱动bug或DDR不足，注意manual控制模式混杂。
- C读回始终有效但错误仍在：该设置未消除故障，不能无证据认定硬件已关闭D3D。
- A/C均无错误：本轮未复现，继续重复/延长，不能当作修复完成。
- C设置被覆盖：控制条件无效，先定位配置覆盖方，不比较FIFO频率。

### 9.6 实现时发现的SDK包装ABI不匹配（本机已规避，非FIFO已证实根因）

最初拟使用`AW_MPI_ISP_GetModuleOnOff/SetModuleOnOff`，但进一步核对
本项目预编译库后发现公共声明不能直接照用：

- `mpi_isp.h`的`ISP_MODULE_ONOFF`字段为`HW_S32`，`HW_S32`是int。
- `libaw_mpp.a`里上述包装实际按原始字节复制前32字节及最后1字节，没有
  把HW_S32字段转换为对应开关；包装还没有传播底层Get/Set/update返回码。
- `libISP.a`的TEST/ENABLE配置处理实际复制33字节并返回33。
- 与之对应的`isp_tuning.h`原生`struct isp_test_enable_cfg`使用HW_S8字段，
  共33字节，manual偏移0、tdf偏移13，布局和公共结构体并不相同。

盲用包装可能读到拼接整数、写到错误开关，甚至只验证了错误的内存字段。
因此本次最终代码不调用该MPI包装，也不进行结构体指针强转，更没有修改SDK。
改用SDK已有原生结构和`isp_get_cfg/isp_set_cfg/isp_update`，编译期核对大小与
关键偏移，配置缓冲显式4字节对齐，运行时核对传输字节数、update结果和读回值。
已确认这三个原生符号在libISP.a中定义；仍需Linux完整链接和板端验证。
更换SDK/库版本后必须重新核对ABI，不能把本库的33字节约定视为通用标准。

主机测试新增原生33字节返回值、错误长度拒绝、update失败恢复、地址对齐，
并按整个33字节配置验证只改manual/tdf，包含编码器降噪开关保留。
这是新增诊断功能的安全性修正；原FIFO日志不能据此归因于这个包装，
原监控运行路径此前没有调用本次新增的控制器。
