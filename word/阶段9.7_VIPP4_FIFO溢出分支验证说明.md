# 阶段9.7：VIPP4 FIFO溢出独立分支验证说明

## 1. 目标与当前状态

分支：`diagnostic/vipp4-fifo`；起点：`main`的`affce61`。
目标是区分VIPP4溢出是否依赖LCD逐帧处理，而不是宣称已找到硬件根因。
主机回归、AddressSanitizer和真实SDK的ARM目标语法检查已通过。
本机为Windows，没有运行Linux ARM完整链接，也没有执行V853新模式A/B测试。

该分支不自动修改开发板启动脚本、不调整时钟、不修改厂商SDK/内核、
不切换NPU模型、不改变VIPP4分辨率/帧率/5帧缓冲。
测试结果明确前，不合并main；main原有提交保持不变。

## 2. 两组测试到底改变了什么

| 项目 | A：`--vipp4-timing` | B：`--vipp4-capture-only` |
| --- | --- | --- |
| VIPP4 | 1920×1080 NV21、20fps、5缓冲 | 相同 |
| VO/G2D/MMZ初始化 | 保留 | 保留，帧池仍分配 |
| 每帧流程 | GetFrame→G2D→VO SendFrame→ReleaseFrame | GetFrame→ReleaseFrame |
| LCD实时摄像头画面 | 应正常显示 | 无新摄像头画面，黑屏/旧画面均可能 |
| VIPP4 ORL区域 | 保留 | 保留，但不送显，LCD看不到实时框 |
| VIPP0编码、OSD、RTSP、MP4 | 保留 | 相同 |
| NPU、越线、区域、音频报警 | 保留 | 相同 |

B不是关闭VIPP4，也不是“只启动一个摄像头模块”。保留其他服务才能
检验相同整机负载下LCD逐帧链路的影响。
VO初始化仍可能改变显示状态，硬件扫描状态不保证与A完全一致；
该实验只能收窄方向，不能单独区分G2D和VO谁有问题。

## 3. 技术实现

`main.c`解析两个可选参数，写入`VideoCaptureContext`。
`--vipp4-capture-only`自动启用耗时统计。
支持与`--npu-model MODEL.nb`组合，参数顺序可交换；
独立NPU/音频自检仍单独运行，不混入此整机对照。

采集线程在成功GetFrame后检查capture-only标志：

- 正常诊断组调用`video_display_submit_timed()`。
- 只取还帧组不调用显示提交，直接进入ReleaseFrame。
- 显示失败或输出帧池全忙也不能跳过ReleaseFrame。
- GetFrame失败时没有取得源帧，不调用ReleaseFrame。

显示模块原`video_display_submit()`作为兼容包装，传入NULL计时参数。
因此不带诊断参数的默认模式不读取诊断时钟，也不打印新诊断汇总。
有计时参数时，在G2D函数和VO SendFrame调用前后记录时间。
统计保存在采集线程的局部结构中，VO异步释放回调不访问它，不引入新共享锁。

时钟采用`clock_gettime(CLOCK_MONOTONIC)`，不使用日期时间或MPP PTS计算耗时，
避免NTP调整系统日期造成负耗时/巨大耗时。MPP PTS只用于对应源图像。
耗时包含函数调用期间的线程调度/抢占，并不等同于纯硬件计算时间。

诊断模式的采集汇总日志在ReleaseFrame之后输出，源帧PTS提前保存为标量；
归还后不会读取像素内存。显示函数内部原有日志及SDK日志仍保留。

## 4. 日志字段怎么读

每100个成功取到的帧打印一次累计统计（20fps下约5秒），首次及退出也打印。
所有avg/max从本次线程启动累计计算，不是最近100帧窗口。

| 字段 | 测量范围/含义 |
| --- | --- |
| get | 成功GetFrame调用的等待时间；失败调用只进入get_fail |
| hold | 成功GetFrame返回，到ReleaseFrame返回；不包含在SDK内部此前排队的时间 |
| display | 整次显示提交函数，包含找空闲缓冲、G2D、送显和内部日志 |
| g2d | `g2d_convert_frame()`整体调用，不是单独测量DMA或GPU占用 |
| vo_send | VO SendFrame函数调用；**不包含异步显示完成时间** |
| release | VI ReleaseFrame函数调用 |
| samples | 实际执行且时钟有效的G2D/送显样本数；跳过的调用不计入平均值 |
| get_fail / release_fail | 对应VI API失败次数，含退出边界发生的失败 |
| display_fail / display_drop | 显示处理失败/应用输出池忙时跳过的次数 |
| slow_hold | hold≥一帧周期的次数；20fps时阈值50000us |

`Slow hold`打印同一帧的G2D/送显/归还耗时，前3次以及每累计100次慢帧告警，
避免连续刷屏。各字段的累计max可能来自不同帧，**不能把这些max相加**。
时钟失败/逆序样本不计入时长统计。B组G2D/VO samples应该都是0。

50000us只是慢处理观察线，不是厂商硬件FIFO的容量或触发阈值。
超过该线不证明一定溢出；没有慢帧也不能排除短时总线竞争。
软件统计不自动读取VIN硬件溢出计数，必须同时保留内核日志。

## 5. Windows分支与虚拟机同步

本次仅本地创建分支并保存诊断提交，不自动push，也不合并main。
需要上传后在虚拟机编译时，先在Windows项目根目录执行：

```powershell
git status --short
git branch --show-current
git push -u origin diagnostic/vipp4-fifo
```

虚拟机项目目录先检查本地未提交修改；若有修改先保留，不要强制覆盖。
工作区干净后执行：

```sh
git fetch origin
git switch --track origin/diagnostic/vipp4-fifo
./build.sh
```

若虚拟机本地已经有此分支，则使用：

```sh
git switch diagnostic/vipp4-fifo
git pull --ff-only origin diagnostic/vipp4-fifo
./build.sh
```

传输新`output/sample_strip`到开发板后使用。旧二进制不认识这些参数，
不能拿旧程序日志验证新模式；启动应出现`[VIPP4-DIAG] mode=...`。
本分支没有生成板端二进制供直接运行。

## 6. 板端A/B验证步骤

两组使用同一固件、模型、网络、场景和报警活动，串行运行，不能同时启动两份程序。
LVGL在两组都保持相同状态。如果继续暂停LVGL，先用ps确认当前实际PID，
只暂停`lv_examples`，不要暂停NPU驱动线程或其他系统进程。
测试完成按实际PID执行`kill -CONT PID`恢复。

先A后B，各运行至少15分钟，跨过多个MP4分段，并主动触发几次报警。
条件允许时再重复A，以减少网络/场景随机变化造成的误判。

在开发板创建唯一日志目录，避免覆盖以前的证据：

```sh
cd /mnt/UDISK
vipp4_ab_dir=$(mktemp -d /mnt/UDISK/vipp4-ab.XXXXXX)
echo "$vipp4_ab_dir"
cat /proc/uptime > "$vipp4_ab_dir/A_start_uptime.txt"
dmesg > "$vipp4_ab_dir/A_kernel_before.txt"
./sample_strip --vipp4-timing 2>&1 | tee "$vipp4_ab_dir/A_app.log"
```

A组运行15分钟后Ctrl+C，回到提示符再执行：

```sh
dmesg > "$vipp4_ab_dir/A_kernel_after.txt"
cat /proc/uptime > "$vipp4_ab_dir/A_end_uptime.txt"
cat /proc/uptime > "$vipp4_ab_dir/B_start_uptime.txt"
dmesg > "$vipp4_ab_dir/B_kernel_before.txt"
./sample_strip --vipp4-capture-only 2>&1 | tee "$vipp4_ab_dir/B_app.log"
```

B组运行15分钟后Ctrl+C，回到提示符再执行：

```sh
dmesg > "$vipp4_ab_dir/B_kernel_after.txt"
cat /proc/uptime > "$vipp4_ab_dir/B_end_uptime.txt"
grep 'video4 fifo overflow' "$vipp4_ab_dir/A_kernel_after.txt"
grep 'video4 fifo overflow' "$vipp4_ab_dir/B_kernel_after.txt"
```

如果当前有效模型不是/lib/yolov8n.nb，两组命令都追加同一个
`--npu-model /mnt/UDISK/实际模型.nb`，不要比较不同模型。
上述pipeline的shell退出码通常属于tee，不代表sample_strip；
判断应用退出使用日志里的`Application exited with code`。

tee仅保存应用stdout/stderr，内核串口消息不保证进入该文件。
dmesg快照可能包含之前运行的错误，应按`*_start_uptime.txt`、
`*_end_uptime.txt`区间筛选内核方括号时间戳，只统计本组新增事件。
内核日志环形缓冲可能覆盖旧行；有覆盖时保留完整串口记录，不用快照总行数相减。
测试期间不要`dmesg -c`，不要自动删除录像或修改时间/频率来混入额外变量。

两组退出都检查：NPU失败数、MP4 pending/释放数、RTSP应用丢弃、
报警failed、应用退出码；同时用VLC确认RTSP和MP4播放。
B组LCD没有实时画面不是失败。日志目录也不属于循环录像的删除对象。

## 7. 怎样判定下一步

| 结果 | 可以得出的结论 | 仍不能断言什么 |
| --- | --- | --- |
| A反复溢出、B明显减少或消失 | LCD逐帧处理是重要触发条件 | 不能直接证明DDR不足或G2D驱动错误 |
| A慢hold与错误时间相近，B持帧很短 | 源帧归还延迟值得进一步定位 | 相关性不等于因果，需重复测试/驱动证据 |
| A/B溢出接近，B无G2D/VO调用 | 问题不依赖这两项应用逐帧调用才能发生 | 初始化/显示扫描、其他负载及驱动仍未排除 |
| 两组均无溢出 | 本轮未复现 | 不能宣布修复成功，需要重复和延长测试 |

根据结果再选择：拆分G2D/VO负载、调整仅预览的尺寸进行对照、
或继续核查厂商VIN DMA中断/地址/总线配置。不要一次改变多个参数。
取得完整A/B证据并完成有针对性的修复、回归与长期压力测试后，再评估合并main。
单纯加入诊断开关不算完成FIFO修复。

## 8. 主机验证与边界

`tests/vipp4_diagnostics_test.c`直接包含真实采集实现，使用测试专用MPP替身：

- 正常模式仍调用原显示接口且不读取诊断时钟。
- 正常计时模式累计Get/G2D/VO/持帧/归还耗时并限流慢帧告警。
- capture-only模式G2D/VO调用为0，仍保持采集属性和取还帧。
- 取帧失败不归还，显示失败/丢帧仍归还，归还失败进入统计。
- 验证累计平均值、最大值及无效时间样本处理。

6组采集测试共1200次归还，普通版本和AddressSanitizer均通过。
原有MP4异步复制/所有权主机回归测试也通过，产品录像实现未修改。
主机替身不验证厂商硬件行为、真实VO回调或FIFO触发。
真实SDK下main.c/video_capture.c/video_display.c的ARM目标语法检查通过，
仅有SDK原有plat_math.h比较警告；这不是完整编译链接或板端验收。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run_vipp4_diagnostics_test.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run_vipp4_diagnostics_test.ps1 -AddressSanitizer
```

脚本只在忽略的output目录生成主机exe。tests/vipp4_stubs不参与产品Makefile，
不上传output中的测试二进制，不修改SDK头文件来迁就主机测试。
