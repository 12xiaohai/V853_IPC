## 4. 为什么Ctrl+C退出不了

`main.c`在停止NPU后调用`audio_encoder_stop()`。
`audio_encoder_stop()`设置停止标志，然后调用`pthread_join()`等待音频取流线程结束。
音频线程需要执行完当前迭代、再次检查停止标志才能退出。

当前音频取流顺序为：

```text
AENC GetStream → 写AAC/统计 → 消费者回调 → MP4同步送流 → AENC ReleaseStream
```

`GetStream`的200ms超时只约束取流等待，不约束后面的文件写入、锁等待和MPP同步送流。
因此“GetStream有超时”不等于“线程一定能在200ms内结束”。

依据日志与清理顺序，最可疑的退出阻塞点是`audio_encoder_stop()`的join；
尚未取得现场线程栈，不能把该点标记成已经由调试器确认。
重复Ctrl+C只会再次设置退出标志，不会自动解除业务锁或终止MPP内部等待。

## 5. 高风险锁与分段同步关系（待线程栈确认）

源码证据：

- `mp4_recorder_push_video()`与`mp4_recorder_push_audio()`共用`send_lock`。
- 两者都持有该锁调用`AW_MPI_MUX_SendVideoStreamSync()`或`AW_MPI_MUX_SendAudioStreamSync()`。
- 这两个接口没有调用方可传入的超时参数。
- 消费者回调返回之前，编码线程不会执行对应的`ReleaseStream`。
- 分段线程的`switch_to_next_segment()`也使用该锁；`mp4_recorder_stop()`开始时同样要取得它。

最可疑的等待环如下，属于工作假设而不是已证实的运行时线程关系：

```text
一路编码线程持send_lock同步送流
  → MUX分段处理等待另一轨数据/时序条件
  → 另一路编码线程获取同一send_lock，无法补充数据
  → 编码缓冲消费停滞，上游AI缓冲满
  → Ctrl+C后主线程join编码线程，无法继续清理
```

日志中音频先达到切段条件、MUX随后等待输入，与上述风险吻合。
但当前不知道究竟哪一路持锁、哪一路等待锁，也不能排除SDK内部等待或其他阻塞；
应通过调用前后诊断与线程栈补齐证据，不能仅凭本日志宣称已经精确定位SDK内部死锁。

原项目`sample/ipc_camera/app/server.c`将VENC/AENC通过`AW_MPI_SYS_Bind()`接到MUX，
不是本复刻项目的应用层持锁同步送流方式。复刻项目的这条实现差异应纳入排查。
如改回隧道方案，需要同步核对RTSP取流方式及AAC去ADTS兼容性，不能直接替换一行接口。

## 6. 修复方向与不能采用的捷径

下一步首先补充MUX送流进入/返回、持锁/解锁、编码线程停止前后的诊断，确定阻塞位置。
随后调整送流的并发和生命周期，使一路媒体等待不会阻止另一路给MUX提供数据；
并建立可停止、可收尾的消费路径，避免清理只能无限join。

候选方向包括：核实SDK支持的独立双轨同步送流，或改用有界队列、独立码流副本与
异步MUX释放回调；也可评估原项目MPP绑定通路。
这些是首次诊断时的候选方案；本次采用异步副本方案，实现与测试见第8节。
如果保留Sync，只把两路合到一个串行工作线程仍可能等待另一轨，不能自动解决问题。

不要采用以下捷径：

- 仅增大AI缓冲：只能延后缓冲耗尽，不能解除阻塞。
- 仅注册空VENC回调：能够消除提示但不能证明媒体恢复；应记录具体事件。
- 在信号处理器中直接停止MPP、打印日志或释放资源：不符合安全信号处理要求。
- 用`pthread_cancel`或提前free仍被MPP使用的码流：可能引入悬空指针与损坏录像。
- 只把MP4停止移到join前：当前MP4停止也先获取`send_lock`，可能仍然等待。
- 直接把Sync替换为Async后立即ReleaseStream：异步消费者可能仍在读取原缓冲。

SDK `mpi_mux.h`明确要求不要混用同步与异步送流。
异步方案必须同时处理音视频、缓冲所有权、释放回调、在途计数和停机收尾。
不能为了join不再等待就直接销毁仍有线程访问的上下文。

## 8. 本次修复：双轨异步送流与缓冲所有权（2026-10-02）

### 8.1 为什么不能只把音视频拆成两把应用锁

除头文件外，进一步核对了项目SDK的`libaw_mpp.a(mpi_mux.c.o)`。
其`aw_mux_SendStream.isra.0`同步分支先取得SDK内部互斥锁，调用组件提交后执行
`cdx_sem_down`，收到缓冲释放通知后才解锁。视频与音频的Sync包装函数都进入此路径。
异步分支提交到组件后直接返回，不走该消费完成信号量等待。

因此应用层只拆`send_lock`仍会遇到SDK内部同步串行等待。本次改动同时替换音视频
为`AW_MPI_MUX_SendVideoStream()`和`AW_MPI_MUX_SendAudioStream()`，不混用Sync/Async。
这是对SDK等待机制的核实，不等于已取得故障现场线程栈或证明所有驱动故障均被解决。

### 8.2 帧如何从编码线程交给MUX

```text
编码线程GetStream
  → RTSP复制自己的数据
  → MP4复制自己的数据与描述符
  → MUX异步提交（不等当前帧消费完成）
  → 编码线程ReleaseStream，继续取下一帧

MUX之后通知RELEASE_*_STREAM
  → 用token找到录像副本
  → 释放副本，归还在途槽
```

`mp4_recorder.c`增加了视频64槽、音频128槽；有效载荷总量上限8 MiB，
上下文和槽描述符另占固定内存。它们是异步在途池，不是另一个会阻塞等待的工作队列。
没有增加串行Sync消费线程，否则仍可能在单线程中等待另一轨。

复制内容包含：

- H.264一个pack的三段数据、PTS及原始描述字段；本SDK包装层只展开首个pack，
  显式拒绝多pack，当前VENC取流本来就使用单pack。
- AAC先在描述符副本上去除ADTS，再复制裸AAC及附加数据，保留PTS。
- 原始AAC缓冲不改写，RTSP与独立`.aac`输出仍保持原格式。

录像器为每份副本分配自己的正31位token，写入录像描述符的`mSeq/mId`；
不修改编码器原始描述符。SDK回调重建结构体，因此不能依赖返回相同描述符指针，
也不能用编码器会循环的原始ID作为长期在途标识。

正确的回收事件是`MPP_EVENT_RELEASE_VENC_STREAM`与`MPP_EVENT_RELEASE_AENC_STREAM`，
参数分别为`MUX_VENC_STREAM_S*`、`MUX_AENC_STREAM_S*`。
它们不是VO/AO使用的`RELEASE_VIDEO_BUFFER/RELEASE_AUDIO_BUFFER`事件。

### 8.3 两把锁各自负责什么

- `send_lock`只串行短时异步提交、接收状态与SwitchFd控制，不等待帧被MUX消费。
- `pending_lock`保护副本池、内存计数与释放状态；调用SDK送流前必须解锁。
- MUX释放回调只使用`pending_lock`，绝不获取`send_lock`，允许SDK在Send返回前通知释放。
- 原有`rotation_lock`继续保护切片事件与文件状态；回调不打开文件或重入SwitchFd。

在途槽满、内存超限或提交失败时，记录一次故障并关闭本次录像入口，不无限malloc、
不等空槽，也不任意丢一个H.264 P帧后声称录像完整。RTSP与编码线程仍可继续工作，
最终录像stop返回失败，正常重启应用才能恢复录像。
磁盘写错误和未知释放通知也会记录故障，不能冒充成功录像。

### 8.4 退出与异常保护

`main.c`停止NPU后先调用`mp4_recorder_close_input()`，禁止新录像提交，
再join音频/视频编码线程；此时编码缓冲不再被MUX长期占用。
MUX和已提交副本仍保留，等生产者停止后再StopChn(FALSE)写尾部索引、DestroyChn。

停止顺序为：

```text
关闭录像入口 → 编码生产者停止 → 切片线程停止
  → MUX正常收尾 → MUX销毁 → 清理残余副本与文件 → 释放上下文
```

如果Stop/Destroy返回错误，保留仍可能被SDK使用的副本和cookie，避免释放后访问。
销毁成功后仍缺释放通知时可安全回收残余副本，但标记录像异常，不能当作验收通过。
VENC同时注册了事件回调，具体记录缓冲满/超时，不再只有“User should RegisterCallback”提示。
新增主线程清理位置日志用于区分音频、视频、MUX哪一步未返回。

本修复移除了同步码流消费等待链，不使用pthread_cancel、提前free或强制杀线程。
异步接口、SwitchFd、Stop/Destroy和文件IO仍依赖厂商SDK/驱动；本代码没有给这些内部
调用施加硬超时，不能宣称任何硬件失效都能保证数秒退出。

## 9. VIPP4 FIFO溢出的独立排查进展（2026-10-02）

### 9.1 已收到的证据，不等于根因已确定

厂商内核`vin-video/vin_core.c`在DMA缓冲溢出状态置位时打印
`video4 fifo overflow, CSI frame count is ...`。这不是MP4文件已满、
RTSP应用队列满或VO帧池满的同义词；CSI frame count也不是累计溢出次数。
仅凭该报错不能区分硬件总线竞争、源帧处理延迟或驱动/DMA配置原因。

后续修复版运行约7分钟的日志中，MP4副本全部回收、Ctrl+C约1.35秒退出，
但仍有11条VIPP4溢出。第一段MP4的播放及同步由用户确认正常。
这些短测支持退出阻塞问题有所改善，不代表完整长期压力测试已通过。

运行时采样显示应用CPU约35%、CPU空闲约55%～62%、剩余内存约200MB。
没有发现持续CPU满载或内存耗尽；但CPU空闲不是DDR总线占用测量。
`clk_summary`报告的CSI/G2D频率及DDR参考计数不能单独证明频率错误，
不能把`isp 24MHz`直接当作运算核心频率，也不能把DDR计数0解释成DDR关闭。

发现后台`lv_examples 5`后，用户执行`kill -STOP 1198`，并用`ps`确认
该进程状态为`T`。随后的附件片段仍包含：

```text
[26796.978273] [VIN_ERR]video4 fifo overflow, CSI frame count is 1133
[26810.584937] [VIN_ERR]video4 fifo overflow, CSI frame count is 1403
```

如果该次运行始终保持LVGL暂停，则暂停更新没有消除溢出；不能再认定
LVGL是唯一根因。暂停进程不保证显示硬件扫描也停止。
附件缺少完整启动和暂停时间，不能准确比较暂停前后的溢出频率。

该片段的退出信号时间为21:00:11.312282，退出码0时间为21:00:12.921973，
耗时约1.61秒。VO提交/释放均1587、MP4在途副本0、NPU推理失败0、
报警完成3次且失败0。录像覆盖约79秒，不能冒充15分钟压力测试。
停机时出现VI仍持有1帧的提示，随后VENC报告源帧列表为空并正常退出；
显示驱动还打印FCM/NULL hdl等提示，需要区分停机日志与运行时溢出，
不能只因两者都出现就判定因果。

### 9.2 独立分支与下一步

从干净的`main`（`affce61`）创建`diagnostic/vipp4-fifo`，
默认启动保留原功能。新增：

- `--vipp4-timing`：正常预览，记录取帧、持帧、G2D、送显、归还耗时。
- `--vipp4-capture-only`：保持VIPP4及VO初始化，跳过逐帧G2D/VO处理，
  成功取帧后立即归还；编码、RTSP、MP4、NPU、ORL及报警仍保留。

两组均使用单调时钟、累计统计和限流告警，不调整时钟、分辨率、帧率或缓冲数。
只取还帧模式没有实时LCD画面是预期现象，RTSP/录像应继续有图像与声音。
主机测试及ARM语法检查通过，但未做新诊断模式的板端A/B验证，
**FIFO根因尚未闭环，诊断代码尚未合并到main**。

完整操作、日志字段和判定边界见
[`阶段9.7_VIPP4_FIFO溢出分支验证说明.md`](阶段9.7_VIPP4_FIFO溢出分支验证说明.md)。
