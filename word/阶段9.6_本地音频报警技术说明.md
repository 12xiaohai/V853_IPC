# 阶段9.6：本地音频报警技术说明

## 1. 当前状态与范围

本阶段已完成代码接入、主机模拟测试和真实SDK的ARM目标语法检查。
**尚未完成开发板声音及完整媒体链路验收，不能仅凭主机测试宣布本阶段完成。**

阶段9.5已有板端证据：同一临时轨迹出现ENTER和LEAVE，后续轨迹也能进入；
越线规则同时运行，Ctrl+C正常清理。轨迹ID变化、边界防抖和长期稳定性仍需观察。

本阶段新增功能：

- 越线两个方向、区域ENTER都可触发本地声音；LEAVE只记录日志。
- 共享一个播放线程，不重复打开多路播放、不会按事件创建分离线程。
- 固定8项事件队列和15秒全局冷却；播放中/冷却中抑制新事件。
- 使用已有`/lib/alarm.wav`，解析真正的PCM样本并送给MPP AO。
- WAV不可用或AO故障只关闭声音服务，不停止检测、预览、推流和录像。
- 保留播放来源、轨迹ID、区域ID、序号、PTS及最终统计日志。

## 2. 与原项目的关系

原项目`sample/common/cross_alarm.c`也通过AO播放报警音；
`sample/ipc_camera/app/server.c`负责创建音频输出通道。
因此仍沿用原项目的“业务事件→本地WAV→MPP AO→板端扬声器”方案，
没有引入额外播放器、OpenCV音频处理或重复编码。

此次没有逐行复制原实现，原因在源代码中可确认：

1. 原代码读取整个文件，却未解析RIFF/fmt/data，WAV头会被当作PCM。
2. 播放参数硬编码为32 kHz、单声道；文件格式不符就可能倍速或噪声。
3. `mBitwidth`需要`AUDIO_BIT_WIDTH_16`枚举，不能直接填整数16。
4. 原代码在创建播放线程后才设置播放标志，多事件可能穿过检查窗口。
5. 分离线程难以join；打开文件失败的部分路径也可能遗留播放状态。

本阶段用单线程、统一清理、格式检查和异步释放确认解决这些风险。
这些是源码审查发现，不应写成已经在用户开发板上发生过的故障。

## 3. 文件职责与调用关系

| 文件 | 负责的工作 |
| --- | --- |
| `app/wav_reader.c`、`include/wav_reader.h` | 校验RIFF WAV、定位data、加载PCM |
| `app/audio_alarm.c`、`include/audio_alarm.h` | 队列、线程、冷却、AO、回调与退出 |
| `app/main.c` | 配置服务，转换两类规则事件，管理启动/停止顺序 |
| `tests/audio_alarm_test.c` | WAV/并发/冷却/故障/退出主机回归 |
| `tests/stubs/mpi_ao.h` | 仅测试使用的AO替身，生产构建不得包含 |

```text
NPU最新快照
  ├─ 越线线程 → dispatch_line_alarm ────┐
  └─ 区域线程 → dispatch_region_alarm ──┤ ENTER入队，LEAVE不入队
                                      ↓
                              固定8项事件队列
                                      ↓
                            单一AudioAlarm线程
                                      ↓
                         AO 0/0 → CODEC → 扬声器
```

两个规则线程的临时track ID独立，不用同一个ID判断“同一个人”。
报警采用全局限流，可能抑制冷却内另一个人的真实事件，这是防重复策略的取舍，
不是业务事件消失：LINE/REGION日志仍会记录规则事件。

## 4. WAV解析：为什么不能直接读文件播放

WAV是容器，至少包含RIFF/WAVE标记、fmt格式块和data样本块。
有些WAV还有LIST/JUNK等块，因此data并不总从第44字节开始。

`wav_pcm_read`的处理顺序：

1. 检查文件长度、RIFF标识、WAVE标识和RIFF声明的范围。
2. 逐块读取chunk类型与长度，跳过不需要的元数据。
3. 奇数长度块额外跳过一个对齐字节，用64位计算防止长度回绕。
4. 从fmt读取编码、声道数、采样率、位宽、块对齐和字节率。
5. 保存data偏移和长度，检查它确实位于文件/RIFF范围内。
6. 只将data加载到内存，播放时不再做文件读取。

当前有意只支持：PCM编码标记1、16-bit little-endian、单声道。
采样率可为8000/11025/12000/16000/22050/24000/32000/44100/48000 Hz；
非空样本最多4 MiB且不超过60秒。浮点WAV、压缩WAV、立体声、
RF64/WAVE_FORMAT_EXTENSIBLE及无头PCM均不是本阶段支持的输入。

采样率来自WAV，不是AAC采集的16 kHz参数；播放与采集无需强行保持相同采样率。
能否由实际板端ALSA配置正确播放这些采样率仍需实测，优先使用原报警音或32 kHz。

## 5. 队列、冷却和防重叠

规则回调只复制`AudioAlarmEvent`，不会把栈上的event指针交给异步线程。
`audio_alarm_push`在短临界区内完成检查和入队，不执行AO或磁盘操作。

- 返回0：已入队，不代表已经发出声音。
- 返回1：播放中、冷却中或队列满，本次声音被抑制。
- 返回-1：无服务、已停止、参数错误或服务因播放故障禁用。

播放器取一个事件后清空同批积压事件，合并为一次声音，避免很久之后
再播放已经过时的报警。在释放互斥锁前设定`playing=1`，没有并发检查漏洞。

默认全局冷却15秒，**从本次播放开始计算，不是从播放结束计算**。
若声音长度超过15秒，播放期间仍抑制，结束后冷却可能已经到期。
采用`CLOCK_MONOTONIC`，开发板NTP校时不会突然解除或延长冷却。
这与越线规则自身的3秒/轨迹冷却是两层不同机制。

## 6. MPP AO播放与缓冲生命周期

`main.c`默认配置：设备0、通道0、音量35、软音量0，使用AUDIOCODEC声卡。
AI采集和AO输出属于不同MPP模块，它们各自的通道0不冲突。
但其他程序占用AO 0/0时，本模块会报错，不会停止或销毁别人的通道。

每次播放重新创建AO通道，完成后停止并销毁，使下一次播放不继承上次EOF状态。
SDK中的`AO_SetPubAttr/Enable/Disable`只是注释声明，本阶段不调用这些接口。

播放步骤：

1. `CreateChn`，设置声卡类型、注册回调、设备音量和通道非静音。
2. `StartChn`。
3. 每帧最多1024个单声道样本（2048字节）；最后不足一帧也照实际长度发送。
4. 填入真实采样率、`AUDIO_BIT_WIDTH_16`、MONO、样本地址、mLen和相对时间戳。
5. `SendFrame(...,100)`，等待`MPP_EVENT_RELEASE_AUDIO_BUFFER`。
6. 全部输入释放后发送`SetStreamEof(TRUE,TRUE)`，等待EOF排空通知。
7. `StopChn`、`DestroyChn`。

一次只有一个在途帧。`AUDIO_FRAME_S`放在上下文中，不是函数栈上的临时变量；
PCM在AO销毁前始终有效。先设置pending，再调用SendFrame，
即使SDK在Send返回前执行回调也不会漏掉释放通知。

输入释放不等于扬声器已经播放完：前者允许复用帧，后者通过EOF排空确认。
释放等待最多2秒，EOF等待最多3秒；超时停AO、记故障并禁用后续声音。
这些应用层超时不能保证厂商驱动内部调用绝不阻塞，真实退出耗时须板测。

## 7. 启动、故障隔离与退出

正常模式：MPP及媒体/NPU启动 → 报警消费者启动 → 越线/区域生产者启动。
若`/lib/alarm.wav`缺失或格式不支持，会打印原因和
`monitoring continues without sound`，但继续进入监控主循环。

播放期间的AO创建/配置/发送/回调等待故障，会使本次运行的声音服务disabled。
不会无限重试播放或停止媒体线程；修复配置后重启应用重新加载。

Ctrl+C时：信号函数只设置标志；主线程先join区域和越线线程，
再置报警停止标志、广播条件变量、join播放线程，最后回收AO和PCM。
不会通过pthread_cancel强杀线程，也不会让已销毁的队列再接收业务回调。

若AO Stop/Destroy异常，不能确认SDK已停止使用PCM或cookie时，会保留上下文
并打印`Retaining context`，避免free后访问。该异常应按清理失败处理，
不是一次可宣称成功的验收；后续MPP退出及进程结束仍由主流程处理。

## 8. 构建与板端验证

Makefile已经扫描`sample/ipc_camera/app/*.c`，两个新C文件自动参加构建；
AO使用已有MPP链接库，不新增第三方库。主机测试文件不属于生产扫描目录。

在Linux虚拟机取得本次源码后执行：

```sh
./build.sh
```

将新`sample_strip`按之前方式传到开发板`/mnt/UDISK`。
只有本地改动已经提交并push后，虚拟机git pull才会取得；本阶段未自动提交或push。

先独立验声音，不同时运行另一份sample：

```sh
cd /mnt/UDISK
ls -lh /lib/alarm.wav
./sample_strip --audio-alarm-test
# 听到一次报警；日志应有Play finished: result=0 close=0。
# 再按Ctrl+C，确认AO和MPP退出。
```

诊断模式播放一次后等待Ctrl+C，不会循环报警。退出码0仅表示主流程正常退出，
仍须核对声音及completed/failed统计，不能只看退出码判断声音正确。

如果格式被拒绝，先在电脑查看文件，不修改系统原始报警资产：

```sh
ffprobe -v error -show_streams alarm.wav
ffmpeg -i alarm.wav -ac 1 -ar 32000 -c:a pcm_s16le alarm_pcm16.wav
```

把转换文件传到UDISK后测试候选文件：

```sh
./sample_strip --audio-alarm-test /mnt/UDISK/alarm_pcm16.wav
```

候选通过后再决定替换系统资产或调整main.c默认路径；当前正常监控模式
没有新增`--alarm-wav`参数，不要把诊断参数误当成完整监控模式。

正常监控验收：

1. 运行`./sample_strip`，确认`[ALARM] Ready`和原有媒体/NPU启动日志。
2. 从画面中央警戒线一侧走到另一侧，核对LINE事件与一次声音。
3. 冷却结束后，进入右半区域，核对REGION ENTER与声音；LEAVE本身不响。
4. 留在区域或快速来回移动，确认没有声音叠加，统计suppressed可以增长。
5. 当前中央线与右半区域边界相同，向右移动可能先产生LINE再产生ENTER；
   后者被冷却抑制是正常的。若要独立验区域来源，可临时让警戒线远离测试路径，
   或等待冷却后在右侧重新建立轨迹再进入确认；不能要求同次动作必须响两次。
6. 报警时观察LCD、VLC的RTSP音视频、MP4分段；报警可能被麦克风拾取进入录像，
   这是声学回声，不是应用主动混音，本阶段尚无AEC。
7. 播放过程中按Ctrl+C，确认退出不等待整个60秒WAV，统计可出现interrupted=1。
8. 连续启动/退出多次，无AO通道占用残留；完成后附完整日志及实际声音结果。

板子必须连接可用的CODEC/扬声器/功放。`Ready`只证明WAV加载和工作线程创建，
不证明AO已打开或扬声器接线正确；AO在实际有事件时才创建。

### 9.2 主机测试启动时上下文创建失败

现象：Windows测试第一次在`audio_alarm_create`处失败，尚未进入AO播放。
诊断：本机winpthreads的`pthread_condattr_setclock(CLOCK_MONOTONIC)`返回22（EINVAL）。
处理：仅在测试翻译单元使用Windows时钟转换适配；Linux生产代码仍要求
单调时钟条件变量，不用实时钟替代，以免NTP跳时影响报警等待。
复测：并发、故障、超时和退出测试通过。此问题属于主机测试环境，
不是开发板故障，也不是修改生产冷却逻辑的理由。

### 9.3 暂未出现的板端问题与定位入口

这些是排查指南，不是已发生事故：

- 没有Ready：先看路径、WAV格式和线程初始化错误。
- 有Ready无Play started：规则是否真正产出事件？是否正处于全局冷却？
- Play started后Create失败：检查同一AO是否被另一应用占用。
- release/EOF timeout：保留AO日志，核实当前SDK的异步回调行为与ALSA配置。
- completed增长却听不见：查扬声器/功放/设备静音和声卡，不据此盲目改NPU。
- 音频/录像出现变化：同时采集与播放属于全双工实际验收，主机AO替身不能证明。
