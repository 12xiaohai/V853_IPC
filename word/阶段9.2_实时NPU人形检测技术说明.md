# 阶段9.2：实时NPU人形检测技术说明

## 1. 阶段目标

阶段9.1已经证明`yolov8n.nb`能够在V853 NPU上加载、运行并正确解析输出。本阶段
把单帧验证接入摄像头实时视频，目标是：

1. 创建不影响预览和编码的NPU专用VI通路；
2. 持续取得`320x320 NV12`摄像头帧；
3. 常驻加载YOLOv8网络并循环执行NPU推理；
4. 只保留COCO类别0（person），执行置信度过滤和NMS；
5. 以线程安全快照发布检测框、PTS和推理耗时；
6. Ctrl+C时先结束线程，再销毁NPU和VI资源。

本阶段只输出检测日志和结果快照，暂不在视频上画框。检测框显示属于阶段9.3。

## 2. 为什么使用独立VIPP 8

当前系统已有三条视频通路：

| 用途 | VIPP | 尺寸/格式 | 数据去向 |
|---|---:|---|---|
| H.264主码流 | 0 | 1920x1080 NV21 | VENC、RTSP、MP4 |
| LCD预览 | 4 | 1920x1080 NV21 | G2D、VO |
| NPU检测 | 8 | 320x320 NV12 | AWNN、YOLOv8后处理 |

VIPP 8由ISP直接产生模型需要的低分辨率NV12图像。与“从1080P预览帧再用CPU缩放”
相比，它减少了大图复制、软件缩放和格式转换，也不会让NPU线程与LCD线程争抢
同一个VI虚拟通道。这与原项目`NnVipp = 8`、`NnViBufNum = 3`的架构一致。

三条VIPP共享摄像头与ISP，但拥有各自的缓冲和虚拟通道。每次成功调用
`AW_MPI_ISP_Run()`均在停止时配对调用`AW_MPI_ISP_Stop()`。

## 3. 数据流程

```text
MIPI CSI传感器
    -> ISP 0
    -> VIPP 8（320x320，NV12，10 FPS，3个缓冲）
    -> AW_MPI_VI_GetFrame
    -> 复制Y平面和UV平面到固定输入缓存
    -> AW_MPI_VI_ReleaseFrame
    -> awnn_set_input_buffers
    -> awnn_run
    -> awnn_get_output_buffers
    -> person筛选 + NMS
    -> 发布NpuDetectionSnapshot
```

输入缓存大小固定为：

```text
Y平面：  320 * 320 = 102400字节
UV平面： 320 * 160 =  51200字节
总大小：               153600字节
```

320已经满足32像素对齐，因此本阶段不需要额外补行。

## 4. 为什么先复制再ReleaseFrame

`AW_MPI_VI_GetFrame()`返回的虚拟地址属于MPP/VI缓冲池，应用不能永久保存。若在
整个NPU推理期间一直持有该帧，推理抖动可能耗尽3个采集缓冲，影响后续取帧。

本实现沿用原项目方法：

1. 取得VI帧；
2. 复制Y、UV两个平面到模块自己的153600字节缓存；
3. 立即归还VI帧；
4. 使用私有缓存完成推理。

这里每帧只复制150 KiB，且AI通路为10 FPS，代价远小于复制1080P帧。`GetFrame`
成功后的所有分支都必须执行`ReleaseFrame`，否则会形成帧泄漏。

## 5. 线程模型

原项目对每个检测模型使用一个工作线程，本阶段也采用一个实时NPU线程：

```text
取帧 -> 拷贝/还帧 -> 推理 -> 后处理 -> 发布快照 -> 下一帧
```

阶段9.1板端实测单帧推理约28 ms，而VIPP 8帧周期为100 ms，因此一条线程能够在
下一帧到来前处理完毕。应用不创建帧队列，不会发生队列无限增长。若未来更换为
更慢模型，才需要拆成取帧线程和推理线程，并使用容量为1的“最新帧槽位”。

`GetFrame`使用200 ms超时，而不是永久阻塞。这样设置`stop_requested`后，线程最多
等待一个超时周期便可退出，主线程能够安全`pthread_join()`。

## 6. AWNN生命周期

实时模式与阶段9.1单帧模式的区别是网络只创建一次：

```text
启动：awnn_get_info -> awnn_init -> awnn_create
循环：awnn_set_input_buffers -> awnn_run -> awnn_get_output_buffers
停止：退出线程 -> awnn_destroy -> awnn_uninit
```

如果每帧都重新加载模型，不仅耗时，还会反复申请VIP内存。当前结构使模型与线程
生命周期一致。独立的`--npu-self-test`模式执行完就退出进程，不会与正常实时模式
同时初始化AWNN。

## 7. 检测结果快照

`NpuDetectionSnapshot`包含：

- `sequence`：完成一次推理后递增；
- `frame_pts_us`：摄像头原始帧PTS；
- `inference_time_us`：本次NPU运行耗时；
- `detection_count`：person框数量；
- `detections[]`：置信度和320x320模型坐标。

NPU线程在互斥锁内整体替换快照。后续显示、越线和区域入侵模块通过
`npu_detector_get_latest()`复制快照，而不是持有模块内部指针。锁只保护一次小型
内存复制，不包围NPU推理，因此不会让消费者阻塞检测线程。

## 8. 启动和退出顺序

启动顺序：

```text
校验模型 -> 分配输入缓存 -> 初始化AWNN -> 创建网络
-> CreateVipp -> SetVippAttr -> ISP_Run -> EnableVipp
-> CreateVirChn -> EnableVirChn -> 创建推理线程
```

退出顺序：

```text
设置停止标志 -> pthread_join
-> DisableVirChn -> DestroyVirChn -> DisableVipp
-> ISP_Stop -> DestroyVipp
-> awnn_destroy -> awnn_uninit -> 释放输入缓存
```

每一步都有状态标志。即使启动到一半失败，也走同一条回滚路径，只释放已经创建
成功的资源。

## 9. 代码文件

| 文件 | 作用 |
|---|---|
| `sample/ipc_camera/include/npu_detector.h` | 配置、快照和公开接口 |
| `sample/ipc_camera/app/npu_detector.c` | VIPP 8、实时线程、AWNN生命周期 |
| `sample/ipc_camera/app/yolov8_postprocess.c` | person过滤与NMS |
| `sample/ipc_camera/app/main.c` | 配置、启动和逆序清理 |

Makefile会递归编译`sample`目录下的C文件，因此新增源文件不需要手工加入源文件列表。

## 10. 编译与板端验证

在Linux虚拟机执行：

```sh
cd ~/sample_demo
git pull --ff-only origin main
./build.sh
```

将`output/sample_strip`复制到开发板后运行：

```sh
cd /mnt/UDISK
chmod +x sample_strip
./sample_strip
```

有人进入镜头时，日志应周期性出现类似内容：

```text
[NPU] Realtime detector started: model=/lib/yolov8n.nb, vipp=8, chn=0,
      320x320@10fps, threshold=0.25, nms=0.45
[NPU] Realtime inference: frame=50, cost=28000 us, persons=1
[NPU] Person[0]: score=0.87, box=(80,35)-(230,310)
```

当前日志第一帧必输出，之后每50帧输出一次，防止10 FPS持续刷屏。日志间隔不影响
实际每帧推理和快照更新。
