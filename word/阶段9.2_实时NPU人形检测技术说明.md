# 阶段9.2：实时NPU人形检测技术说明

## 1. 阶段目标

阶段9.1已经证明`yolov8n.nb`能够在V853 NPU上加载、运行并正确解析输出。本阶段
把单帧验证接入摄像头实时视频，目标是：

1. 创建不影响预览和编码的NPU专用VI通路；
2. 持续取得`320x320 NV12`摄像头帧；
3. 常驻加载YOLOv8网络并循环执行NPU推理；
4. 只保留COCO类别0（person），执行置信度过滤和NMS；
5. 以线程安全快照发布检测框、PTS和推理耗时；
6. Ctrl+C时先结束线程，再销毁NPU和VI资源。

本阶段只输出检测日志和结果快照，暂不在视频上画框。检测框显示属于阶段9.3。

## 2. 为什么使用独立VIPP 8

当前系统已有三条视频通路：

| 用途 | VIPP | 尺寸/格式 | 数据去向 |
|---|---:|---|---|
| H.264主码流 | 0 | 1920x1080 NV21 | VENC、RTSP、MP4 |
| LCD预览 | 4 | 1920x1080 NV21 | G2D、VO |
| NPU检测 | 8 | 320x320 NV12 | AWNN、YOLOv8后处理 |

VIPP 8由ISP直接产生模型需要的低分辨率NV12图像。与“从1080P预览帧再用CPU缩放”
相比，它减少了大图复制、软件缩放和格式转换，也不会让NPU线程与LCD线程争抢
同一个VI虚拟通道。这与原项目`NnVipp = 8`、`NnViBufNum = 3`的架构一致。

三条VIPP共享摄像头与ISP，但拥有各自的缓冲和虚拟通道。每次成功调用
`AW_MPI_ISP_Run()`均在停止时配对调用`AW_MPI_ISP_Stop()`。

## 3. 数据流程

```text
MIPI CSI传感器
    -> ISP 0
    -> VIPP 8（320x320，NV12，10 FPS，3个缓冲）
    -> AW_MPI_VI_GetFrame
    -> 复制Y平面和UV平面到固定输入缓存
    -> AW_MPI_VI_ReleaseFrame
    -> awnn_set_input_buffers
    -> awnn_run
    -> awnn_get_output_buffers
    -> person筛选 + NMS
    -> 发布NpuDetectionSnapshot
```

输入缓存大小固定为：

```text
Y平面：  320 * 320 = 102400字节
UV平面： 320 * 160 =  51200字节
总大小：               153600字节
```

320已经满足32像素对齐，因此本阶段不需要额外补行。

## 4. 为什么先复制再ReleaseFrame

`AW_MPI_VI_GetFrame()`返回的虚拟地址属于MPP/VI缓冲池，应用不能永久保存。若在
整个NPU推理期间一直持有该帧，推理抖动可能耗尽3个采集缓冲，影响后续取帧。

本实现沿用原项目方法：

1. 取得VI帧；
2. 复制Y、UV两个平面到模块自己的153600字节缓存；
3. 立即归还VI帧；
4. 使用私有缓存完成推理。

这里每帧只复制150 KiB，且AI通路为10 FPS，代价远小于复制1080P帧。`GetFrame`
成功后的所有分支都必须执行`ReleaseFrame`，否则会形成帧泄漏。

## 5. 线程模型

原项目对每个检测模型使用一个工作线程，本阶段也采用一个实时NPU线程：

```text
取帧 -> 拷贝/还帧 -> 推理 -> 后处理 -> 发布快照 -> 下一帧
```

阶段9.1板端实测单帧推理约28 ms，阶段9.2首次运行约为30到36 ms，因此一条线程
能够在下一个10 FPS推理周期前处理完毕。应用不创建帧队列，不会发生队列无限
增长。若未来更换为更慢模型，才需要拆成取帧线程和推理线程，并使用容量为1的
“最新帧槽位”。

首次板端日志还证明：V853的次级VIPP在`use_current_win=1`时可能忽略设置的
`attributes.fps=10`，仍按传感器20 FPS返回帧。模块因此增加PTS限频：如果当前帧
距离上一次推理不足100000 us，就立即`ReleaseFrame`，不复制也不执行NPU。退出
日志分别统计`received`、`inferred`和`skipped`，便于确认限频是否生效。

`GetFrame`使用200 ms超时，而不是永久阻塞。这样设置`stop_requested`后，线程最多
等待一个超时周期便可退出，主线程能够安全`pthread_join()`。

## 6. AWNN生命周期

实时模式与阶段9.1单帧模式的区别是网络只创建一次：

```text
启动：awnn_get_info -> awnn_init -> awnn_create
循环：awnn_set_input_buffers -> awnn_run -> awnn_get_output_buffers
停止：退出线程 -> awnn_destroy -> awnn_uninit
```

如果每帧都重新加载模型，不仅耗时，还会反复申请VIP内存。当前结构使模型与线程
生命周期一致。独立的`--npu-self-test`模式执行完就退出进程，不会与正常实时模式
同时初始化AWNN。

## 7. 检测结果快照

`NpuDetectionSnapshot`包含：

- `sequence`：完成一次推理后递增；
- `frame_pts_us`：摄像头原始帧PTS；
- `inference_time_us`：本次NPU运行耗时；
- `detection_count`：person框数量；
- `detections[]`：置信度和320x320模型坐标。

NPU线程在互斥锁内整体替换快照。后续显示、越线和区域入侵模块通过
`npu_detector_get_latest()`复制快照，而不是持有模块内部指针。锁只保护一次小型
内存复制，不包围NPU推理，因此不会让消费者阻塞检测线程。

## 8. 启动和退出顺序

启动顺序：

```text
校验模型 -> 分配输入缓存 -> 初始化AWNN -> 创建网络
-> CreateVipp -> SetVippAttr -> ISP_Run -> EnableVipp
-> CreateVirChn -> EnableVirChn -> 创建推理线程
```

退出顺序：

```text
设置停止标志 -> pthread_join
-> DisableVirChn -> DestroyVirChn -> DisableVipp
-> ISP_Stop -> DestroyVipp
-> awnn_destroy -> awnn_uninit -> 释放输入缓存
```

每一步都有状态标志。即使启动到一半失败，也走同一条回滚路径，只释放已经创建
成功的资源。

## 9. 代码文件

| 文件 | 作用 |
|---|---|
| `sample/ipc_camera/include/npu_detector.h` | 配置、快照和公开接口 |

| `sample/ipc_camera/app/yolov8_postprocess.c` | person过滤与NMS |
| `sample/ipc_camera/app/main.c` | 配置、启动和逆序清理 |

```text
[NPU] Realtime detector started: model=/lib/yolov8n.nb, vipp=8, chn=0,
      320x320@10fps, threshold=0.25, nms=0.45
```

## 12. 当前状态

阶段9.2已经在V853完成第一次实时运行，日志结果如下：

- ARM交叉编译、链接和板端启动成功；
- `/lib/yolov8n.nb`成功分配4522312字节VIP内存并创建网络；
- VIPP 8以`320x320 NV12`、3个缓冲成功启动；
- 约35秒内完成699次推理，单次耗时约30到36 ms，`failures=0`；
- LCD预览、H.264、AAC、RTSP和MP4在检测期间持续工作；
- RTSP统计视频和音频均无队列丢帧；
- Ctrl+C后先退出NPU线程，再关闭VIPP 8并释放VIP内存；
- 应用最终以退出码0结束。

第一次日志同时发现VIPP 8实际按约20 FPS返回帧，没有遵守配置的10 FPS。代码已
增加基于VI PTS的应用层限频，需要重新编译确认退出统计接近
`received : inferred : skipped = 2 : 1 : 1`。

第二次板端复测已经确认PTS限频生效：第1次推理日志时间为`19:42:49.610`，第50次
为`19:42:54.554`，49个推理间隔共耗时约4.944秒，对应约9.91 FPS，符合配置的
10 FPS。单次NPU耗时约31到34 ms，仍明显小于100 ms推理周期。由于本次提供的
日志在运行过程中截断，尚未取得退出时的`received/inferred/skipped/failures`
完整统计，下一次正常Ctrl+C退出时仍需核对该项。

第三次完整复测已经取得退出统计：

```text
received=437, inferred=214, skipped=223, failures=0
```

`214 + 223 = 437`，证明每个取得的VI帧都进入“执行推理”或“限频跳过”之一，没有
丢失所有权；实际推理与跳过数量接近1:1，也与20 FPS输入限频到10 FPS相符。运行
约22秒完成214次推理，对应约9.7 FPS。Ctrl+C后线程先退出，随后VIPP 8关闭、VIP
内存释放，应用最终退出码为0，因此限频、帧生命周期和退出顺序均已通过。

前几次日志中的检测输出始终为`persons=0`。最初测试只露出人脸，不能作为COCO
person检测的充分条件；随后已经让完整人体进入镜头，但连续307次有效推理仍为0。
因此现在不能继续归因于测试姿态，需要抓取VIPP 8实际送入AWNN的输入帧，检查
裁剪、方向、平面顺序和像素格式。

代码现已启用一次性调试抓帧。为方便单人测试，程序不会抓启动瞬间的空画面，
而是在第50个有效推理帧（启动后约5秒）保存：

```text
/mnt/UDISK/npu_realtime_320x320.nv12
```

它是复制到私有缓存、准备传给`awnn_set_input_buffers()`的同一份153600字节数据，
不是从预览或编码文件间接截取。运行程序后应立即走入摄像头并保持到抓帧日志出现。
文件只在每次启动时写一次，且写入前已经归还VI
源帧，不会长期占用MPP采集缓冲。诊断完成后应把`main.c`中的
`debug_dump_path`改回`NULL`，避免产品模式每次启动都写调试文件。另外
第一次日志中两次出现`video4 fifo overflow`；第二次降低NPU推理频率后仍出现一次，
说明该提示不只是“推理频率过高”造成。第一次运行的预览最终
`submitted=released=725`且`dropped=0`，暂未观察到应用层帧泄漏或持续黑屏，
但仍需在30分钟稳定性测试中统计其发生频率并观察画面是否实际卡顿。

第三次运行还出现107次TinyServer底层`sendTo()`返回
`Resource temporarily unavailable`。应用自己的RTSP队列最终统计仍为
`video=451/451 dropped=0, audio=346/346 dropped=0`，所以这不是NPU线程或应用
有界队列丢帧，而是RTSP客户端使用UDP时，Wi-Fi/内核套接字发送缓存短时拥塞。
后续稳定性测试优先让客户端改用RTSP over TCP；若UDP仍必须使用，再考虑降低
H.264码率或增大发送缓冲。

## 13. 实时输入抓帧诊断步骤

重新编译运行后，先确认日志出现：

```text
[NPU] Debug input saved: file=/mnt/UDISK/npu_realtime_320x320.nv12,
      format=NV12, size=320x320, bytes=153600
```

在开发板检查文件大小：

```sh
ls -l /mnt/UDISK/npu_realtime_320x320.nv12
```

停止正常监控程序后，用完全相同的模型和后处理离线运行这张实时帧：

```sh
./sample_strip --npu-self-test /lib/yolov8n.nb \
    /mnt/UDISK/npu_realtime_320x320.nv12
echo $?
```

把文件复制到电脑或虚拟机，先按NV12查看：

```sh
ffplay -f rawvideo -pixel_format nv12 -video_size 320x320 \
    npu_realtime_320x320.nv12
```

再按NV21查看一次，用于排查UV/VU平面顺序：

```sh
ffplay -f rawvideo -pixel_format nv21 -video_size 320x320 \
    npu_realtime_320x320.nv12
```

判断方法：

- NV12画面颜色正常且包含完整人体：继续检查方向、模型阈值和输出张量；
- NV21颜色正常而NV12明显偏色：VIPP实际输出为NV21，需要修正格式配置；
- 两种格式都裁剪掉人体：检查`use_current_win`与VIPP 8缩放/裁剪行为；
- 画面错行或撕裂：不能再假设stride等于320，需要按实际平面跨度复制；
- 离线自检能检测、实时模式不能：检查实时AWNN输入切换和线程状态；
- 离线自检仍为0：问题可缩小到该输入帧、方向/格式、阈值或模型本身。
