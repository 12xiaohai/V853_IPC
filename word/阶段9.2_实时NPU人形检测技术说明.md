# 阶段9.2：实时NPU人形检测技术说明

## 1. 阶段目标

阶段9.1已经证明`yolov8n.nb`能够在V853 NPU上加载、运行并正确解析输出。本阶段
把单帧验证接入摄像头实时视频，目标是：

1. 创建不影响预览和编码的NPU专用VI通路；
2. 持续取得`320x320 NV12`摄像头帧；
3. 常驻加载YOLOv8网络并循环执行NPU推理；
4. 只保留COCO类别0（person），执行置信度过滤和NMS；
5. 以线程安全快照发布检测框、PTS和推理耗时；
6. Ctrl+C时先结束线程，再销毁NPU和VI资源。

本阶段只输出检测日志和结果快照，暂不在视频上画框。检测框显示属于阶段9.3。

## 2. 为什么使用独立VIPP 8

当前系统已有三条视频通路：

| 用途 | VIPP | 尺寸/格式 | 数据去向 |
|---|---:|---|---|
| H.264主码流 | 0 | 1920x1080 NV21 | VENC、RTSP、MP4 |
| LCD预览 | 4 | 1920x1080 NV21 | G2D、VO |
| NPU检测 | 8 | 320x320 NV12 | AWNN、YOLOv8后处理 |

VIPP 8由ISP直接产生模型需要的低分辨率NV12图像。与“从1080P预览帧再用CPU缩放”
相比，它减少了大图复制、软件缩放和格式转换，也不会让NPU线程与LCD线程争抢
同一个VI虚拟通道。这与原项目`NnVipp = 8`、`NnViBufNum = 3`的架构一致。

三条VIPP共享摄像头与ISP，但拥有各自的缓冲和虚拟通道。每次成功调用
`AW_MPI_ISP_Run()`均在停止时配对调用`AW_MPI_ISP_Stop()`。

## 3. 数据流程

```text
MIPI CSI传感器
    -> ISP 0
    -> VIPP 8（320x320，NV12，10 FPS，3个缓冲）
    -> AW_MPI_VI_GetFrame
    -> 复制Y平面和UV平面到固定输入缓存
    -> AW_MPI_VI_ReleaseFrame
    -> awnn_set_input_buffers
    -> awnn_run
    -> awnn_get_output_buffers
    -> person筛选 + NMS
    -> 发布NpuDetectionSnapshot
```

输入缓存大小固定为：

```text
Y平面：  320 * 320 = 102400字节
UV平面： 320 * 160 =  51200字节
总大小：               153600字节
```

320已经满足32像素对齐，因此本阶段不需要额外补行。

## 4. 为什么先复制再ReleaseFrame

`AW_MPI_VI_GetFrame()`返回的虚拟地址属于MPP/VI缓冲池，应用不能永久保存。若在
整个NPU推理期间一直持有该帧，推理抖动可能耗尽3个采集缓冲，影响后续取帧。

本实现沿用原项目方法：

1. 取得VI帧；
2. 复制Y、UV两个平面到模块自己的153600字节缓存；
3. 立即归还VI帧；
4. 使用私有缓存完成推理。

这里每帧只复制150 KiB，且AI通路为10 FPS，代价远小于复制1080P帧。`GetFrame`
成功后的所有分支都必须执行`ReleaseFrame`，否则会形成帧泄漏。

## 5. 线程模型

原项目对每个检测模型使用一个工作线程，本阶段也采用一个实时NPU线程：

```text
取帧 -> 拷贝/还帧 -> 推理 -> 后处理 -> 发布快照 -> 下一帧
```

阶段9.1板端实测单帧推理约28 ms，阶段9.2首次运行约为30到36 ms，因此一条线程
能够在下一个10 FPS推理周期前处理完毕。应用不创建帧队列，不会发生队列无限
增长。若未来更换为更慢模型，才需要拆成取帧线程和推理线程，并使用容量为1的
“最新帧槽位”。

首次板端日志还证明：V853的次级VIPP在`use_current_win=1`时可能忽略设置的
`attributes.fps=10`，仍按传感器20 FPS返回帧。模块因此增加PTS限频：如果当前帧
距离上一次推理不足100000 us，就立即`ReleaseFrame`，不复制也不执行NPU。退出
日志分别统计`received`、`inferred`和`skipped`，便于确认限频是否生效。

`GetFrame`使用200 ms超时，而不是永久阻塞。这样设置`stop_requested`后，线程最多
等待一个超时周期便可退出，主线程能够安全`pthread_join()`。

## 6. AWNN生命周期

实时模式与阶段9.1单帧模式的区别是网络只创建一次：

```text
启动：awnn_get_info -> awnn_init -> awnn_create
循环：awnn_set_input_buffers -> awnn_run -> awnn_get_output_buffers
停止：退出线程 -> awnn_destroy -> awnn_uninit
```

如果每帧都重新加载模型，不仅耗时，还会反复申请VIP内存。当前结构使模型与线程
生命周期一致。独立的`--npu-self-test`模式执行完就退出进程，不会与正常实时模式
同时初始化AWNN。

## 7. 检测结果快照

`NpuDetectionSnapshot`包含：

- `sequence`：完成一次推理后递增；
- `frame_pts_us`：摄像头原始帧PTS；
- `inference_time_us`：本次NPU运行耗时；
- `detection_count`：person框数量；
- `detections[]`：置信度和320x320模型坐标。

NPU线程在互斥锁内整体替换快照。后续显示、越线和区域入侵模块通过
`npu_detector_get_latest()`复制快照，而不是持有模块内部指针。锁只保护一次小型
内存复制，不包围NPU推理，因此不会让消费者阻塞检测线程。

## 8. 启动和退出顺序

启动顺序：

```text
校验模型 -> 分配输入缓存 -> 初始化AWNN -> 创建网络
-> CreateVipp -> SetVippAttr -> ISP_Run -> EnableVipp
-> CreateVirChn -> EnableVirChn -> 创建推理线程
```

退出顺序：

```text
设置停止标志 -> pthread_join
-> DisableVirChn -> DestroyVirChn -> DisableVipp
-> ISP_Stop -> DestroyVipp
-> awnn_destroy -> awnn_uninit -> 释放输入缓存
```

每一步都有状态标志。即使启动到一半失败，也走同一条回滚路径，只释放已经创建
成功的资源。

### 13.3 VIPP 8硬件180度方向校正

工程现在只对NPU使用的VIPP 8启用两个硬件变换：

```c
npu_config.mirror = 1;
npu_config.flip = 1;
```

水平镜像和垂直翻转同时开启，等效于旋转180度。调用顺序为：

```text
CreateVipp -> SetVippAttr -> ISP_Run -> EnableVipp
           -> SetVippMirror(1) -> SetVippFlip(1)
           -> CreateVirChn -> EnableVirChn
```

`SetVippMirror/SetVippFlip`必须在`EnableVipp`完成stream-on之后执行，
这与V853 SDK参考代码的要求一致。因为操作的是VIPP 8，所以预期不改变
VIPP 4 LCD预览和VIPP 0 H.264编码通路。启动日志也会输出
`mirror=1, flip=1`，便于确认配置已生效。

修正后的验收条件是：

1. 新导出的`npu_realtime_320x320.nv12`按NV12查看时人物正立；
2. 人体正常站立时，实时日志能连续而不是偶发输出`persons=1`；
3. LCD预览、H.264、RTSP和MP4的方向与修改前一致；
4. 退出时仍为`failures=0`，不留下VI帧或NPU资源。

> 注意：本次首个检测的`score=1.642`超出了常规的`0~1`置信度区间。
> 这不影响“模型已经检出人形”的结论，但方向修正验收后，还要核对模型
> 输出张量是否已带sigmoid，避免在后处理中少做或重复做sigmoid。

退出。后续30分钟稳定性测试仍需观察LCD是否有真实卡顿，并统计提示频率。

### 13.5 检测分数固定为1.642的根因

方向校正后仍不能立即宣布9.2完全验收，因为所有检测框的`score`始终
精确等于`1.642`，而且相邻帧频繁出现`persons=1 -> 0 -> 1`。检查
`yolov8-nv12/ovxilb/yolov8n-sim_nbg_unify/nbg_meta.json`后发现输出张量为：

```text
shape      = [1, 84, 2100]
qtype      = UINT8 asymmetric affine
min/max    = 0 / 418.781799
scale      = 1.6422815322875977
zero_point = 0
```

日志中的`1.642`恰好是该张量的一个量化步长。YOLOv8这个单一张量同时
包含最高数百的框坐标和`0~1`的类别概率。两类数据共用较大的UINT8量化步长
后，person概率几乎只能变成`0.000`或`1.6422815`两档，导致原始置信度
精度丢失和帧间检测闪烁。

所以这不是少调用一次sigmoid，也不能通过把`1.642`强行截断为`1.0`解决；
截断只会修改显示值，不能恢复量化时丢失的概率精度。重新核对配套课件后
确认，这不是`add_postproc_node`配置错误，而是课程专门说明的YOLOv8纯UINT8
量化精度问题。课件给出的两种方向是：最终输出使用INT16混合量化，或者把
后处理放到CPU；本项目采用前者。

后续应在模型部署环境中把最终`Concat_/model.22/Concat_5_1`节点改为
`dynamic_fixed_point-i16`并重新生成NBG。新模型必须先确认
`nbg_meta.json`不再把整个`[1,84,2100]`张量作为步长1.642的UINT8输出，
再旁路上板复测。

定位到该问题时的阶段状态为：**实时链路和方向校正通过，人形已能检出；输出
量化精度问题尚未修正。** 后续修复与最新验收状态见13.6至13.8。

### 13.6 依据配套课件实施的混合量化修复

本次查阅了课程中的《20-8 YOLOV8模型部署》《20-9 混合量化部署》、
《20-10 模型增加前处理实现YUV输入》和《21-1 视频流人形检测部署》。其中
《20-8》明确指出YOLOv8做UINT8量化后会出现检测概率值不变、效果变差；
《20-9》给出的修复是编辑`yolov8n-sim.quantize`：

```yaml
customized_quantize_layers:
  Concat_/model.22/Concat_5_1: dynamic_fixed_point-i16
```

然后在`pegasus quantize`中增加`--hybrid`，继续使用该量化表重新执行量化、
预推理和`pegasus export ovxlib`。网络主体仍采用UINT8，最终输出采用动态
定点INT16，从而提高类别概率的分辨率。后处理配置则恢复课程生成值：

```yaml
add_postproc_node: false
force_float32: true
```

因此，先前“把`add_postproc_node`改成true即可得到浮点输出”的判断作废，
不得按该旧方案重生成模型。

同时新增`yolov8-nv12/validate_nbg_meta.py`，用来在部署前自动检查
`nbg_meta.json`。脚本接受课程指定的`dynamic_fixed_point-i16`输出，也兼容
工具链可能生成的float16/float32输出；发现当前这种UINT8低精度输出时返回
非0，防止误覆盖板端模型。

当前Windows工作区不包含Acuity 6.9.3和OVXLIB 1.1.34可执行环境，因此已完成
混合量化配置和验收门禁，但新`.nb`文件必须回到原模型转换环境中重新生成。
旧的`nbg_meta.json`已经用等价的JSON检查确认会被门禁拒绝，原因是它仍包含
`scale=1.6422815322875977`的量化输出。

正常监控程序同时新增了候选模型参数：

```sh
./sample_strip --npu-model /mnt/UDISK/yolov8n_hybrid_i16.nb
```

该参数只改变本次运行的NPU模型路径，不覆盖`/lib/yolov8n.nb`，新模型失败时
可直接去掉参数回退到旧模型。

### 13.7 NV12混合量化模型重新部署问题复盘

第一次按照混合量化流程重新生成模型后，正常监控模式中的日志表明新模型已经
完成NPU加载和实时检测通道初始化：

```text
VIP memory = 4802947
awnn_create成功
VIPP 8启动成功
Realtime detection thread started
...
gckvip_drv_exit
Segmentation fault
```

崩溃发生在实时检测线程启动后的第一次NPU推理附近，而不是应用启动早期。此时
LCD预览、音频采集/编码、RTSP和MP4模块均已完成各自初始化，日志中也没有这些
模块的致命错误。因此不能把该段错误归因于LCD、音频或MP4；`VIP memory =
4802947`以及`awnn_create`成功只说明模型文件能够被NPU运行时加载和创建，并不
代表应用提供的输入张量数量、形状和缓冲区长度与模型一致。日志中的
`gckvip_drv_exit`是崩溃后的NPU驱动清理表现，不是最初故障原因。

为了隔离其他业务模块，随后使用同一个新模型执行`--npu-self-test`。单帧自测同样
在`awnn_run()`附近失败，但信号表现为`Bus error`，进程返回码为135。正常监控的
`Segmentation fault`和隔离自测的`Bus error`虽然信号不同，却都发生在第一轮NPU
输入/推理阶段，并且随模型更换出现，因此共同把故障范围缩小到新NBG与应用输入
接口的兼容性，而不是多媒体链路。

该模型的`nbg_meta.json`显示只有一个
`[1,3,320,320]`的INT8输入，而应用传入的是320x320 NV12两平面数据：

```text
Y平面  = 320 * 320 = 102400字节
UV平面 = 320 * 160 =  51200字节
合计                   153600字节
```

模型单输入张量需要`1 * 3 * 320 * 320 = 307200`字节，接口数量和缓冲区大小
均与应用不一致，因此发生越界访问。根因是输入元数据仍配置为：

```yaml
add_preproc_node: false
preproc_type: IMAGE_RGB
```

修正为以下配置并重新量化、导出后，`nbg_meta.json`已得到与应用一致的两个
UINT8输入：

```yaml
add_preproc_node: true
preproc_type: IMAGE_NV12
```

```text
输入0：[1, 1, 320, 320]，UINT8（Y平面）
输入1：[1, 1, 160, 320]，UINT8（UV平面）
```

这一步解决的是输入接口和内存布局问题，只能证明NV12前处理节点已经加入，
不能证明输出混合量化已经生效。

第二次检查发现，最终`[1,84,2100]`输出仍是`asymmetric_affine-i8`，量化步长
仍为`1.6421838998794556`。排查过程中发现两个独立问题：

1. 最初的`dynamic_fixed_point-i16`中曾混入Unicode特殊连字符，工具没有识别；
2. 只指定内部`Concat_/model.22/Concat_5_1`时，内部张量已经变成INT16，但
   对外的`attach_Concat_/model.22/Concat_5/out0_0`输出节点仍保持INT8，最终
   `nbg_meta.json`记录的正是这个attach节点。

最终量化配置同时覆盖内部计算节点和对外输出节点：

```yaml
customized_quantize_layers:
  Concat_/model.22/Concat_5_1: dynamic_fixed_point-i16
  attach_Concat_/model.22/Concat_5/out0_0: dynamic_fixed_point-i16
```

注意上述`-`必须是ASCII减号。修改后重新执行`pegasus quantize --hybrid`，且
不能添加`--rebuild`，否则可能重新生成量化表并覆盖手工配置。本次重新量化后
已经确认量化表顶部两个节点均为：

```yaml
qtype: i16
quantizer: dynamic_fixed_point
rounding: rtne
max_value: 418.75689697265625
min_value: 7.628663934847437e-17
fl: 6
```

其中`fl=6`是本次校准数据计算出的结果，不应在其他模型中硬编码；验收重点是
内部Concat和对外attach节点均使用`i16 + dynamic_fixed_point`。

完成混合量化后必须删除或备份旧的`ovxilb/yolov8n-sim_nbg_unify`目录，再依次
执行量化预推理和`pegasus export ovxlib`，避免误读旧导出产物。新模型只有同时
满足以下条件才允许上传开发板：

1. `nbg_meta.json`包含两个NV12 UINT8输入，形状分别为`[1,1,320,320]`和
   `[1,1,160,320]`；
2. 输出形状为`[1,84,2100]`；
3. 对外输出不再是步长约1.642的INT8量化，而是动态定点INT16；
4. `--npu-self-test`和实时模式均不再出现`Bus error`或`Segmentation fault`，
   自测返回码为0；
5. 同一张包含正立人体的NV12测试帧能够产生合理的`0~1`置信度；
6. 候选模型通过`--npu-model`旁路实时测试后，才能替换`/lib/yolov8n.nb`。

当前状态：**NV12双输入和双输出节点混合量化配置已经修正，量化表已确认两个
输出节点均为i16、`fl=6`；NBG元数据、单帧推理和实时检测功能验收均已通过，
仍需完成30分钟稳定性测试。**

### 13.8 新旧模型核对与INT16候选模型单帧验收

第一次修复后仍出现崩溃，并不是新INT16模型运行失败。板端实际加载的文件仍为
旧错误模型：

随后把新模型放在`/mnt/UDISK/yolov8n.nb`，不覆盖系统模型。第一次执行自测时
因Shell续行符使用错误，NV12路径没有作为第二个参数传入，程序以代码1退出；
下一行又被Shell当成可执行文件，因此出现`Permission denied`和代码126。这两个

#### 13.8.1 实时旁路验收结果

使用候选模型执行完整监控程序后，系统持续运行约45秒并由Ctrl+C正常退出。NPU
线程统计为：

```text
received=895
inferred=434
skipped=461
failures=0
```

`434 + 461 = 895`，说明所有VIPP 8输入帧均被推理或被10 FPS限流逻辑跳过，没有
帧所有权泄漏。按运行时长估算，VIPP 8接收约20 FPS，NPU有效推理约9.7 FPS；
单次推理耗时主要为34~41 ms，满足100 ms推理周期。

混合量化修复后的person置信度不再固定为`1.642`，实测出现：

```text
0.281, 0.312, 0.359, 0.406, 0.453, 0.500, 0.547, 0.641
```

这些数值均在合理的`0~1`范围内，并符合`fl=6`对应的`1/64`动态定点分辨率，证明
INT16输出被AWNN正确转换，原UINT8步长过大造成的概率精度丢失已经修复。日志中
多次得到`persons=1`和随人体位置变化的检测框，实时人形检测链路已经生效。

本次同时验证了其他功能链路：

- LCD预览：`submitted=928, released=928, dropped=0`；
- H.264编码：916帧，约28.2 MB；
- AAC编码：711帧，约177 KB；
- MP4：视频916帧、音频711帧，跳过数均为0，成功完成1个文件；
- RTSP：视频`916/916`、音频`711/711`，应用队列丢帧均为0；
- NPU：退出前先停止线程，再释放VIPP 8和VIP内存；
- 应用最终退出码为0。

运行期间出现两次`video4 fifo overflow`，但没有造成预览丢帧、编码失败、NPU
失败或异常退出。该提示继续列入30分钟稳定性测试观察项，不影响本次功能验收。

相邻帧仍会出现`persons=1 -> 0 -> 1`，部分置信度接近0.25阈值。这已不再是量化
步长固定问题，而属于低置信度目标的帧间抖动；后续越线和区域入侵模块不应直接
使用单帧结果触发报警，应增加连续命中、丢失容忍或时间窗口状态机。

阶段9.2当前结论：**实时NPU人形检测功能验收通过；模型可以备份旧版本后部署到
`/lib/yolov8n.nb`。长时间稳定性和报警防抖将在后续阶段继续验证。**
