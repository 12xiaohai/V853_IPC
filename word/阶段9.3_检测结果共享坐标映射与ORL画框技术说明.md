## 1. 阶段目标

阶段9.2已经能在独立VIPP 8上完成320x320 NV12实时人形检测，但检测结果只在日志中可见。本阶段完成以下工作：

1. 从NPU线程安全获取最新检测快照；
2. 把320x320模型坐标映射到1920x1080编码画面；
3. 确认NPU通路与编码通路的实际方向关系；
4. 沿用原项目MPP `ORL_RGN`方式绘制人形矩形框；
5. 无目标时立即清框，NPU长时间无新结果时超时清框；
6. 不阻塞NPU推理线程，不破坏时间OSD、RTSP和MP4录像。

## 2. 为什么选择MPP ORL

原项目的`paint_objects()`并不会在CPU上逐像素修改NV21/NV12画面，而是：

1. 创建`ORL_RGN`区域；
2. 设置矩形位置、颜色、线宽和图层；
3. 把region附着到指定VIPP；
4. 由MPP硬件在通路内完成叠加。

本阶段沿用该方案，主要优点是：

- 不需要频繁复制1920x1080大尺寸图像；
- 画框不占用大量CPU时间；
- 附着到VIPP 0后，检测框会直接进入H.264编码结果；
- RTSP和MP4复用同一路H.264，因此会同时看到检测框。

## 3. 模块关系

```text
VIPP 8 (320x320 NV12)
        |
        v
   NPU推理线程
        |
        | 发布NpuDetectionSnapshot（互斥量保护）
        v
 detection_overlay结果消费线程
        |
        | 方向关系校验 + 缩放 + 2像素对齐
        |
        |-- ORL handles 100..115 -> VIPP 0 -> VENC 0
        |                                      |-- H.264裸流
        |                                      |-- RTSP
        |                                      `-- MP4
        |
        `-- ORL handles 200..215 -> VIPP 4 -> GetFrame -> G2D旋转 -> VO -> LCD
```

NPU线程只负责发布快照，编码与LCD画框上下文分别通过`npu_detector_get_latest()`拷贝数据。它们不共享可变指针，也不会在推理期间调用RGN接口。由于RGN句柄是MPP全局资源，两个画框线程使用模块内的全局互斥量串行化Create/Attach/Detach/Destroy操作。

## 4. 坐标映射

### 4.1 基本缩放

YOLOv8输出坐标域为320x320，编码画面为1920x1080。不考虑方向时：

```text
video_x = model_x * 1920 / 320
video_y = model_y * 1080 / 320
```

X和Y必须分别使用宽度和高度缩放比，不能共用一个比例。

### 4.2 共享sensor方向与重复变换问题

VIPP 8实测图像倒置，因此NPU启动时同时调用了`AW_MPI_VI_SetVippMirror(8, 1)`和`AW_MPI_VI_SetVippFlip(8, 1)`。最初假设这两个选项只影响VIPP 8，因此画框代码又对坐标做了180度反变换。

2026-10-02板端日志给出了实际行为：

```text
[ISP] sensor set hflip : 1, vflip : 1
```

这说明当前驱动实际修改的是VIPP 0和VIPP 8共享的sensor方向，两条通路会同时看到校正后的图像。因此坐标只需要从320x320缩放到1920x1080，不能再执行额外的mirror/flip。

当前正确配置为：

```text
map_mirror = 0
map_flip   = 0
```

如果对同方向的坐标再做一次反变换，检测框会被重复旋转并出现在人物对角。代码仍保留`map_mirror/map_flip`配置项，仅供未来使用真正独立方向的图像通路时启用。

### 4.3 边界与对齐

映射后还会执行：

- 坐标限制在画面边界内；
- 左上角向下取2像素对齐；
- 右下角向上取2像素对齐；
- 矩形宽高至少为2像素。

这可避免MPP因越界或非法对齐拒绝附着region。

## 5. RGN资源与OSD共存

| 用途 | 附着目标 | RGN句柄 |
|---|---|---:|
| 时间OSD | VENC 0 | 0 |
| 编码人形检测框 | VIPP 0 | 100～115 |
| LCD人形检测框 | VIPP 4 | 200～215 |

检测框和时间OSD使用不同句柄范围，而且附着层级不同，因此可以共存。当一个新快照到来时，程序按以下顺序刷新：

1. `AW_MPI_RGN_DetachFromChn`拆除旧框；
2. `AW_MPI_RGN_Destroy`销毁旧region；
3. `AW_MPI_RGN_Create`创建新ORL region；
4. `AW_MPI_RGN_AttachToChn`附着新矩形。

这一顺序与原项目一致。当前最多绘制16个人形框，避免异常结果无限占用region资源。

## 6. 过期框清理

两个画框线程各自每50 ms读取一次快照：

- `sequence`变化：立即刷新框；
- 新快照的`detection_count=0`：立即清除旧框；
- 500 ms没有任何新快照：判定NPU结果过期并清框。

超时使用`CLOCK_MONOTONIC`，不会受开发板NTP校时影响。

## 7. 启停顺序

启动顺序：

```text
VIPP 0 / VENC + VIPP 4 / G2D / VO -> NPU detector
    -> encoding detection overlay -> LCD detection overlay
```

停止顺序：

```text
LCD detection overlay -> encoding detection overlay -> NPU detector
    -> VENC / preview VI
```

两个画框上下文分别依赖VIPP 0和VIPP 4，并且都依赖NPU快照，因此必须在NPU、VENC和预览VI之前停止。它们退出时会拆除各自的region，防止下次启动遇到句柄冲突。

## 10. 当前范围与后续工作

编码主码流使用VIPP 0上的ORL，所以H.264、RTSP和MP4可见。LCD预览使用另一条VIPP 4 -> G2D -> VO通路，因此新增第二组ORL句柄200～215，在1920x1080的VIPP 4帧上画框。之后G2D将图像和框整体旋转270度，不需要对检测框另外计算480x800 LCD坐标。

当前后处理只保留COCO类别0（person），因此黄色框本身就表示person。ORL硬件区域只负责绘制线框，置信度继续由`[NPU] Result[...] score=...`日志输出，本阶段不在画面上额外渲染文字，以保持和原项目相同的低开销实现。

板端验证本阶段通过后，下一小阶段进入区域入侵规则：使用人形框底边中点作为人员位置，判断该点是否进入配置多边形。

## 11. 本阶段可能遇到的问题

### 11.1 有检测日志，但RTSP中没有框

优先查看是否有`Create region failed`或`Attach region failed`。检查编码目标是否为`VIPP0:0`且句柄为100～115；LCD目标应为`VIPP4:0`且句柄为200～215。

### 11.2 框在人物的对角

首先检查启动日志是否出现`[ISP] sensor set hflip:1, vflip:1`。当前V853驱动会让VIPP 0和VIPP 8共享该方向，因此应使用`map_mirror=0`和`map_flip=0`。如果配置为1，坐标会被重复旋转180度。

### 11.6 检测框能显示，但位置在人物对角或明显偏移

2026-10-02第二次验证时，ORL线程已经正常更新，NPU也连续输出了合理的人形坐标，但框位置不准。根据同一份日志中的`[ISP] sensor set hflip:1, vflip:1`可以确定，根因是将sensor级方向变换误判为VIPP 8私有变换，导致画框坐标多做了180度反变换。

当时修复在main.c中将两个映射开关设为0；当前默认值迁移到config.c的
`config->overlay.map_mirror/map_flip`，LCD配置由`config->lcd_overlay`继承。
application.c分别连接NPU对象并启动两个ORL。ORL日志仍同时输出模型与视频坐标：

```text
[ORL] Box map: sequence=..., model=(xmin,ymin)-(xmax,ymax),
      video=(left,top)-(right,bottom), drawn=1
```

例如模型框`(160,160)-(320,320)`应大致映射为视频框`(960,540)-(1920,1080)`。该日志可以继续区分“方向错误”和“缩放/裁剪误差”。

### 11.3 框停在旧位置

检查NPU的`sequence`是否继续增加。若NPU无新快照，程序应在500 ms后输出`Stale detection boxes cleared`并清框。

### 11.4 频繁报region句柄已存在

检查退出顺序，必须在销毁VIPP 0之前执行`detection_overlay_stop()`。正常停止会先Detach再Destroy所有活动句柄。

### 11.5 RTSP和录像有框，但LCD没有框

这是两条不同VIPP通路造成的：VIPP 0上的ORL只会进入VENC，不能自动出现在VIPP 4预览帧。应确认启动日志同时出现`target=VIPP4:0`和`handles=200..215`，并检查是否存在VIPP 4的`Create region failed`或`Attach region failed`。

LCD通路的框在VIPP 4的1920x1080原始方向上绘制，随后由G2D和图像一起旋转270度。因此这里不能再次把检测坐标换算成480x800，否则会产生重复旋转或缩放。如果VIPP 4日志持续显示`drawn=1`但LCD仍没有框，则说明当前固件的VI ORL处理点位于`GetFrame`之后，需要改用G2D前的软件NV21画框或独立VO图层；应保留日志并据此选择兼容方案。

### 12.2 2026-10-02 LCD画框验证结论

板端实测确认LCD上能够显示并刷新人形检测框，证明当前固件的VIPP 4 ORL会进入`AW_MPI_VI_GetFrame`取得的预览帧，并随图像一起经过G2D旋转后送到VO。日志证据如下：

```text
[ORL] Detection overlay started: target=VIPP4:0, ..., handles=200..215
[ORL] Box map: target=VIPP4:0, sequence=41,
      model=(208,106)-(316,320), video=(1248,356)-(1896,1080), drawn=1
[ORL] Boxes cleared: target=VIPP4:0, sequence=43, detected=0
```

同一个检测快照也被VIPP 0通路消费，并映射为相同的1920x1080坐标。因此LCD、RTSP和MP4使用同一检测结果，不会出现三套业务坐标：

```text
VIPP 4：sequence=64, video=(384,340)-(1224,962), drawn=1
VIPP 0：sequence=64, video=(384,340)-(1224,962), drawn=1
```

退出时两个ORL线程都先于NPU、VENC和VIPP 4停止，最终程序返回0：

```text
[ORL] Detection overlay thread stopped: target=VIPP4:0, updates=169
[ORL] Detection overlay thread stopped: target=VIPP0:0, updates=169
[NPU] Realtime detection thread stopped: ..., failures=0
[Main] Application exited with code: 0
```

本次日志中出现过一次`video4 fifo overflow`，但预览最终统计为`submitted=367, released=367, dropped=0`，且程序正常退出，因此不影响本次LCD画框功能判定。如果后续长时间运行频繁出现该警告，再单独检查VIPP 4取帧速度、G2D耗时和缓存数量。
