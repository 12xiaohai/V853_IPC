# 阶段9.4：人形越线检测技术说明

## 1. 阶段目标

阶段9.4在现有YOLOv8实时人形检测结果上增加越线规则，不重新取摄像头帧，也不重复执行NPU推理。本阶段实现：

1. 从`NpuDetectionSnapshot`读取最新person框；
2. 使用人框底边中点近似人员落脚位置；
3. 通过最近距离关联前后帧中的同一人员；
4. 判断人员是否穿过有限警戒线段；
5. 使用滞回带、丢帧容忍和冷却时间抑制重复报警；
6. 生成带方向、轨迹ID、视频PTS和检测序号的越线事件；
7. 为后续音频报警模块预留事件回调。

本阶段首先用日志验证规则正确性，不播放报警音。报警播放将在后续阶段使用已预留的回调接入。

## 2. 文件结构

```text
sample/ipc_camera/include/line_crossing.h
sample/ipc_camera/app/line_crossing.c
sample/ipc_camera/app/main.c
```

`Makefile`会递归编译`sample`目录中的C文件，因此新增源文件不需要手工加入源文件列表。

## 3. 数据通路

```text
VIPP 8 -> YOLOv8 NPU线程
              |
              | 发布NpuDetectionSnapshot
              v
        line_crossing线程
              |
              | person框底边中点
              v
       最近距离轨迹关联
              |
              | 侧别 + 有限线段相交 + 防抖 + 冷却
              v
       LineCrossingEvent
              |-- 当前：输出[LINE]日志
              `-- 后续：触发音频报警
```

越线模块只复制检测快照，不持有NPU内部指针，也不访问VI图像缓冲。因此规则计算不会阻塞NPU、LCD、RTSP或录像线程。

## 4. 默认警戒线

警戒线使用`320x320`模型坐标。`main.c`中的默认配置为：

```text
A = (160, 0)
B = (160, 320)
```

它是一条贯穿画面中央的竖直线。由于有向线从上向下：

- 画面左边是正侧；
- 画面右边是负侧；
- `positive-to-negative`表示从左向右越线；
- `negative-to-positive`表示从右向左越线。

如果需要调整位置，修改`main.c`中的`line_ax/line_ay/line_bx/line_by`即可。坐标必须属于模型范围，不是1920x1080编码坐标，也不是480x800 LCD坐标。

## 5. 为什么使用底边中点

对检测框`(xmin,ymin)-(xmax,ymax)`，人员位置定义为：

```text
point_x = (xmin + xmax) / 2
point_y = ymax
```

框中心会随人的上半身姿态明显变化，而底边中点更接近脚底位置，更符合门口、走廊和警戒区域的监控语义。

当脚部超出画面时，YOLO框底边可能贴在图像边界。这仍可用于左右方向的中央竖线测试，但实际部署时应让警戒线位于人员脚部可见的区域。

## 6. 侧别判断

设警戒线端点为`A(x1,y1)`、`B(x2,y2)`，目标点为`P(x,y)`：

```text
side(P) = (x2-x1)*(y-y1) - (y2-y1)*(x-x1)
```

- `side > 0`：点在正侧；
- `side < 0`：点在负侧；
- `side = 0`：点在线上。

代码使用64位整数完成计算，避免浮点误差。

## 7. 滞回带防抖

如果人员在线附近轻微移动，叉积符号可能连续变化并产生多次事件。当前配置在线两侧各设置12像素滞回距离：

```c
line_crossing_config.hysteresis_pixels = 12U;
```

目标进入滞回带时返回中间状态0，不立即改变稳定侧别。只有目标离开防抖带并到达另一侧，才可能构成越线。

代码通过以下等价比较避免调用`sqrt()`：

```text
cross² <= line_length² * hysteresis²
```

因此不需要额外链接数学库。

## 8. 简单多目标关联

YOLOv8检测结果没有永久目标ID。当前使用轻量最近距离方法：

1. 计算每个person框的底边中点；
2. 在尚未匹配的旧轨迹中寻找最近点；
3. 距离不超过96模型像素则认为是同一人；
4. 找不到匹配轨迹时分配新ID；
5. 连续丢失超过5个检测快照后删除轨迹。

该方案不依赖OpenCV，计算量很小，适合V853。在多人严重遮挡或轨迹交叉时，最近距离可能交换ID；如果后续业务要求精确计数，可再升级为IoU、匈牙利匹配或ByteTrack。

## 9. 有限线段相交

仅仅发生侧别变化还不够。代码还会检查：

```text
上一稳定锚点 -> 当前落脚点
```

形成的运动线段是否与`A -> B`警戒线段真实相交。这样目标穿过警戒线的无限延长线、但没有经过实际警戒线范围时不会误报。

每次确认处于防抖带外的稳定侧后，程序都会更新锚点。即使目标在滞回带内停留多帧，最终到达另一侧时仍能用上一次稳定侧的锚点完成相交判断。

## 10. 冷却时间

同一轨迹触发后进入3秒冷却：

```c
line_crossing_config.cooldown_ms = 3000U;
```

冷却期间不会再次发布事件，但侧别仍会正常更新，避免冷却结束后补报已经发生的旧动作。

冷却是“每条轨迹独立”的，不会阻止另一个人触发越线。

## 11. 事件结构

```c
typedef struct LineCrossingEvent {
    unsigned int track_id;
    LineCrossingDirection direction;
    unsigned long long sequence;
    unsigned long long frame_pts_us;
    int point_x;
    int point_y;
} LineCrossingEvent;
```

字段含义：

- `track_id`：应用层临时轨迹ID；
- `direction`：正侧到负侧，或负侧到正侧；
- `sequence`：产生事件的NPU检测序号；
- `frame_pts_us`：对应摄像头帧PTS，可与录像时间对齐；
- `point_x/point_y`：触发时的模型坐标落脚点。

`event_callback`当前为空，因此事件只写日志。后续音频报警模块只需设置回调，不需要侵入越线算法。

## 12. 生命周期

启动顺序：

```text
NPU detector -> RTSP/MP4/LCD ORL -> line crossing
```

停止顺序：

```text
line crossing -> LCD ORL -> encoding ORL -> NPU detector
```

越线线程必须先于NPU停止，否则可能读取已经释放的检测器上下文。`main.c`已把正常退出和失败回滚统一放在`cleanup`中。

## 13. 当前配置

| 参数 | 当前值 | 作用 |
|---|---:|---|
| 警戒线 | `(160,0)-(160,320)` | 画面中央竖线 |
| 滞回距离 | 12 px | 抑制线附近抖动 |
| 最大匹配距离 | 96 px | 关联相邻快照人员 |
| 最大连续丢失 | 5帧 | 容忍短暂漏检 |
| 冷却时间 | 3000 ms | 防止同一轨迹重复触发 |
| 轮询周期 | 50 ms | 读取最新NPU快照 |
| 最大轨迹数 | 16 | 限制内存和计算量 |

### 14.2 左向右验证

1. 保证完整人体尽量进入画面；
2. 先站在画面左半边，等待检测框稳定；
3. 连续走到画面右半边；
4. 预期只出现一次：

```text

```

### 14.3 右向左验证

从画面右半边走到左半边，预期只出现一次：

```text

```

### 14.4 防抖与丢帧验证

- 在线附近小幅晃动，不应连续刷事件；
- 人短暂漏检后重新出现，轨迹在5帧范围内应继续；
- 两次真正往返越线间隔超过3秒后，应分别产生两个方向事件；
- RTSP、MP4和LCD继续正常显示检测框；
- 时间OSD和音视频录制不受影响。

## 15. 常见问题

### 15.1 人经过中央线但没有事件

先检查是否持续出现person检测。越线模块使用框底边中点，不是框中心；如果只有头部或上半身进入画面，落脚点可能不符合预期。还要确保人员先稳定出现在一侧防抖带外，再完整走到另一侧。

### 15.2 方向与理解相反

方向由`A -> B`决定。当前竖线从上向下，所以正到负是左向右。如果交换A、B，两个方向名称也会交换，但几何检测仍然正确。

### 15.3 同一次动作触发多次

检查日志中的`id`是否变化。如果ID不变，增大`hysteresis_pixels`或`cooldown_ms`；如果ID不断变化，说明检测漏帧时间超过限制，可增大`max_missing_snapshots`，或改善摄像头角度和光照。

### 15.4 多人交叉时ID交换

这是最近距离关联的已知边界，不影响单人和人员间距较大的监控场景。需要严格多目标身份时再引入更完整的跟踪器。
