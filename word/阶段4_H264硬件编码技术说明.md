# 阶段 4：H.264 硬件编码技术说明

## 1. 阶段目标

本阶段在实时预览正常工作的基础上增加 V853 硬件 H.264 编码，形成两条并行视频通路：

```text
                         ┌→ VIPP 4 / VI Chn 0
GC2053 → ISP 0 ──────────┤       → GetFrame → G2D → VO → LCD
                         │
                         └→ VIPP 0 / VI Chn 0
                                 → MPP Bind → VENC 0
                                 → GetStream → sample_demo.h264
```

实时显示继续使用阶段 3 的 VIPP 4；主码流编码沿用原项目的 VIPP 0、VI 虚拟通道 0 和 VENC 通道 0。

## 3. 编码参数

本阶段采用原项目主码流的核心参数：

| 参数 | 当前值 |
| --- | ---: |
| 编码格式 | H.264 |
| VENC 通道 | 0 |
| 编码 VIPP | 0 |
| 编码 VI 虚拟通道 | 0 |
| ISP | 0 |
| 输入格式 | NV21 |
| 分辨率 | 1920×1080 |
| 帧率 | 20 fps |
| 码率控制 | CBR |
| 目标码率 | 5,242,880 bit/s（约 5 Mbit/s） |
| H.264 Profile | Main Profile（值 1） |

码流 VBV 阈值和缓冲大小根据码率、帧率及原项目公式计算，避免编码器输出缓存过小造成阻塞。

## 4. 为什么使用独立的 VIPP 0

阶段 3 的 VIPP 4 用于应用态取帧、G2D 旋转和 LCD 显示。原项目为主码流编码另外创建 VIPP 0，并通过 MPP 绑定到 VENC。

这种设计有以下优势：

- 实时预览和视频编码互不阻塞；
- VENC 不需要等待应用调用 `GetFrame()`；
- 应用不需要对每帧调用 `AW_MPI_VENC_SendFrame()`；
- 原始图像不经过 CPU 内存复制；
- 后续 RTSP、录像和 OSD 可以直接围绕 VENC 通道扩展。

两个 VIPP 共享 ISP 0 和同一摄像头数据源，但各自拥有独立的视频通道配置和缓冲队列。

## 5. MPP Bind 内部传递方式

编码 VI 和 VENC 使用以下通道描述：

```c
MPP_CHN_S vi_channel   = { MOD_ID_VIU,  0, 0 };
MPP_CHN_S venc_channel = { MOD_ID_VENC, 0, 0 };
```

调用：

```c
AW_MPI_SYS_Bind(&vi_channel, &venc_channel);
```

绑定后，MPP 在内部连接 VI 输出端口与 VENC 输入端口。VI 产生一帧时，框架把包含物理地址、尺寸、格式和 PTS 的媒体缓冲描述传递给 VENC，并通过内部引用计数管理缓冲生命周期。

VENC 直接通过物理地址/DMA 读取该帧，不需要应用执行以下操作：

```text
AW_MPI_VI_GetFrame()
AW_MPI_VENC_SendFrame()
AW_MPI_VI_ReleaseFrame()
```

这就是 MPP 绑定方式相对于应用态手动搬运的核心区别。这里的“内部传递”主要是传递帧描述符和缓冲所有权，而不是让 CPU 再复制一份 1920×1080 的 NV21 数据。

## 6. VENC 初始化流程

编码模块按以下顺序启动：

1. 为 VIPP 0 填充 `VI_ATTR_S`。
2. 创建并配置 VIPP 0。
3. 启动共享的 ISP 0。
4. 使能 VIPP 0并创建 VI 虚拟通道 0。
5. 填充 `VENC_CHN_ATTR_S`，配置 H.264、分辨率、CBR、码率和 GOP。
6. 创建 VENC 通道 0。
7. 获取并设置 H.264 码率控制参数。
8. 打开 `/mnt/UDISK/sample_demo.h264`。
9. 获取 SPS/PPS 并写入 H.264 文件开头。
10. 将 VI 通道绑定到 VENC 通道。
11. 启动 VENC 接收图像。
12. 使能 VI 虚拟通道。
13. 创建码流提取线程。

任一步失败都会调用统一清理流程，只销毁此前已经成功创建的资源。

## 7. H.264 码流线程

码流线程不处理原始 YUV 图像，只处理硬件编码后的压缩数据：

```text
AW_MPI_VENC_GetStream(timeout=200 ms)
        ↓
读取 mLen0/mLen1/mLen2 和 PTS
        ↓
按顺序写入 sample_demo.h264
        ↓
AW_MPI_VENC_ReleaseStream()
```

一个 `VENC_PACK_S` 最多包含三段数据，因此保存时必须依次处理 `mpAddr0/1/2`，不能只写第一段。

每取得 100 个编码帧，程序打印一次帧序号、字节数、关键帧标志和 PTS，并刷新文件缓冲。退出前也会执行 `fflush()`，避免最后一段码流仍留在用户态缓冲中。

## 8. SPS、PPS 与关键帧

SPS 描述分辨率、Profile、Level 等序列参数，PPS 描述图像级编码参数。没有 SPS/PPS 的裸 H.264 文件通常无法被播放器正确解析。

本阶段在启动时调用 `AW_MPI_VENC_GetH264SpsPpsInfo()`，并将返回内容写到文件开头。随后写入 VENC 输出的 I/P 帧码流，形成可供 FFmpeg、ffplay 或 VLC 解析的 H.264 Annex-B 文件。

GOP 设置为 75，理论上每 75 帧产生一个关键帧。在 20 fps 下，关键帧间隔约为 3.75 秒。

## 9. 安全退出顺序

收到退出信号后，编码模块执行：

```text
禁用编码 VI 虚拟通道，停止新帧进入 VENC
  → 码流线程取完剩余输出并退出
  → AW_MPI_VENC_StopRecvPic
  → AW_MPI_SYS_UnBind
  → Reset/Destroy VENC
  → Destroy VI 虚拟通道
  → Disable VIPP 0
  → Stop ISP 0
  → Destroy VIPP 0
  → fflush/fclose H.264 文件
```

编码链路停止后，主程序再停止 VIPP 4 的实时预览链路，最后关闭 VO、G2D 和 MPP。

## 10. 编译与开发板验证

在 Linux 虚拟机中同步并编译：

```sh
cd ~/sample_demo
git pull origin main
./build.sh
```

在开发板运行：

```sh
cd /mnt/UDISK
rm -f sample_demo.h264
./sample_strip
```

运行 10～20 秒后按 `Ctrl+C`。预期日志包含：

```text
[VENC] H.264 encoder started: vipp=0, vi_chn=0, venc_chn=0,
       1920x1080@20fps, bitrate=5242880, gop=75,
       file=/mnt/UDISK/sample_demo.h264
[VENC] Stream thread started
[VENC] Encoded frame=1, seq=..., bytes=..., key=1, pts=... us
[VENC] Encoded frame=100, seq=..., bytes=..., key=..., pts=... us
```

退出时预期包含：

```text
[VENC] Stream thread stopped, frames=..., bytes=...
[VENC] Encoder stopped: encoded=..., key=..., bytes=...
[Main] Application exited with code: 0
```

在开发板上检查文件：

```sh
ls -lh /mnt/UDISK/sample_demo.h264
```

将文件复制到电脑后，可使用 FFmpeg 工具验证：

```sh
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,profile,width,height,r_frame_rate \
  -of default=noprint_wrappers=1 sample_demo.h264

ffplay -f h264 sample_demo.h264
```

预期识别为 H.264、1920×1080，播放速度约 20 fps。

### 12.2 日志告警说明

- `eRcMode is 0, suggested 1`：Cedarc 建议使用另一种码率控制模式；当前项目明确采用 CBR，该信息不影响编码成功。
- `no pGdcCxt, bGDC_en=0`：当前没有启用 GDC 几何校正，属于正常配置提示。
- `using frame not empty, remain 1`：停止 VI 时隧道中仍有一帧正在被 VENC 使用；随后日志显示 VENC 输入帧列表已清空，没有形成持续资源泄漏。
- `tunnel request may be some danger in StateExecuting`：本次测试版本在 `StartRecvPic` 后执行 Bind。代码现已调整为先 Bind、再 `StartRecvPic`，避免在执行态建立隧道；调整后已再次通过 ARM 目标严格语法检查。
