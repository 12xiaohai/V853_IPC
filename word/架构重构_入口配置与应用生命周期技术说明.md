# 架构重构：入口、配置与应用生命周期技术说明

记录日期：2026-10-03。开发分支：`main`。

## 1. 为什么整理架构

阶段1～9逐步增加LCD、编码、推流、录像、检测、画框和报警后，原来的
`main.c`累计约901行，`main()`约680行。参数赋值、服务创建、回调接线、
主循环和失败清理都挤在入口中，读者不容易看清“程序究竟怎样运行”。

本次按职责拆分，不重写已经验证的媒体模块，不引入通用服务框架或新的
线程管理器。整理后的`main.c`约132行，`main()`约69行（含注释和空行）。

| 层次 | 文件 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| 程序入口 | `app/main.c` | 信号、日志、运行模式、等待退出、统一清理入口 | 不展开各模块默认参数和资源状态 |
| 纯配置 | `app/config.c`、`include/config.h` | 默认参数、命令行校验 | 不分配服务、不初始化MPP、不创建工作线程 |
| 应用编排 | `app/application.c`、`include/application.h` | 持有模块、按依赖启动/停止、连接回调 | 不重复实现编码、推理、文件队列和几何规则 |
| 功能实现 | 原有VI/VO/VENC/RTSP/MP4/NPU/报警模块 | 各自硬件资源、缓冲区及工作线程 | 不决定整个应用的启动顺序 |

表中的路径相对`sample/ipc_camera/`。原项目入口清晰的思路得到保留，但
没有照搬原项目实现：当前各模块已经管理自己的工作线程，无需再增加一套
集中式`create_threads()`来重复管理。

## 2. 从main读懂整个流程

建议阅读顺序：`main.c` → `config.c` → `application.c` → 需要学习的功能模块。

正常监控流程：

1. 安装SIGINT/SIGTERM处理器，初始化日志，校验命令行。
2. 生成默认配置，按参数覆盖模型或报警文件路径。
3. `ip_camera_application_create()`创建应用上下文。
4. `ip_camera_application_start()`启动服务。
5. 主线程等待退出，工作由原有模块线程完成。
6. `ip_camera_application_stop()`停止服务，再`destroy()`释放上下文。
7. 打印退出结果，关闭日志。

任意初始化失败都跳到同一个`cleanup`标签。信号处理函数仍然只写
`volatile sig_atomic_t`标志，不在信号处理器中调用日志、释放内存或MPP。

独立NPU单帧自检直接调用`npu_self_test_run()`，不创建应用上下文或MPP；
声音自检只启动MPP和本地音频报警，然后等待Ctrl+C。

## 3. 配置与状态分开保存

`IpCameraConfig`是各模块配置的集合；`VideoCaptureConfig`只保存采集参数。
原有`VideoCaptureContext`继续保存VI线程、计数和硬件资源状态，二者不混用。

`IpCameraContext`改为不透明类型：头文件只声明类型，实际字段放在
`application.c`。入口不再依赖内部模块指针和十几个`started`标志。
原来的全局`g_pContext`和`g_mutex_mpp`被应用实例及其消费者锁替代。

重要约定：

- 配置结构在create时复制；路径字符串仍是借用引用，必须存活到destroy。
  默认静态字符串和main的argv满足这个条件。
- 配置默认值中的detector、事件回调、码流回调和SPS/PPS指针为空。
  应用层创建真实对象后才连接这些运行时依赖。
- 同一应用上下文只允许一次启动尝试；停止后不能重启。需要再次运行时，
  创建新上下文，避免复用部分失败的硬件状态。
- start返回失败后，调用者仍应stop/destroy。main统一执行，destroy也会兜底stop。
- stop可重复调用，不再次操作已清理资源，并保留首次停止的返回结果。
  某个stop报错时继续尝试其他清理；这不等于保证驱动异常时所有资源都能成功释放。

旧接口`constructIpCameraContext/destructIpCameraContext`以及入口中的
`initialize_context`不再使用，分别由默认配置和应用生命周期接口取代。
早期阶段文档保留历史实现记录，阅读当前代码时以本说明为准。

## 4. 启停依赖没有改变

正常启动顺序：

```text
MPP → VO/G2D → VIPP4采集 → RTSP → VENC → 时间OSD → MP4
    → AAC → NPU → 编码ORL → LCD ORL → 音频报警 → 越线 → 区域入侵
```

应用层用小型`start_xxx()`辅助函数表达这些依赖。失败后不启动后续服务。
报警服务仍是可选项：普通监控模式下WAV/AO初始化失败只降级声音，不阻断
检测和录像；声音自检模式下则返回失败。

停止顺序不是简单反转启动表：

```text
区域 → 越线 → 音频报警 → LCD ORL → 编码ORL → NPU
    → 关闭MP4输入 → AAC → 时间OSD → VENC
    → MP4收尾/销毁 → RTSP → VIPP4采集 → VO/G2D → MPP
```

规则线程先退出，才释放报警队列；ORL消费者先退出，才释放NPU；
采集先退出，才销毁显示对象。

此前退出阻塞问题的关键顺序保留：先关闭MP4输入，编码线程退出后才让MUX
收尾并释放消费者。测试模拟编码停止前的最后一次回调，验证其仍能访问
RTSP/MP4对象，不会因为入口变短而提前销毁消费者。

## 5. 数据分发与默认行为

`MediaConsumers`及H.264/AAC分发回调移入应用层。每个应用实例持有自己的锁：
在锁内读取消费者指针快照，在锁外调用RTSP/MUX。不能持锁进行网络发送
或录像提交，也不能在生产线程尚未退出时销毁消费者。

RTSP/MP4继续使用原有深拷贝策略，编码缓冲在回调返回后仍归还MPP。
规则事件继续复制入报警队列；区域LEAVE不触发声音，ENTER才触发。

主要默认值保持原样：

| 通路/功能 | 保留参数 |
| --- | --- |
| LCD预览 | VIPP4、1920×1080 NV21、20 FPS、G2D 270°、480×800 |
| H.264 | VIPP0/VENC0、5242880 bit/s、GOP 75 |
| NPU | VIPP8、320×320 NV12、10 FPS、mirror/flip各1 |
| ORL | 编码/LCD独立句柄100/200、映射mirror/flip各0 |
| 音频 | 16000 Hz、PCM16、单声道、每帧1024采样 |
| MP4 | 60秒分段、最多10段、预留512 MiB、UDISK路径 |
| 报警 | `/lib/alarm.wav`、音量35、15秒冷却 |
| 规则 | 模型中央竖线、右半多边形、原确认/匹配/冷却参数 |

原有命令保持：

```sh
./sample_strip
./sample_strip --npu-model /mnt/UDISK/yolov8n_hybrid_i16.nb
./sample_strip --npu-self-test /mnt/UDISK/yolov8n.nb /mnt/UDISK/npu_realtime_320x320.nv12
./sample_strip --audio-alarm-test /mnt/UDISK/alarm_pcm16.wav
```

参数校验更严格：NPU自检不再悄悄忽略多余参数，所有模式拒绝空路径。
不新增INI/JSON配置文件、动态开关或自动重启；这些属于后续功能，不混入本次整理。


会包含新增`application.c`，不会编译`tests/`。
