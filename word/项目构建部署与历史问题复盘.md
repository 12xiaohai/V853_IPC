# 项目构建、部署与历史问题复盘

## 1. 文档目的

本文件记录不只属于某一个媒体功能阶段、但实际影响项目复刻的构建环境、
运行库、版本管理和硬件环境问题。各媒体阶段自身的问题仍记录在对应的阶段
技术说明中。

问题记录统一包含：现象、定位依据、根因、解决方法和验证结果。尚未复测的
项目必须明确标记，不把“代码已修改”等同于“问题已解决”。

## 2. 项目头文件 `context.h` 找不到

现象：

```text
fatal error: context.h: No such file or directory
```

根因：源码使用 `#include <context.h>`，但Makefile没有把复刻工程自己的
`sample/ipc_camera/include` 放入编译器搜索路径，或者该路径排在大量SDK目录
之后。

解决方法：

```make
USER_INCS  = -I$(ROOT_DIR)/sample/ipc_camera/include/
USER_INCS += -I$(ROOT_DIR)/sample/common/
```

项目目录需要排在SDK通用头文件之前，避免 `config.h`、`log.h` 等同名文件
错误匹配到SDK内部版本。

验证结果：项目自己的 `context.h`、`config.h` 和 `log.h` 可以稳定解析，后续
阶段均使用同一组包含路径。

## 3. 标准头文件 `signal.h` 找不到

现象：

```text
fatal error: signal.h: No such file or directory
```

根因：最初只复制了交叉编译器可执行文件或部分目录，没有同时提供重定位后
工具链需要的完整C运行库头文件/sysroot。标准头文件不是项目源码的一部分，
不能通过复制一个 `signal.h` 到项目include目录来正确解决。

解决方法：把工具链的 `bin`、目标头文件、GCC内部目录和目标库作为完整结构
保存在 `sdk/toolchain/toolchain-sunxi-musl/toolchain` 下，并在Makefile中加入：

```make
TOOLCHAIN_ROOT := $(abspath $(dir $(COMPILE_PREX))/..)
TOOLCHAIN_SYS_INCS := -idirafter $(TOOLCHAIN_ROOT)/include
```

验证结果：`signal.h`、`pthread.h`、`unistd.h` 等Linux标准头文件均可解析，
信号处理和主循环能够在ARM目标上编译运行。

## 4. 链接阶段找不到 `crt1.o` 和 `crti.o`

现象：

```text
ld: cannot find crt1.o
ld: cannot find crti.o
```

根因：C启动文件属于目标运行库和sysroot，不在普通MPP库目录中。工具链复制
不完整或重定位后没有为GCC/ld提供目标库搜索根目录，就会在最终链接阶段失败。

解决方法：保留工具链完整目录，并显式加入启动文件和目标库搜索路径：

```make
TOOLCHAIN_SYS_LIBS := -B$(TOOLCHAIN_ROOT)/lib/ -L$(TOOLCHAIN_ROOT)/lib
```

验证结果：链接器能够找到启动文件并生成ARM可执行程序。

## 5. C源码收到C++选项警告

现象：

```text
warning: '-std=c++11' is valid for C++ but not for C
warning: '-fpermissive' is valid for C++ but not for C
```

根因：早期Makefile把C++专用选项同时传给了 `.c` 和 `.cpp`。

解决方法：拆分公共选项和C++专用选项：

```make
COMMON_FLAGS = -g
CXX_ONLY_FLAGS = -std=c++11 -fpermissive
CFLAGS = $(COMMON_FLAGS) ...
CXXFLAGS = $(COMMON_FLAGS) $(CXX_ONLY_FLAGS) ...
```

验证结果：C文件使用交叉GCC编译，RTSP C++文件使用交叉G++编译，不再混用
语言专用参数。

## 6. C++编译时 `<cstdlib>` 找不到下一层 `stdlib.h`

现象：

```text
cstdlib: fatal error: stdlib.h: No such file or directory
#include_next <stdlib.h>
```

根因：libstdc++的 `<cstdlib>` 使用 `#include_next` 查找目标C库头文件。重定位
工具链的系统头文件顺序不正确时，下一层 `stdlib.h` 无法找到。

解决方法：把目标C库目录作为 `-idirafter` 系统后置目录，而不是简单地用一个
普通 `-I` 打乱GCC/libstdc++原有搜索顺序：

```make
TOOLCHAIN_SYS_INCS := -idirafter $(TOOLCHAIN_ROOT)/include
```

验证结果：`sample/common/rtsp_server.cpp` 能够通过交叉G++编译。

## 7. 开发板缺少OpenCV动态库

现象：程序在开发板启动前由动态加载器报错：

```text
Error loading shared library libopencv_core.so.4.1
Error loading shared library libopencv_imgproc.so.4.1
...
```

根因：链接阶段在工程SDK中找到了OpenCV `.so`，但目标根文件系统的动态库
搜索目录没有对应文件。能成功交叉编译不代表目标机运行依赖已经满足。

解决方法：沿用原项目部署模型，把匹配版本的OpenCV和其他共享库放入固件
rootfs的 `/usr/lib`，通过 `./build.sh firmware` 生成包含运行库的新固件，而
不是只复制单个可执行文件并假设它完全静态链接。

验证方法：

```sh
ldd /usr/bin/sample
ls -l /usr/lib/libopencv_core.so*
```

验证结果：安装匹配共享库后程序能够进入MPP初始化并运行。

## 8. Git推送出现 non-fast-forward

现象：

```text
rejected: main -> main (non-fast-forward)
```

根因：远端 `main` 含有本地没有的提交，Git为避免覆盖远端历史而拒绝普通
push。网络超时与non-fast-forward是两个不同问题，不能通过反复重试网络来
解决分支历史冲突。

处理原则：先检查远端历史，再选择合并/rebase；只有明确要用本地历史替换
远端时才使用 `--force-with-lease`，不能随意使用裸 `--force`。

## 9. Git传输大仓库时出现TLS/RPC超时

现象包括：

```text
Failed to connect to github.com port 443
OpenSSL SSL_read: Connection was reset
RPC failed; HTTP 408
GnuTLS recv error; early EOF
```

根因：仓库包含工具链、SDK和固件资源，首次传输对象接近数百MiB，再叠加
不稳定网络会导致HTTPS连接中断。该问题不同于代码编译错误。

处理原则：先确认代理/网络和远端状态；避免重复重新初始化仓库制造多套历史；
大二进制依赖后续可考虑Git LFS、Release附件或可校验的独立依赖包。当前项目
选择把完整SDK保存在仓库中，是“开箱可编译”和“仓库体积较大”之间的明确
权衡。

## 10. RTSP启动时开发板未联网

现象：RTSP服务无法得到可用的WLAN地址或客户端无法连接，但本地编码仍可
工作。

根因：TinyServer依赖 `wlan0`，开发板获得IP、电脑与开发板处于同一网络，
是RTSP验证的前置条件。启动应用不会自动保证Wi-Fi已经联网。

验证步骤：

```sh
ifconfig wlan0
ping -c 3 <PC-IP>
```

网络恢复后，日志输出实际RTSP URL，VLC成功连接并连续播放；该问题不是VENC
或RTSP帧队列代码故障。

## 11. LCD黑屏但编码文件正常

现象：H.264文件可正常播放，导出的VI原始帧和G2D旋转帧也正确，但LCD持续
黑屏；独立LVGL示例同样无法显示。

定位结论：当摄像头数据、G2D结果和编码输出都正常，而完全独立的显示示例也
失败时，故障范围已经离开视频编码通路。重新连接LCD硬件排线后显示恢复，
确认是硬件接触不良，而不是VI、G2D、VO或VENC逻辑错误。

详细日志与验证过程见阶段3、阶段4技术说明。

## 12. OSD显示1970年

现象：时间水印正常刷新，但日期为 `1970-01-01`。

根因：OSD正确读取了Linux系统时间，但开发板启动后系统时钟尚未通过RTC或
NTP校准。联网只表示接口可用，不等于已经自动校时。

解决方法：

```sh
busybox ntpd -n -q -p ntp.aliyun.com
date
hwclock -w
```

验证结果：系统和RTC显示2026年正确时间，重新运行应用后OSD日期和秒数正常。
详细过程见阶段7技术说明。

## 13. RTSP UDP发送缓存短时写满

现象：TinyServer反复输出：

```text
sendTo() error: Resource temporarily unavailable
```

阶段9.2联调日志中出现107次，但应用RTSP队列退出统计为视频`451/451`、音频
`346/346`且`dropped=0`。这表明数据已经离开应用队列，失败位置是TinyServer向
客户端发送UDP/RTP数据的套接字层，不是NPU或编码器丢帧。

处理顺序：先改用RTSP over TCP复测；再检查Wi-Fi信号和客户端读取状态；只有必须
使用UDP时，才进一步降低视频码率或调整套接字发送缓冲。该问题是否影响观看体验
仍需通过客户端画面验证，不能只凭应用队列`dropped=0`认定网络发送完全正常。

## 14. YOLOv8人形分数固定为1.642且帧间闪烁

现象：VIPP 8方向校正后已能够检出person，但所有检测分数均为
`1.642`，相邻帧经常在`persons=1`和`persons=0`之间切换。

根因：模型的`[1,84,2100]`输出张量同时容纳数百大小的框坐标和
`0~1`的类别概率，却统一使用了`scale=1.6422815`的UINT8非对称量化。
实时日志的`1.642`正好等于一个量化步长，说明类别概率精度在模型
转换阶段已经大量丢失。

处理原则：不通过截断分数或额外sigmoid掩盖问题。查阅配套课件后确认，
应在`yolov8n-sim.quantize`中把最终
`Concat_/model.22/Concat_5_1`设为`dynamic_fixed_point-i16`，并使用
`pegasus quantize --hybrid`重新生成NBG；不能通过把
`add_postproc_node`改成true来代替混合量化。新模型需通过`nbg_meta.json`
和实时置信度分布双重验证。详细证据见阶段9.2技术说明。

## 15. 后续维护要求

1. 新问题首先记录原始日志，不先凭现象修改代码；
2. 区分致命错误、可恢复超时、驱动提示和环境问题；
3. 修复后必须保留复测证据；
4. 问题属于具体功能阶段时，详细记录写入该阶段文档；
5. 跨阶段的构建、部署、Git、硬件和系统环境问题记录在本文件；
6. 尚未完成实测的修复标记为“等待验证”。
