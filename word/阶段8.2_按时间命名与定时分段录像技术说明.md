# 阶段8.2：按时间命名与定时分段录像技术说明

## 1. 阶段目标

阶段8.1已经能够把H.264和AAC正确封装成单个MP4文件。阶段8.2在不停止采集、
编码、显示和RTSP服务的前提下，实现：

1. 根据开发板本地时间自动生成录像文件名；
2. 每段录像达到配置时长后自动切换到新MP4文件；
3. 每个新文件从H.264关键帧开始，能够单独解码和拖动播放；
4. 文件切换期间继续使用原来的VENC/AENC码流，不创建第二套编码器；
5. 应用退出时正常封口当前录像文件。

本阶段先验证“持续分段生成正确文件”。自动删除旧文件和磁盘空间管理放在
阶段8.3实现，避免在分段链路尚未验证时引入删除操作。

## 2. 当前配置

`main.c`中的录像配置为：

```c
mp4_config.output_path = NULL;
mp4_config.output_directory = "/mnt/UDISK";
mp4_config.file_prefix = "record";
mp4_config.segment_duration_seconds = 60;
```

生成的文件名示例：

```text
/mnt/UDISK/record_20261001_153012_0000.mp4
/mnt/UDISK/record_20261001_153113_0001.mp4
/mnt/UDISK/record_20261001_153214_0002.mp4
```

时间精确到秒，末尾四位序号用于避免同一秒内重复命名。创建文件时使用
`O_EXCL`，如果同名文件已经存在就递增序号重新尝试，不覆盖已有录像。

## 3. MUX原生分段机制

MUX配置项：

```c
attributes->mMaxFileDuration =
    (int64_t)segment_duration_seconds * 1000;
```

单位是毫秒。达到目标时长时，MPP不会要求应用停止并重新创建MUX，而是通过
回调发送：

```text
MPP_EVENT_NEED_NEXT_FD
```

应用准备新文件描述符并调用：

```c
AW_MPI_MUX_SwitchFd(mux_channel, next_fd, 0);
```

MUX完成旧文件的索引和文件尾后发送：

```text
MPP_EVENT_RECORD_DONE
```

这样视频和音频编码器能够连续运行，RTSP也不会因本地录像切片而重启。

## 4. 为什么回调中不直接切换文件

MPP回调运行在SDK内部线程。如果在回调中执行`open()`、文件系统操作以及
`AW_MPI_MUX_SwitchFd()`，可能长时间阻塞MPP线程，某些SDK版本还可能因为
回调重入MUX而死锁。

本阶段采用“回调通知 + 专用工作线程”结构：

```text
MPP内部回调
    |
    | 设置next_fd_requested并唤醒条件变量
    v
segment_rotation_thread
    |
    | 生成文件名 -> O_EXCL创建文件 -> SwitchFd
    v
MUX开始写入下一段MP4
```

回调只修改少量状态，真正的文件操作全部由`segment_rotation_thread`完成。

## 5. 文件切换与送帧互斥

视频编码线程和音频编码线程都会调用同步MUX送流接口，切片线程则调用
`AW_MPI_MUX_SwitchFd()`。三条路径共享`send_lock`：

```text
视频SendVideoStreamSync ----+
                            +---- send_lock ---- MUX
音频SendAudioStreamSync ----+
文件AW_MPI_MUX_SwitchFd ----+
```

因此文件描述符切换不会与某一帧提交进行到一半时交叉发生。切换操作很短，
不会复制编码帧，也不会长期阻塞编码线程。

## 6. 关键帧边界策略

本阶段显式设置：

```c
RecordFileDurationPolicy_MinDuration
```

含义是：文件时长至少达到配置值，然后等待下一个I帧再切换。这样每个新MP4
都从关键帧开始，能够独立播放。

当前编码参数为20 fps、GOP为75帧，一个GOP约3.75秒。因此配置60秒后，实际
文件时长可能在60秒基础上增加不到一个GOP，这是正常现象，不是定时器失效。

## 7. AAC兼容性处理保持不变

AENC仍以`attachAACHeader=1`输出ADTS帧：

- 独立`sample_demo.aac`继续保存完整ADTS帧；
- RTSP继续使用原来的AAC数据；
- 只有送进MP4 MUX前剥离7/9字节ADTS头。

文件切换不会改变该逻辑，因此每个分段MP4中的AAC sample都应保持Windows
播放器可兼容的裸AAC格式。

## 8. 启动与退出顺序

启动：

1. 生成第一个时间文件名并以`O_EXCL`创建；
2. 创建MUX并设置60秒时长；
3. 设置关键帧切换策略；
4. 注册MUX回调；
5. 设置VENC流映射和SPS/PPS；
6. 启动切片工作线程；
7. 启动MUX并等待首个关键帧。

退出：

1. 禁止录像器接收新音视频帧；
2. 唤醒并退出切片线程，禁止新的`SwitchFd`；
3. 使用非强制方式停止MUX，让当前MP4写完索引；
4. 销毁MUX并关闭初始文件描述符；
5. 销毁条件变量和互斥量。

## 9. 预期日志

首次启动：

```text
[MP4] Segment rotation thread started
[MP4] Recorder started: ..., segment=60s, file=/mnt/UDISK/record_....mp4
```

达到分段时间：

```text
[MP4] MUX requested the next segment
[MP4] Switched to next segment: /mnt/UDISK/record_....mp4
[MP4] MUX reported record done: muxer_id=0
```

安全退出：

```text
[MP4] Segment rotation thread stopped
[MP4] Recorder stopped: ..., completed_files=..., file=...
```

不应出现：

```text
Switch to next segment failed
Invalid ADTS frame
audio streamId wrong
User should RegisterCallback
```

### 12.2 下一个FD预申请和实际切换

```text
13:51:36 [MP4] MUX requested the next segment
13:51:36 [MP4] Switched to next segment:
         /mnt/UDISK/record_20261001_135136_0001.mp4
```

这里的`SwitchFd`表示把备用FD交给MUX，不代表此刻立即结束旧文件。达到60秒并
等到可用关键帧后，MUX在约13:51:46完成真正的文件边界切换：

```text

[MP4] MUX reported record done: muxer_id=0
```

```text

音频有效时长约59.904秒
文件大小约39,821,555字节
```

这证明`MinDuration`策略按设计工作：文件至少达到60秒，并在关键帧边界切换。

需要注意，第二个文件名记录的是MUX预申请FD的时间13:51:36，而实际内容起点
约为13:51:46，两者相差约10秒。这是当前SDK提前请求下一个FD造成的命名语义
差异，不影响文件内容和播放；后续若要求文件名严格代表首帧时间，可单独优化
为“计划边界时间”命名。
