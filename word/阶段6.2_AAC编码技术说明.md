# 阶段 6.2：AAC 编码技术说明

> 架构同步（2026-10-03）：当前main.c负责信号、运行模式与主循环，
> 默认参数集中在config.c，服务启动/回调/清理由application.c负责。
> 默认参数在config->audio_encoder；application启动AENC并连接RTSP/MP4消费者。
> 早期阶段范围、旧代码示例及实测日志属于当时快照，不表示重构后已完成板端复测。
> 详见[架构重构说明](架构重构_入口配置与应用生命周期技术说明.md)。

## 1. 本阶段目标

阶段 6.1 已经证明麦克风、AudioCodec、AI 通道和 PCM 参数正常。本阶段在此基础上创建 MPP AENC 通道，将 AI 采集的 16 kHz 单声道 PCM 编码为带 ADTS 帧头的 AAC 文件：

```text
/mnt/UDISK/sample_demo.aac
```

本阶段先独立验证 AAC 编码结果，不把音频送入 RTSP。这样如果播放异常，问题范围只涉及 AI、AENC 和文件写入，不会与网络传输、客户端兼容性或音视频同步问题混在一起。

## 2. 数据通路

```text
板载麦克风
    ↓
AudioCodec / ALSA
    ↓
AI Device 0 / Channel 0
    ↓  AW_MPI_SYS_Bind（MPP 内部传递 PCM）
AENC Channel 0（AAC）
    ↓  AW_MPI_AENC_GetStream
应用取流线程
    ↓
/mnt/UDISK/sample_demo.aac
```

AI 和 AENC 绑定后，应用不再反复调用 `AW_MPI_AI_GetFrame()` 和 `AW_MPI_AENC_SendFrame()` 搬运 PCM。MPP 将 AI 输出缓冲直接交给 AENC，应用只获取体积更小的编码结果。这种方式减少了用户态线程的参与和一次 PCM 数据传递，也是原项目采用的通路。

## 3. 新增文件

```text
sample/ipc_camera/include/audio_encoder.h
sample/ipc_camera/app/audio_encoder.c
```

`audio_encoder.h` 定义音频编码配置和以下生命周期接口：

```text
audio_encoder_create()
        ↓
audio_encoder_start()
        ↓
audio_encoder_stop()
        ↓
audio_encoder_destroy()
```

阶段 6.1 的 `audio_capture.c/.h` 被保留下来，便于以后单独抓取 PCM 排查麦克风问题；但主程序已经切换到 `audio_encoder`，不会同时从同一个 AI 通道取 PCM，以免和 MPP 绑定通路竞争音频帧。

## 4. 编码参数

| 参数 | 配置值 | 说明 |
| --- | ---: | --- |
| AI 设备/通道 | 0 / 0 | 板载音频输入 |
| AENC 通道 | 0 | 第一个音频编码通道 |
| 编码格式 | `PT_AAC` | AAC 编码 |
| 采样率 | 16000 Hz | 与 AI 输入一致 |
| 位宽 | 16 bit | 与 AI 输入一致 |
| 声道数 | 1 | 单声道 |
| 每帧采样点 | 1024 | 每帧覆盖约 64 ms |
| `attachAACHeader` | 1 | 每帧附带 ADTS 头 |
| `bitRate` | 0 | 沿用原项目，由 SDK 采用默认值 |

AI 与 AENC 的采样率、位宽和声道数必须一致。参数不一致可能导致创建通道失败，或者产生速度、音调异常的编码结果。

## 5. ADTS 帧头的作用

AAC 编码数据本身可以有不同的封装方式。本阶段将 `attachAACHeader` 设置为 1，使每个 AAC 帧前都带 ADTS 头。ADTS 中记录了采样率索引、声道数和帧长度，因此连续写入各帧后得到的 `.aac` 文件可以被 FFmpeg、ffplay 或 VLC 直接识别。

如果不附加 ADTS，只把裸 AAC payload 拼接到文件，普通播放器通常无法判断每一帧的边界和音频参数。

## 6. 初始化顺序

`audio_encoder_start()` 按以下顺序执行：

1. 设置并启用 AI 设备；
2. 设置麦克风采集音量；
3. 创建 AI 通道；
4. 创建 AENC AAC 通道；
5. 使用 `AW_MPI_SYS_Bind()` 绑定 AI 与 AENC；
6. 创建 AAC 输出文件；
7. 启用 AI 通道；
8. 调用 `AW_MPI_AENC_StartRecvPcm()`；
9. 创建 AENC 码流读取线程。

每一步均记录资源状态。如果后续步骤失败，统一调用停止函数，仅回收已经成功创建的部分，避免残留通道影响下一次运行。

## 7. 码流线程与缓冲区所有权

线程通过以下接口获取编码帧：

```text
AW_MPI_AENC_GetStream()
        ↓
将 stream.pStream 的 stream.mLen 字节写入 AAC 文件
        ↓
AW_MPI_AENC_ReleaseStream()
```

`pStream` 指向 AENC 内部缓冲区，只能在当前帧被持有时访问。每次 `GetStream` 成功后都必须调用 `ReleaseStream`，否则输出缓冲会被耗尽，编码最终停止。

线程记录 AAC 帧数、总字节数、首帧 PTS 和末帧 PTS。这些 PTS 将在阶段 6.3 中用于 RTSP 音视频同步。

## 8. 安全退出顺序

退出时依次执行：

1. 设置线程退出标志并等待取流线程结束；
2. 禁用 AI 通道；
3. 停止 AENC 接收 PCM；
4. 解除 AI 与 AENC 的绑定；
5. 重置并销毁 AI 通道，禁用 AI 设备；
6. 重置并销毁 AENC 通道；
7. 刷新并关闭 AAC 文件。

先等待取流线程退出，可以避免线程仍访问 AENC 缓冲时通道已经被销毁。

## 10. 电脑端验证

AAC 带有 ADTS 帧头，可以直接检查和播放：

```sh
ffprobe -hide_banner sample_demo.aac
ffplay sample_demo.aac
```

也可以直接使用 VLC 打开 `sample_demo.aac`。需要确认：

1. FFmpeg 能识别为 AAC、16000 Hz、单声道；
2. 时长与实际运行时间大致一致；
3. 能听见录音，且速度和音调正常；
4. 程序按 `Ctrl+C` 后退出码为 0；
5. LCD、H.264 文件和 RTSP 视频仍正常。

## 11. 开发板初步实测结果

2026-09-30 在 V853 开发板上完成第一次 AENC 运行测试：

```text
AAC 帧数：175
AAC 总字节数：43406
首帧 PTS：31682253975 us
末帧 PTS：31693389976 us
RTSP 视频：发送 229 帧，丢帧 0
LCD 预览：提交/释放 237/237 帧，丢帧 0
程序退出码：0
```

首末 PTS 相差 11.136001 秒。175 帧之间有 174 个时间间隔，而每个 AAC
帧包含 1024 个采样点：

```text
174 × 1024 ÷ 16000 = 11.136 秒
```

两者完全吻合，说明 AI → AENC 的数据速率和时间戳连续、正确。日志还显示
MPP 成功解除 AI/AENC tunnel，AI 和 AENC 组件均正常销毁，程序退出码为
0。随后使用 VLC 直接打开 `sample_demo.aac`，能够正常听到录音声音，
证明 ADTS 封装、AAC 编码结果和客户端解码均正常。至此，AI 采集、MPP
内部绑定、AENC 编码、AAC 文件写入和安全退出已全部验证，阶段 6.2 正式
完成。
