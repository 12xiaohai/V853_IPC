## 1 阶段目标

本阶段的学习目标是理解当前完整程序的“外壳”：配置从哪里来，资源在哪里创建，主线程如何等待退出，初始化失败后如何清理。媒体、检测和报警模块已经实现，但本篇只展开入口、日志、上下文、MPP和信号处理。

本阶段完成以下功能：

1. 初始化 Allwinner glog 日志系统。
2. 创建和释放应用级上下文 `IpCameraContext`。
3. 配置并初始化 MPP；区分MPP内部ISP基础初始化与VI模块调用`AW_MPI_ISP_Run()`。
4. 获取系统当前 PTS，并建立媒体时间戳基准。
5. 注册 `SIGINT` 和 `SIGTERM` 信号处理函数。
6. 实现持续运行的主循环。
7. 收到退出信号后，按资源依赖尝试清理已创建的模块，并记录失败。

推荐阅读顺序：

1. [main.c](../sample/ipc_camera/app/main.c)：看`main()`、`main_loop()`和`cleanup`。
2. [config.h](../sample/ipc_camera/include/config.h)和[config.c](../sample/ipc_camera/app/config.c)：看运行模式、参数校验、默认配置。
3. [application.h](../sample/ipc_camera/include/application.h)和[application.c](../sample/ipc_camera/app/application.c)：看create/start/stop/destroy。
4. [log.c](../sample/ipc_camera/app/log.c)和[platform.c](../sample/ipc_camera/app/platform.c)：看基础资源的创建和退出。

## 2 当前代码结构

```text
sample/ipc_camera/
├── app/
│   ├── main.c          程序入口、信号、模式选择和主循环
│   ├── application.c   应用上下文、模块接线、启动和安全清理
│   ├── config.c        默认配置与命令行校验，不创建硬件资源
│   ├── platform.c      MPP 初始化、PTS 初始化和 MPP 退出
│   └── log.c           日志目录创建和 glog 配置
└── include/
    ├── application.h   应用生命周期接口
    ├── config.h        IpCameraConfig、运行模式和参数接口
    ├── context.h       VI运行状态、IpCameraContext不透明声明
    ├── platform.h      平台接口声明
    └── log.h           日志接口声明
```

项目头文件路径在 Makefile 中排在 SDK 头文件路径之前，避免 `config.h`、`log.h` 等通用文件名错误匹配到 SDK 内部的同名文件。

`main.c`不是线程调度器，也不逐一管理摄像头、编码器等对象。它调用应用生命周期接口；`application.c`接线并管理对象，各功能模块自己管理工作线程。

## 3 程序执行流程

```text
main
  -> 注册 SIGINT 和 SIGTERM，初始化 glog
  -> ip_camera_options_parse：选择监控/声音自检/NPU单帧自检
  -> 按模式分支
       NPU单帧自检：直接执行自检，不初始化MPP，不进入主循环
       其他模式：
         -> ip_camera_config_defaults生成参数，再覆盖命令行指定路径
         -> ip_camera_application_create创建上下文及消费者锁
         -> ip_camera_application_start初始化MPP/PTS并按模式启动服务
         -> 主循环等待退出信号
         -> ip_camera_application_stop按依赖停止服务，最后退出MPP
         -> ip_camera_application_destroy释放上下文及消费者锁
  -> 关闭 glog，返回退出码
```

`main()`的`cleanup`是统一入口，但模块资源清理已经移入`application.c`的
`ip_camera_application_stop()`。main只记录日志是否初始化；应用上下文记录
MPP和各模块启动状态，只清理实际创建的资源。完整服务顺序见架构重构说明。

模式之间的区别如下：

| 调用方式 | 实际范围 |
| --- | --- |
| `./sample_strip` | 完整监控：预览、编码、音频、RTSP、录像、NPU及规则等 |
| `./sample_strip --npu-model MODEL.nb` | 仍是完整监控，只替换本次运行的模型路径 |
| `./sample_strip --npu-self-test [MODEL.nb] [INPUT.nv12]` | 单帧NPU自检，main直接执行，不初始化MPP |
| `./sample_strip --audio-alarm-test [ALARM.wav]` | MPP和声音自检，播放一次后等待退出，不启动完整监控 |

当前没有`--stage1`、`--capture-only`或`--preview-only`选项。诊断分支曾出现的选项不能当作main分支现有接口。

这种结构可以覆盖以下三种退出情况：

- 初始化过程中发生错误。
- 程序正常结束。
- 收到 `SIGINT` 或 `SIGTERM`。

## 4 日志系统

### 4.1 接口

```c
int init_glog(char *argv[]);
void deinit_glog(void);
```

### 4.2 初始化过程

`init_glog()` 在调用任何 `alogd()` 或 MPP 接口之前执行。函数首先创建 `/tmp/log` 目录，然后填充 `GLogConfig` 并调用 `log_init()`。

当前主要配置如下：

| 配置项 | 当前值 | 作用 |
|---|---:|---|
| `FLAGS_logtostderr` | 0 | 启用文件日志 |
| `FLAGS_stderrthreshold` | `INFO` | INFO 及以上日志同时输出到终端 |
| `FLAGS_minloglevel` | `INFO` | 过滤低于 INFO 的日志 |
| `FLAGS_logbufsecs` | 0 | 日志立即刷新 |
| `FLAGS_max_log_size` | 1 | 单个日志文件最大约 1 MB |
| `LogDir` | `/tmp/log` | 日志文件目录 |

`/tmp` 通常属于临时文件系统，设备重启后日志可能消失。该路径适合开发调试，不适合作为长期日志存储目录。

### 4.3 退出过程

程序完成 MPP 和上下文清理后调用：

```c
deinit_glog();  /* 内部调用 log_quit()，关闭日志系统。 */
```

关闭日志之后不能继续调用 `alogd()`、`alogw()` 或 `aloge()`。

## 5 当前应用上下文生命周期

对于应用级上下文，`context.h`只公开不透明声明；该头文件同时公开VI模块使用的`VideoCaptureContext`，两者不是同一个对象：

```c
typedef struct IpCameraContext IpCameraContext;
```

实际布局由`application.c`管理，包含模块对象、启动状态和消费者锁；
配置使用独立的`IpCameraConfig`。当前公开接口来自`application.h`：

```c
IpCameraContext *ip_camera_application_create(const IpCameraConfig *config);
int ip_camera_application_start(IpCameraContext *context, IpCameraRunMode mode);
int ip_camera_application_stop(IpCameraContext *context);
void ip_camera_application_destroy(IpCameraContext *context);
```

### 5.1 create：建立对象，不启动硬件

`ip_camera_application_create()`检查配置指针，使用`calloc()`分配上下文，复制配置，初始化消费者互斥锁，再将`config->preview`复制到VI运行状态，并接入编码数据分发回调。

配置结构按值复制，但路径字符串是借用引用，没有逐个复制字符串内容。路径必须存活到destroy结束。此时不创建VI、VO或编码硬件通道，也不启动工作线程。

### 5.2 start：按模式和依赖启动

`ip_camera_application_start()`先初始化MPP；声音自检只启动报警模块，监控模式则调用各个`start_*()`函数。已成功启动的模块用状态标志记录，失败后由main的`cleanup`调用stop进行清理。同一个上下文不能重复start。

### 5.3 stop / destroy：先停使用者，再释放对象

完整监控的当前清理顺序是：

```text
区域规则 → 越线规则 → 声音报警 → LCD检测框 → 编码检测框 → NPU
→ 关闭MP4输入入口 → 音频编码 → 时间OSD → 视频编码
→ MP4收尾 → RTSP → VI采集 → VO/G2D显示 → MPP
```

这是资源依赖顺序，不是把启动列表机械倒序。编码回调停止前，录像和RTSP消费者对象不能先销毁；VI线程停止前，显示对象也不能先释放。

stop处理NULL、部分启动和重复调用：清理过程中记录错误并继续尝试后续操作；结束后缓存结果，重复stop返回缓存结果，不会重新执行整套硬件清理。destroy兜底调用stop，再销毁消费者锁并释放上下文。它不是裸`free()`，但也不是能强制中断阻塞驱动的看门狗。

旧`constructIpCameraContext()`、`destructIpCameraContext()`只放在文末历史附录，当前入口不调用它们。

## 6 MPP 平台初始化

MPP 初始化由 `platform_init()` 完成。

### 6.1 设置系统配置

```c
MPP_SYS_CONF_S sys_conf;

memset(&sys_conf, 0, sizeof(sys_conf));
sys_conf.nAlignWidth = 32;

AW_MPI_SYS_SetConf(&sys_conf);
```

`nAlignWidth` 设置为 32，供后续媒体缓冲区和图像数据按照硬件要求对齐。

不要把这个MPP对齐配置与VI有效分辨率混为一谈。日志出现1920×1088的ISP工作尺寸，不表示应用配置的1920×1080必须在这里改成1088。

### 6.2 初始化 MPP

```c
AW_MPI_SYS_Init();
```

该接口会初始化 MPP 基础模块。开发板日志表明，调用过程中同时完成了 ISP、硬件显示基础层和 ALSA Mixer 的初始化。

这里的ISP基础初始化不等于已经创建摄像头采集通路。具体VIPP属性、`AW_MPI_ISP_Run()`、VI虚拟通道和取帧线程属于阶段2。

### 6.3 初始化 PTS 基准

```c
uint64_t current_pts = 0;

AW_MPI_SYS_GetCurPts(&current_pts);
AW_MPI_SYS_InitPtsBase(current_pts);
```

`AW_MPI_SYS_GetCurPts()` 要求传入 `uint64_t *`，因此必须使用 `&current_pts`。PTS 基准将供后续视频、音频、编码、推流和录像模块使用。

这不是校准日历时间，也不会自动联网对时。媒体PTS与阶段7水印读取的日期时间应分开理解；建立PTS基准也不能替代后续推流和封装模块的同步处理。

### 6.4 错误回滚

每个 MPP 接口都检查返回值。如果 MPP 已经初始化，但 PTS 获取或 PTS 基准设置失败，`platform_init()` 会调用 `AW_MPI_SYS_Exit()` 回滚已经初始化的资源。

### 6.5 平台退出

```c
int platform_deinit(void)
{
    ERRORTYPE result = AW_MPI_SYS_Exit();
    return result == SUCCESS ? 0 : -1;
}
```

开发板日志中的 `alsaCloseMixer`、`hwd_exit` 和 `MonitorEnvVar thread will exit` 都属于 MPP 正常退出过程。

## 7 信号处理

### 7.1 支持的信号

程序处理以下两个退出信号：

| 信号 | 常见来源 | 作用 |
|---|---|---|
| `SIGINT` | 终端按下 `Ctrl+C` | 交互式停止程序 |
| `SIGTERM` | `kill` 或服务管理器 | 请求程序正常退出 |

### 7.2 信号标志

```c
static volatile sig_atomic_t g_exit_signal;
```

`sig_atomic_t`适合在信号处理函数和主流程之间传递简单标志；`volatile`防止编译器把反复检查的标志当作不会变化。它不等于互斥锁，也不能推导为所有线程共享数据都已具备同步保护。

### 7.3 信号处理函数

```c
static void handle_exit_signal(int signal_number)
{
    g_exit_signal = signal_number;
}
```

信号处理函数只记录信号编号，不执行以下操作：

- 不打印日志。
- 不调用 `free()`。
- 不调用 MPP 接口。
- 不执行互斥锁操作。

这些操作不适合在异步信号上下文中执行。真正的资源释放由主线程完成。

### 7.4 使用 sigaction 注册

```c
struct sigaction action;

memset(&action, 0, sizeof(action));
action.sa_handler = handle_exit_signal;
sigemptyset(&action.sa_mask);

sigaction(SIGINT, &action, NULL);
sigaction(SIGTERM, &action, NULL);
```

源码在包含系统头文件之前定义：

```c
#define _POSIX_C_SOURCE 200809L
```

该宏使严格 C 标准模式下能够获得 `struct sigaction`、`sigaction()` 和 `sigemptyset()` 的 POSIX 声明。

## 8 主循环

应用所选模式启动成功后，main调用`main_loop()`。以下摘录为监控模式的日志与等待逻辑：

```c
alogd("[Main] Application is running; press Ctrl+C to exit");

while (g_exit_signal == 0) {
    sleep(1);
}

alogd("[Main] Exit signal received: %d", (int)g_exit_signal);
```

主线程通过`sleep(1)`避免空转，醒来后检查退出标志。信号投递到主线程时可中断sleep；在多线程进程中不能保证信号一定由主线程接收，因此不能承诺“按Ctrl+C后所有资源立即释放”。即使主循环已退出，后面的join和MPP驱动清理仍需要时间。

当前视频、音频、推流、录像和AI模块已经有各自的工作线程，主循环只负责等待退出，不处理每一帧图像。

学习检查：能否说明“信号标志已设置”“工作线程已退出”“硬件资源已释放”是三个不同的时刻？能否解释为什么日志系统最后关闭？

## 附录A：阶段1旧上下文示例（接口已移除）

下列代码解释早期“分配/释放一个最小对象”的做法，不是当前头文件和生命周期接口：

```c
typedef struct IpCameraContext {
    int initialized;
} IpCameraContext;
```

```c
IpCameraContext *constructIpCameraContext(void)
{
    IpCameraContext *context = calloc(1, sizeof(*context));

    if (context == NULL) {
        aloge("fatal error! allocate IP camera context failed");
        return NULL;
    }

    return context;
}
```

```c
void destructIpCameraContext(IpCameraContext *context)
{
    free(context);
}
```

`calloc()`把新分配的对象清零；裸`free()`只释放对象内存。现在对象包含线程和硬件服务的生命周期依赖，必须使用`ip_camera_application_stop()`和`ip_camera_application_destroy()`，不能把这个历史例子直接复制到当前main。
