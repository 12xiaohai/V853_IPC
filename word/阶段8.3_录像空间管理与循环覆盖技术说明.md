# 阶段8.3：录像空间管理与循环覆盖技术说明

> 架构同步（2026-10-03）：当前main.c负责信号、运行模式与主循环，
> 默认参数集中在config.c，服务启动/回调/清理由application.c负责。
> 空间/段数策略现位于config->recorder；扫描与删除范围仍由mp4_recorder严格限制。
> 早期阶段范围、旧代码示例及实测日志属于当时快照，不表示重构后已完成板端复测。
> 详见[架构重构说明](架构重构_入口配置与应用生命周期技术说明.md)。

## 1. 阶段目标

阶段8.2能够持续生成按时间命名的分段MP4。阶段8.3增加受控的存储管理：

1. 启动时扫描已有录像；
2. 限制受管录像文件数量；
3. 保证录像分区保留最低可用空间；
4. 达到限制时优先删除最旧录像；
5. 不删除程序、裸码流、普通MP4或用户的其他数据；
6. 删除失败、只读文件系统和空间不足均输出明确日志。

## 2. 当前策略

当前`config.c`的`ip_camera_config_defaults()`中配置为：

```c
config->recorder.max_segment_files = 10;
config->recorder.min_free_space_mb = 512;
```

含义：

- 最多保留10个受管分段录像；
- `/mnt/UDISK`可用空间低于512 MiB时继续删除最旧的受管录像；
- 两个条件任意一个触发都会执行清理；
- 当前正在写入的文件始终受保护。

文件数量限制比原项目的固定10段策略更清晰，同时增加了剩余空间保护，避免
其他文件占用磁盘后仅依赖录像数量仍然写满分区。

## 3. 严格的删除范围

只有文件名完全符合以下格式才属于受管录像：

```text
record_YYYYMMDD_HHMMSS_NNNN.mp4
```

代码逐段检查：

- 前缀必须与`file_prefix`完全一致；
- 日期必须是8个数字；
- 时间必须是6个数字；
- 序号必须是4个数字；
- 扩展名必须精确为`.mp4`；
- `lstat()`结果必须是普通文件。

因此以下内容不会被删除：

```text
sample_strip
sample_demo.h264
sample_demo.aac
sample_demo.mp4
record_backup.mp4
record_20261001_120000_0001.mp4.bak
任何目录或符号链接
```

输出目录必须是绝对路径，不能是根目录`/`，路径中不接受`/../`；文件前缀只
允许字母、数字和连字符。这些检查用于防止配置错误扩大删除范围。

## 4. 清理时机

存储检查在四个时机执行：

1. 应用启动、创建首段之前：为新文件预留一个数量名额；
2. MUX请求下一个FD时：先清理，再创建下一段；
3. 收到`MPP_EVENT_RECORD_DONE`后：旧文件完成，重新执行数量检查；
4. Ctrl+C完成最后一段封口后：执行最终清理。

MUX回调本身不扫描目录和删除文件。`RECORD_DONE`只设置`cleanup_requested`并
唤醒原有切片工作线程，避免在MPP内部线程中执行慢速文件系统操作。

## 5. 最旧文件判定

扫描结果按照文件修改时间`st_mtime`从旧到新排序；修改时间相同时再按完整
路径排序，确保选择结果稳定。

删除循环每次只删除一个最旧候选，然后重新读取可用空间，直到同时满足：

```text
受管文件数 + 预留名额 <= max_segment_files
可用空间 >= min_free_space_mb
```

文件名中的时间只用于识别和展示，不作为唯一的删除顺序依据。这样即使NTP
校时或系统时间发生跳变，仍主要按照文件系统实际修改时间处理。

## 6. 当前文件保护

清理函数接收`protected_path`。扫描列表中即使该文件修改时间最早，也不会被
选为删除候选：

- 切换前保护当前正在写入的旧段；
- MUX预取阶段继续保护当前正在写入的旧段；
- 收到`RECORD_DONE`确认实际切换后，才把备用段晋升为当前文件并保护；
- 程序退出后仍保护本次最后生成的录像。

当磁盘空间不足且除当前文件外没有任何可删除的受管录像时，系统记录错误并
停止提供下一个分段FD，不会删除当前文件，也不会转而删除不受管文件。

## 7. 删除失败处理

以下情况会设置存储错误状态：

- 无法打开录像目录；
- `statvfs()`查询空间失败；
- 删除旧录像失败；
- 删除所有可用候选后仍低于最低空间；
- 文件切换前的存储清理失败。

错误会在日志中保留路径和`errno`。应用安全退出时录像器返回失败，使主程序
最终退出码反映存储异常。`SwitchFd`失败时刚创建但尚未交给MUX的空文件会被
立即删除，避免留下零字节占位文件。

此外，`AW_MPI_MUX_SwitchFd()`成功只代表MUX接收了下一个文件描述符，并不
代表实际分段已经发生。程序使用`pending_output_path`单独保存备用文件：

- 正常收到`MPP_EVENT_RECORD_DONE`后，备用文件才晋升为当前录像；
- 停止MUX后，若备用文件仍为0字节，说明它从未启用，程序将其删除；
- 若备用文件已经非空，则说明MUX已经开始写入，程序会保留它；
- 退出统计通过`discarded_empty_files`记录清理的空备用文件数量。

## 8. 预期日志

空间充足且未超过数量：

```text
[MP4] Storage check: managed=2, available=7100 MiB, limit=10, reserve=1
```

超过限制时：

```text
[MP4] Deleted old recording: /mnt/UDISK/record_....mp4
[MP4] Storage check: managed=9, available=..., limit=10, reserve=1
```

退出统计增加：

```text
completed_files=...
deleted_files=...
discarded_empty_files=...
```

## 9. 首次开发板验证与问题复盘

### 9.1 验证结果

首次运行日志报告：

```text
managed=2, available=7079 MiB, limit=10, reserve=1
```

说明目录扫描、文件名过滤和可用空间统计均正常。本次没有达到数量或空间阈值，
程序没有删除任何旧录像。运行期间成功生成3个有内容、可正常播放的分段文件，
证明循环管理没有破坏原有MP4切片链路。

### 9.2 遇到的问题：退出后残留0字节分段

首次测试在Ctrl+C退出后出现：

```text
record_20261001_140824_0003.mp4    0 bytes
```

日志时序表明这不是磁盘写满，也不是清理函数误删：退出信号到达后、MUX真正停
止前，MUX恰好发出了`MPP_EVENT_NEED_NEXT_FD`。切片线程创建并通过
`AW_MPI_MUX_SwitchFd()`提交了下一段文件，但60秒切片边界尚未到达，MUX没有
真正向它写入数据，于是留下了空文件。

问题根因是旧实现把“SwitchFd接收成功”误认为“新文件已经成为当前文件”。修复
后将文件状态分成：

```text
当前正在写入文件 -> 已提交的备用文件 -> RECORD_DONE后成为新的当前文件
```

停止流程会先停止并销毁MUX，确保其不再写文件，然后检查备用文件：0字节则
删除，非0字节则保留。这样既消除空占位文件，也不会误删已经开始写入的短录像。

## 10. 安全验证步骤

### 10.1 首次验证不制造删除条件

保持当前`max_segment_files=10`，重新编译并运行一次，先确认扫描范围正确：

```sh
./sample_strip
```

日志应报告现有`record_*.mp4`数量和剩余空间，不应删除任何文件。退出后确认：

```sh
ls -lh /mnt/UDISK
```

`sample_strip`、`sample_demo.*`和其他文件必须仍然存在。

### 10.2 循环删除验证前先备份真实录像

循环删除属于不可恢复操作。若要加速测试数量上限，应先把需要保留的真实录像
移动到不匹配命名规则的备份目录，再使用测试录像验证。不要直接把重要文件
留在`record_*.mp4`受管集合中进行删除实验。

建议在确认普通运行无误后，再临时将`max_segment_files`改为2或3，在明确没有
重要受管录像的条件下运行多段测试。验证完成后恢复为10。

### 10.3 验证项目

1. 删除顺序确实从最旧文件开始；
2. 文件数不超过配置上限；
3. 当前正在写入的文件不会被删除；
4. 非受管文件全部保留；
5. 删除后新MP4仍有正常画面和声音；
6. Ctrl+C后最后一段正常封口；
7. 日志中的`deleted_files`与实际删除数量一致。

### 10.4 空备用文件回归测试

程序启动约50秒、日志出现`Submitted pending segment`后，在下一次60秒切片边界
到达前按Ctrl+C。预期日志包含：

```text
[MP4] Removed unused empty pending segment: ...
discarded_empty_files=1
```

随后执行`ls -lh /mnt/UDISK/record_*.mp4`，不应再出现本次运行产生的0字节录像。

开发板回归结果：

```text
record_20261001_142120_0000.mp4    5.8M
sample_demo.aac                  111.1K
sample_demo.h264                   4.7M
sample_strip                       5.3M
```

本次仅保留了一个已有有效内容的分段MP4，没有生成或遗留0字节的下一段文件；
`sample_demo.aac`、`sample_demo.h264`及应用程序也未被空间管理逻辑误删。因此
“退出后残留0字节分段”问题的回归验证通过。
