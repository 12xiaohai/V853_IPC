# 阶段 6.3：RTSP 音视频同步推流技术说明

## 1. 本阶段目标

阶段 5 已经完成 H.264 RTSP 视频推流，阶段 6.2 已经验证 AAC 编码文件。
本阶段将两条已经独立验证的链路合并，让同一个 RTSP 地址同时提供 H.264
视频轨和 AAC 音频轨：

```text
rtsp://<开发板-wlan0-IP>:8554/ch0
```

目标是在 VLC 中同时看到实时画面、听到麦克风声音，并保持音视频时间关系
稳定。

## 2. 整体数据通路

```text
VIPP 0 → VENC(H.264) → VENC取流线程 → 视频深拷贝 → 视频环形队列 ┐
                                                                  ├→ RTSP发送线程 → TinyServer
AI 0  → AENC(AAC)    → AENC取流线程 → 音频深拷贝 → 音频环形队列 ┘
```

本阶段不让 VENC/AENC 线程直接调用网络库。编码线程只完成文件写入和快速
入队，统一的 RTSP 发送线程负责调用 TinyServer。这样即使网络短暂变慢，
也不会长时间占用 MPP 编码缓冲。

## 4. 为什么需要深拷贝

VENC/AENC 返回的码流地址属于 MPP 内部缓冲区：

```text
GetStream → 临时持有缓冲 → ReleaseStream → 地址失效或被复用
```

RTSP 网络发送发生在另一个线程中，因此不能只把 `pStream` 指针放进队列。
入队函数会立即分配自己的内存并复制整帧数据，编码线程随后才能安全调用
`ReleaseStream()`。RTSP线程发送完成后负责释放副本。

## 5. 独立的有界队列

视频和音频各有一个固定容量环形队列，当前每个队列容量均为16帧：

```text
video_queue：16 × H.264帧
audio_queue：16 × AAC帧
```

两类帧大小和产生频率不同，因此不能混用同一组队列下标。队列固定容量可
限制最坏情况下的内存占用。若网络发送持续落后导致队列满，模块会丢弃该
媒体队列中最旧的帧，使直播尽快回到当前时刻，而不是无限积累延迟。

## 6. PTS与音视频同步

VENC输出的H.264帧和AENC输出的AAC帧都携带MPP微秒PTS，二者来自同一个
系统媒体时钟。代码完整保留这些时间戳，不使用系统墙上时间，也不根据
帧数重新计算PTS。

发送线程每次查看两个队头：

1. 只有一种帧时，立即发送该帧；
2. 两种帧同时存在时，先发送PTS较早的帧；
3. 视频帧调用 `appendVideoData(..., video_pts, ...)`；
4. 音频帧调用 `appendAudioData(..., audio_pts)`。

音频和视频保持各自独立的采样节奏，不强行把“一帧音频”绑定到“一帧
视频”。TinyServer根据两个媒体轨的PTS产生RTP时间关系，客户端再根据
时间戳同步播放。

## 7. 为什么不能简单一帧视频配一帧音频

当前视频约为20 fps，每帧间隔约50 ms；AAC每帧1024个采样点，在16 kHz
下的间隔为：

```text
1024 ÷ 16000 = 64 ms
```

两者帧率不同。如果机械地一一配对，音频会被迫按照20 fps发送，长期运行
后必然出现声音速度异常、帧丢失或同步漂移。正确方法是让两种媒体各自按
原始PTS发送。

## 8. 线程安全和停止顺序

VENC线程和AENC线程是两个生产者，RTSP线程是消费者。所有队列下标和
计数都由同一个互斥量保护，条件变量在任一队列加入新帧时唤醒消费者。

程序退出时按照以下顺序处理：

1. 停止AENC，使音频队列不再产生新帧；
2. 停止VENC，使视频队列不再产生新帧；
3. 通知RTSP线程停止，并发送完已经入队的剩余帧；
4. 停止并销毁TinyServer；
5. 清理环形队列和同步对象。

这能避免RTSP上下文销毁后，编码线程仍向其中推送数据。

## 9. 运行日志统计

退出时RTSP模块会分别输出音视频统计：

```text
[RTSP] Sender stopped: video=发送/入队 dropped=丢弃,
                       audio=发送/入队 dropped=丢弃
[RTSP] A/V PTS offset: first=... us, last=... us
```

`first` 为首个音频PTS减首个视频PTS。由于视频编码器先启动，首帧音频晚于
首帧视频是正常现象。`last` 还会受按下 `Ctrl+C` 的时刻和不同帧周期影响，
不能单独作为漂移结论；需要结合长时间播放和队列丢帧情况判断。

1. VLC能够显示连续摄像头画面；
2. VLC能够同时播放麦克风声音；

4. 对着镜头拍手或敲击物体，观察动作和声音是否基本同步；
5. 连续运行至少2分钟，声音无明显持续漂移；
6. 退出日志中音视频 `queued` 与 `sent` 一致，`dropped=0`；
7. `sample_demo.h264` 和 `sample_demo.aac` 仍能分别独立播放；
8. 按 `Ctrl+C` 后程序退出码为0。

也可以用FFmpeg工具查看RTSP中的媒体轨：

```sh

```

## 12. 开发板长时间实测结果

2026-09-30 在 V853 开发板上连续运行约 5 分 27 秒，统计如下：

```text
RTSP视频：入队 6511，发送 6511，丢弃 0
RTSP音频：入队 5107，发送 5107，丢弃 0
AAC数据：5107帧，1266129字节
LCD预览：提交 6519，释放 6519，丢弃 0
首帧 A-V PTS：+264286 us
末帧 A-V PTS： -71576 us
程序退出码：0
```

AAC共有5107帧，即5106个帧间隔，其理论持续时间为：

```text
5106 × 1024 ÷ 16000 = 326.784 秒
```

日志中AAC首末PTS差为326.783950秒，误差仅约50微秒，证明音频时间戳和
采样节奏长期连续、准确。首帧音频晚约264毫秒，是因为主程序先启动VENC、
后启动AENC；退出时先停止AENC、再停止VENC，所以末帧音频早于视频约72
毫秒。这两个端点差主要由启动/停止顺序造成，不能当作播放过程中的累计
漂移。

两个RTSP队列在五分多钟内均实现入队数等于发送数且零丢帧，说明编码线程、
深拷贝队列和TinyServer发送速度匹配。所有组件最终正常销毁，退出码为0。
日志中偶发的摄像头FIFO告警没有造成应用层预览丢帧，但若实际画面出现花屏
或跳帧，应单独检查CSI时序、传感器线路和系统负载。
