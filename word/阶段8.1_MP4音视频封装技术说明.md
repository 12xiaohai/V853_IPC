# 阶段 8.1：MP4 音视频封装技术说明

> 当前实现更新（2026-10-02）：本文件保留阶段8.1的同步送流开发过程。
> 阶段9.7压力测试发现分段附近的送流/退出阻塞风险，现已改为音视频统一异步MUX、
> 有界码流副本及释放回调；调用者返回后可归还原始编码缓冲。
> 详见[阶段9.7压力测试复盘第8节](阶段9.7_集成压力测试与退出阻塞复盘.md)。

## 1. 本阶段目标

把项目中已经生成的H.264视频帧和AAC音频帧封装进同一个MP4文件：

```text
/mnt/UDISK/sample_demo.mp4
```

本阶段先使用固定文件名，不做定时分段和循环覆盖。程序收到 `Ctrl+C` 后，
必须正常停止MUX并写完MP4尾部索引，使文件能够被VLC、ffplay和ffprobe读取。

## 2. 为什么不能直接拼接H.264和AAC

`.h264` 和 `.aac` 是两种独立的裸码流。简单地把它们写入同一个文件无法
形成MP4，因为MP4还需要保存：

- 视频轨和音频轨的编码参数；
- 每帧的时间戳和持续时间；
- 关键帧索引；
- 音视频轨之间的对应关系；
- 文件尾部的索引和容器元数据。

因此本阶段使用全志MPP提供的MUX模块完成容器封装。

## 3. 数据通路

```text
VI ─→ VENC(H.264) ─┬─→ sample_demo.h264
                   ├─→ RTSP视频队列
                   └─→ MPP MUX视频输入 ─┐
                                        ├─→ sample_demo.mp4
AI ─→ AENC(AAC) ───┬─→ sample_demo.aac  │
                   ├─→ RTSP音频队列      │
                   └─→ MPP MUX音频输入 ─┘
```

录像、裸流文件和RTSP共享同一套VENC/AENC输出，不新增第二套编码器。这可以
减少V853的编码资源占用，并保证三个输出使用完全相同的编码帧和原始MPP PTS。

## 4. 与原项目录像方式的关系

原项目同样使用 `AW_MPI_MUX` 生成MP4，但为存储通路另外创建了VENC/AENC，
然后通过 `AW_MPI_SYS_Bind()` 把它们绑定到MUX。

当前复刻工程已经由应用线程调用 `AW_MPI_VENC_GetStream()` 和
`AW_MPI_AENC_GetStream()`，同一批码流还要用于RTSP和裸流测试。如果再把现有
编码通道以隧道方式独占绑定给MUX，可能与应用取流产生冲突；如果完全复制原
项目的独立存储编码通路，又会重复占用硬件编码资源。

因此本阶段仍使用原项目的MPP MUX，只是采用它提供的非隧道同步接口：

```text
AW_MPI_MUX_SendVideoStreamSync()
AW_MPI_MUX_SendAudioStreamSync()
```

同步接口返回后，VENC/AENC缓冲才由编码线程释放，所以MUX不会引用已经归还
给编码器的内存，也不需要为录像再次深拷贝整帧码流。

## 5. 新增文件

```text
sample/ipc_camera/include/mp4_recorder.h
sample/ipc_camera/app/mp4_recorder.c
```

录像模块提供以下生命周期：

```text
mp4_recorder_create()
        ↓

        ↓
mp4_recorder_push_video()/push_audio()
        ↓
mp4_recorder_stop()
        ↓
mp4_recorder_destroy()
```

## 6. MUX媒体参数

阶段8.1创建一个MP4 MUX通道，并配置：

- 视频：H.264、1920×1080、20 fps、VENC通道0；
- 音频：AAC、16000 Hz、16 bit、单声道、每帧1024采样点；
- 文件格式：`MEDIA_FILE_FORMAT_MP4`；
- 文件时长与大小限制：0，表示本阶段不自动分段；
- 写文件模式：`FSWRITEMODE_SIMPLECACHE`；
- 缓存大小：64 KiB。

VENC产生的SPS/PPS通过 `AW_MPI_MUX_SetH264SpsPpsInfo()` 传给MUX，用于生成
MP4视频轨的解码配置。

由于本阶段使用非隧道送流，MPP不会像 `AW_MPI_SYS_Bind()` 那样自动建立VENC
与MUX输入端口的关系。因此创建MUX后还必须显式调用：

```c
AW_MPI_MUX_SetVeChnBindStreamId(mux_channel, venc_channel, 0);
```

它表示VENC通道0对应MUX视频流0。必须先建立映射，再设置SPS/PPS，否则MUX
无法找到SPS/PPS所属的视频轨。

本SDK在单视频轨、单音频轨配置下使用以下流编号：

```text
streamId 0：H.264视频
streamId 1：AAC音频
```

因此 `AW_MPI_MUX_SendVideoStreamSync()` 必须传0，
`AW_MPI_MUX_SendAudioStreamSync()` 必须传1。若音频错误地传0，SDK会输出
`audio streamId[0!=1] wrong`，MP4中不会生成有效音频帧。

## 7. 从关键帧开始录像

MP4的第一帧视频必须能够独立解码。录像器启动后先进入
`waiting_for_key_frame` 状态：

1. 到达首个IDR之前，跳过P帧和音频帧；
2. 收到IDR后开始向MUX送入视频；
3. 随后的AAC帧才开始进入音频轨。

录像器接入消费者后，主程序调用 `AW_MPI_VENC_RequestIDR()` 请求VENC尽快
产生关键帧，避免等待完整GOP。

## 8. 音视频时间戳

视频帧使用 `VENC_PACK_S.mPTS`，音频帧使用 `AUDIO_STREAM_S.mTimeStamp`。
两者均为MPP产生的微秒时间戳。录像路径不重新使用系统时间计算PTS，也不按
线程到达时间伪造时间戳，从而保持与阶段6.3 RTSP音画同步相同的时间基础。

系统时间只用于后续阶段8.2的文件命名，不参与MP4内部音画同步。

## 9. 并发与缓冲所有权

H.264和AAC分别来自两个编码线程。录像模块使用互斥量串行访问同一个MUX
通道。每次送流都遵循：

```text
GetStream
    ↓
写裸流/发送RTSP/同步发送MUX
    ↓
ReleaseStream
```

RTSP在回调中深拷贝数据；MUX同步接口在返回前消费数据。因此执行
`ReleaseStream` 后，不会有消费者继续访问MPP编码缓冲。

## 10. 安全退出

退出时必须先停止编码线程，再关闭MUX：

1. 停止AENC取流线程；
2. 从VENC解绑并销毁OSD；
3. 停止VENC取流线程；
4. 禁止录像器接收新帧；
5. 调用 `AW_MPI_MUX_StopChn(..., FALSE)` 正常写完缓存和索引；
6. 销毁MUX通道；
7. 关闭MP4文件描述符。

不能直接断电或使用强制停止参数，否则MP4可能缺少尾部索引而无法播放。

## 13. 实际问题与排障记录

### 13.1 第一次实测：首个关键帧到达后程序段错误

问题现象：

```text
RecRenderSetH264SpsPpsInfo: not find VeChn[0] in streamId binding list
Segmentation fault (core dumped)
```

程序成功创建MUX并收到首个IDR帧，但在MP4内部初始化视频轨、读取SPS/PPS
节点时崩溃，生成的 `sample_demo.mp4` 为0字节。

定位依据：日志明确指出MUX的streamId映射表中找不到VENC通道0。原项目采用
MPP隧道绑定，绑定过程会自动建立通道映射；复刻工程采用非隧道同步送流，
不会自动建立该映射。

根因：调用 `AW_MPI_MUX_SetH264SpsPpsInfo()` 前，没有告诉MUX“VENC通道0
属于视频流0”。

解决方法：创建MUX通道后、设置SPS/PPS前增加：

```c
AW_MPI_MUX_SetVeChnBindStreamId(mux_channel, venc_channel, 0);
```

第二次实测结果：

```text
RecRenderVeChnBindStreamId: VeChn mChnId: 0 bind StreamId: 0
[MP4] VENC-to-MUX mapping ready: venc=0 -> stream=0
RecRenderSetH264SpsPpsInfo: ... set Venc header data is success
```

段错误消失，程序连续运行约6秒并以返回码0退出，MP4成功写入视频轨和尾部
索引，文件大小约3.9 MiB。

### 13.2 第一次实测：出现块设备越界写错误

问题现象：

```text
attempt to access beyond end of device
mmcblk0p1: want=..., limit=6016
Buffer I/O error on dev mmcblk0p1
```

最初怀疑 `/mnt/UDISK` 容量不足。随后通过 `df`、`/proc/mounts`、
`/proc/partitions` 和sysfs进行只读检查，得到：

```text
/mnt/UDISK -> /dev/mmcblk0p7 -> 约7 GiB，空间充足
/mnt/extsd -> /dev/mmcblk0p1 -> 物理约2.94 MiB
Vfat文件系统报告 /mnt/extsd 为8 MiB且已100%使用
```

根因：报错设备是 `mmcblk0p1`，即 `/mnt/extsd`，不是MP4所在的
`mmcblk0p7`。该Vfat文件系统记录的容量大于底层分区实际容量，ISP保存上下文
文件时可能触发越界I/O。

处理结论：阶段8.1继续使用容量正常的 `/mnt/UDISK`；不把录像路径切换到
`/mnt/extsd`。extsd的分区/文件系统不匹配问题与MP4封装分开处理。

### 13.3 第二次实测：MP4只有视频，没有有效AAC音频

问题现象：程序不再崩溃，录像器统计收到85帧AAC，但每一帧都出现：

```text
aw_mux_SendAudioStream: audio streamId[0!=1] wrong
```

退出时MP4日志进一步显示视频时长约6.1秒，而音频轨时长为0：

```text
mp4_dur_info:0-...-6102697-...
mp4_dur_info:1-0-0-64
```

根因：单视频轨、单音频轨的MUX配置中，视频使用streamId 0，音频使用
streamId 1。代码错误地给 `AW_MPI_MUX_SendAudioStreamSync()` 传入了0。

解决方法：为流编号定义明确常量，并将音频送流改为：

```c
#define MP4_VIDEO_STREAM_ID 0
#define MP4_AUDIO_STREAM_ID 1

AW_MPI_MUX_SendAudioStreamSync(mux_channel,
                               &audio_stream,
                               MP4_AUDIO_STREAM_ID);
```

验证结果：第三次实测中不再出现 `audio streamId[0!=1] wrong`。录像器共向
MUX提交1775帧AAC数据，MUX的音频轨生成了非零时长和1775个chunk索引；仍需
使用ffprobe和播放器完成最终的解码、听音验证。

### 13.4 第二次实测：MUX退出时提示没有注册回调

问题现象：MP4已经正常写完尾部索引，但停止时出现：

```text
RecRenderEventHandler: Error! User should RegisterCallback to mpp!
```

根因：固定文件模式虽然不需要切换下一个FD，但MUX在正常完成文件时仍会上报
`MPP_EVENT_RECORD_DONE`；录像模块没有注册回调，SDK只能打印错误提示。

解决方法：创建MUX通道后调用 `AW_MPI_MUX_RegisterCallback()`，在回调中记录
`MPP_EVENT_RECORD_DONE`；阶段8.1若意外收到 `MPP_EVENT_NEED_NEXT_FD`，则记录
警告。第三次实测已经收到 `[MP4] MUX reported record done: muxer_id=0`，且不再
出现未注册回调错误，说明该修复有效。

重复出现或造成卡顿，再检查强制IDR前后的VENC缓存帧顺序。

### 13.7 第三次提交的日志仍来自旧版二进制

问题现象：再次提交的运行日志仍然包含：

```text

User should RegisterCallback to mpp!
```

这两个现象按当前源码应同时消失，因此首先需要判断开发板运行的程序是否
确实包含最新修复，而不能立即继续修改MUX代码。

定位证据：

1. 该日志运行时间为 `2026-10-01 12:58`；
2. 包含音频streamId与MUX回调修复的仓库提交时间为 `13:02:07`；

4. 当前源码明确存在 `MP4_AUDIO_STREAM_ID 1` 和
   `AW_MPI_MUX_RegisterCallback()`。

根因：这份日志是在修复提交生成之前运行得到的，或者虚拟机没有拉取最新
提交、增量构建没有重编译 `mp4_recorder.o`、复制到开发板的仍是旧程序。

处理方法：虚拟机拉取最新提交后执行干净构建，并对虚拟机产物和开发板程序
计算SHA-256，确认两者完全相同：

```sh

git log -1 --oneline
make clean

```

复制后在开发板执行：

```sh

strings /mnt/UDISK/sample_strip | grep "MUX reported record done"
```

两个SHA-256必须相同，并且 `strings` 必须能找到新回调日志字符串，才能开始
真正的第三次实测。

### 13.9 VLC有声音，但Windows本地媒体播放器无声音

问题现象：同一个 `sample_demo.mp4` 使用VLC播放时画面和声音均正常，使用
Windows本地媒体播放器时只有画面、没有声音。

初步结论：VLC能够正常解码，证明MP4中存在有效AAC数据，音频采集、AAC编码
和写入MUX的基本链路已经成立。该现象更可能来自播放器对当前AAC参数或
Allwinner MUX生成的MP4音轨描述兼容性不同。当前音频参数为AAC、16000 Hz、
单声道；VLC自带解码器且容错能力较强，系统播放器则依赖Windows媒体框架和
已安装的解码组件。

首先在电脑执行以下命令，检查音轨的编解码器名称、Profile、采样率、声道、
codec tag、时长及extradata：

```sh
ffprobe -v error -show_entries \
stream=index,codec_name,codec_long_name,profile,codec_type,codec_tag_string,\
sample_rate,channels,channel_layout,duration,bit_rate,extradata_size \
-of default=noprint_wrappers=1 sample_demo.mp4
```

再做一次不重新编码的标准化封装测试：

```sh
ffmpeg -i sample_demo.mp4 -map 0 -c copy -movflags +faststart \
sample_demo_remux.mp4
```

判断方法：

1. 如果 `sample_demo_remux.mp4` 能在Windows播放器中发声，说明AAC本身正常，
   主要问题是原MUX生成的MP4容器元数据或索引兼容性；
2. 如果重封装后仍无声音，再将音频转成兼容性更广的AAC-LC、48000 Hz、双声道
   进行对照，视频保持不重新编码：

```sh
ffmpeg -i sample_demo.mp4 -c:v copy -c:a aac -profile:a aac_low \
-ar 48000 -ac 2 -b:a 128k -movflags +faststart sample_demo_compat.mp4
```

如果兼容版能够发声，则问题集中在16000 Hz单声道AAC参数或其音轨描述。拿到
ffprobe输出前，不直接修改开发板的采样率或编码链路，避免把播放器兼容性问题
误判成采集故障。

实际验证结果如下：

```text
codec_name=aac
profile=LC
codec_tag_string=mp4a
sample_rate=16000
channels=1
channel_layout=mono
time_base=1/16000
duration=113.000000
bit_rate=31616
nb_frames=1775
```

这些字段表明音轨已经被识别为标准AAC-LC音轨，帧数和前述MUX统计一致。随后
使用 `ffmpeg -map 0 -c copy -movflags +faststart` 进行无损重封装，生成的
`sample_demo_remux.mp4` 可以被Windows本地播放器正常播放声音。

由于 `-c copy` 没有重新编码AAC，本次对照实验已经排除音频采集失败、AAC数据
损坏和16000 Hz单声道本身无法解码等原因。根因范围收敛到Allwinner MUX生成
的原始MP4音频sample、音轨元数据、时间戳/edit list或索引结构与Windows媒体
框架兼容性不足。VLC和FFmpeg容错能力较强，因此能正常处理原文件。

下一步先检查原MP4解复用后的首个AAC sample是否仍带ADTS同步头：

```sh
ffmpeg -v error -i sample_demo.mp4 -map 0:a:0 -c copy -f data - | xxd -l 16
ffmpeg -v error -i sample_demo_remux.mp4 -map 0:a:0 -c copy -f data - | xxd -l 16
```

如果原文件开头是 `ff f1` 或 `ff f9`，而重封装文件不是，说明带ADTS头的AAC
帧被直接作为MP4 sample写入；MP4通常应存放去掉ADTS头的AAC访问单元。此时应
在送入MUX前剥离每帧7字节或9字节ADTS头，同时保留独立 `.aac` 文件和RTSP所
需要的ADTS格式。如果两者都不含ADTS头，则继续对比MP4的音轨sample entry、
edit list和时间戳结构，不修改AAC采集参数。

实际对比结果为：

```text
原始MP4:   ff f1 60 40 19 5f fc ...
重封装MP4: de 04 00 00 6c 69 62 66 ...
```

`ff f1` 是不带CRC的ADTS同步头，因此根因已经确认：AENC因为
`attachAACHeader=1` 输出ADTS帧，应用将同一帧完整送入了MP4 MUX，SDK没有
自动剥离ADTS头。FFmpeg重封装时自动完成了ADTS到AudioSpecificConfig/裸AAC
sample的转换，所以重封装文件能被Windows播放器正常解码。命令末尾出现的
`Broken pipe` 是 `xxd -l 16` 读取16字节后主动关闭管道所致，不是文件错误。

代码修复位于 `mp4_recorder_push_audio()`：

1. 识别12位ADTS同步字；
2. 根据 `protection_absent` 判断头长为7字节还是9字节；
3. 解析13位 `frame_length` 并校验它与AENC帧长度一致；
4. 仅调整送给MUX的描述符指针和长度，剥离ADTS头后发送裸AAC sample；
5. 不修改原始AENC缓冲，因此独立 `.aac` 文件和RTSP继续使用完整ADTS帧；
6. 停止日志新增 `adts_stripped` 计数，便于确认每个MP4音频帧都完成转换。

修复代码通过源码差异及空白错误检查后重新部署至开发板。最终实测确认新生成
的MP4录像能够正常播放画面和声音，说明仅在MUX路径剥离ADTS头的处理有效，
且没有破坏H.264视频轨、AAC音频内容或MP4文件收尾。

### 13.10 阶段8.1最终验证结论

阶段8.1已经完成以下闭环验证：

1. H.264和AAC复用进同一个MP4文件；
2. 视频、音频均有连续有效数据和正确时长；
3. MP4从首个关键帧开始，停止时正常写入索引与文件尾；
4. 修正视频流映射和AAC音频streamId；
5. 注册MUX回调并正常收到录像完成事件；
6. MP4中的AAC sample不再携带ADTS头；
7. 最终录像画面和声音均可正常播放；
8. 独立AAC文件与RTSP路径仍保留原有ADTS数据格式，不受MP4修复影响。

因此阶段8.1“MP4音视频封装”正式完成。
