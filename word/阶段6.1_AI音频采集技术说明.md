# 阶段 6.1：AI 音频采集技术说明

> 架构同步（2026-10-03）：当前main.c负责信号、运行模式与主循环，
> 默认参数集中在config.c，服务启动/回调/清理由application.c负责。
> 独立PCM采集仅保留诊断实现；当前application启动AI→AENC，不同时启动旧PCM取帧通路。
> 早期阶段范围、旧代码示例及实测日志属于当时快照，不表示重构后已完成板端复测。
> 详见[架构重构说明](架构重构_入口配置与应用生命周期技术说明.md)。

## 1. 本阶段目标

本阶段先打通 V853 的麦克风采集链路，不急于加入 AAC 编码和 RTSP 音频推流。程序通过 MPP 的 AI（Audio Input）模块读取原始 PCM 音频帧，并保存为：

```text
/mnt/UDISK/sample_demo.pcm
```

这样可以先独立确认麦克风、AudioCodec、采样参数和 AI 通道是否正常，避免后续出现问题时无法判断故障来自采集、编码还是网络传输。

## 2. 音频参数

当前参数与原项目保持一致：

| 参数 | 配置值 | 含义 |
| --- | ---: | --- |
| AI 设备号 | 0 | 使用板载 AudioCodec |
| AI 通道号 | 0 | 使用第一个音频输入通道 |
| 采样率 | 16000 Hz | 每秒采集 16000 个采样点 |
| 位宽 | 16 bit | 每个采样点占 2 字节 |
| 声道数 | 1 | 单声道 |
| 每帧采样点 | 1024 | 每次 AI 帧约包含 64 ms 音频 |
| 录音音量 | 100 | AI 设备录音音量 |

理论数据量为：

```text
16000 × 2 × 1 = 32000 字节/秒
```

因此录制 10 秒时，PCM 文件大小应接近 320 KB。实际大小会受程序启动和退出时刻影响。

## 3. 软件结构

新增文件：

```text
sample/ipc_camera/include/audio_capture.h
sample/ipc_camera/app/audio_capture.c
```

`audio_capture.h` 提供配置结构和模块生命周期接口：

```text
audio_capture_create()
        ↓
audio_capture_start()
        ↓
audio_capture_stop()
        ↓
audio_capture_destroy()
```

阶段6.1当时由main.c启动独立PCM采集。当前正常监控由`application.c`启动
`audio_encoder`的AI→AENC绑定通路，参数位于`config.c`的`config->audio_encoder`。
`audio_capture.c/.h`仅保留为诊断实现，没有新增自动抓PCM的命令行模式，正常运行
不会同时启用这条旧采集通路或自动生成`sample_demo.pcm`。

## 4. AI 初始化流程

`audio_capture_start()` 依次完成：

1. 使用 `AW_MPI_AI_SetPubAttr()` 设置采样率、位宽、声道数和每帧采样点数。
2. 使用 `AW_MPI_AI_Enable()` 启用 AI 设备。
3. 使用 `AW_MPI_AI_SetDevVolume()` 设置录音音量。
4. 使用 `AW_MPI_AI_CreateChn()` 创建 AI 通道。
5. 设置用户态可持有的音频帧深度。
6. 创建或覆盖 PCM 输出文件。
7. 使用 `AW_MPI_AI_EnableChn()` 启用 AI 通道。
8. 创建采集线程，持续获取音频帧。

如果中间任一步骤失败，模块会按已经创建资源的实际状态进行回滚，避免设备或通道残留。

## 5. 音频帧的获取与归还

采集线程的核心流程如下：

```text
AW_MPI_AI_GetFrame()
        ↓
将 frame.mpAddr 指向的 frame.mLen 字节写入 PCM 文件
        ↓
AW_MPI_AI_ReleaseFrame()
```

`GetFrame` 和 `ReleaseFrame` 必须一一对应。AI 返回的内存属于 MPP 内部缓冲池，应用只能在持有音频帧期间读取，不能长期保存该地址。若取帧后不归还，内部缓冲会逐渐耗尽，最终无法继续采集。

线程还记录首帧和末帧 PTS。后续加入 AAC 和 RTSP 时，会以这些时间戳为基础处理音视频同步。

## 6. 为什么先保存裸 PCM

裸 PCM 没有文件头，也没有压缩，能够直接反映采集链路输出。若 PCM 可以正常播放，说明下列部分已经基本正常：

- 板载麦克风及硬件连接；
- AudioCodec 驱动；
- AI 设备与通道；
- 采样率、位宽和声道配置；
- 用户态取帧与归还逻辑。

PCM 验证成功后，再增加 AENC/AAC，排查范围会明显缩小。

## 7. 开发板验证方法

先删除旧文件，再运行新程序：

```sh
cd /mnt/UDISK
rm -f sample_demo.pcm
./sample_strip
```

对着麦克风连续说话 10～20 秒，然后按 `Ctrl+C`。检查文件：

```sh
ls -lh /mnt/UDISK/sample_demo.pcm
```

正常情况下日志中应出现类似内容：

```text
[AI] PCM capture started: dev=0, chn=0, 16000 Hz, 16 bit, 1 channel
[AI] Frame=1, ...
[AI] Capture thread stopped: frames=..., bytes=..., first_pts=..., last_pts=...
[AI] PCM capture stopped: frames=..., bytes=...
```

## 8. 电脑端播放方法

将 `sample_demo.pcm` 复制到电脑后，必须手动告诉播放器其格式：

```sh
ffplay -f s16le -ar 16000 -ac 1 sample_demo.pcm
```

参数含义：

- `-f s16le`：16 位有符号、小端序 PCM；
- `-ar 16000`：采样率 16 kHz；
- `-ac 1`：单声道。

也可以先转换为普通 WAV 文件：

```sh
ffmpeg -f s16le -ar 16000 -ac 1 -i sample_demo.pcm sample_demo.wav
```

## 9. 通过标准

本阶段满足以下条件后才算验证完成：

1. 程序启动时 AI 设备和通道无错误；
2. PCM 文件持续增长，大小与录制时长大致匹配；
3. 使用正确参数播放时能听到清晰声音，速度和音调正常；
4. 按 `Ctrl+C` 后线程、通道和设备均能安全退出；
5. 原有 LCD 预览、H.264 文件和 RTSP 视频不受影响。

## 10. 开发板实测结果

2026-09-30 在 V853 开发板上运行约 16.6 秒，结果如下：

```text
AI 参数：16000 Hz、16 bit、单声道、每帧 1024 个采样点
采集帧数：260
每帧字节数：2048
总字节数：532480
首帧 PTS：29880465868 us
末帧 PTS：29897041598 us
程序退出码：0
```

文件大小校验正确：

```text
260 × 1024 × 2 = 532480 字节
```

首末 PTS 相差约 16.58 秒；按照每秒 32000 字节计算，文件大小也与
采集时长吻合。AI 采集线程、通道和设备均正常退出，同时 LCD、VENC
和 RTSP 未受影响。

随后在 Ubuntu 中使用以下命令转换：

```sh
ffmpeg -f s16le -ar 16000 -ac 1 -i sample_demo.pcm sample_demo.wav
```

FFmpeg 正确识别出 16.64 秒、16000 Hz、单声道、16 bit、256 kbit/s
的 PCM 音频。生成的 WAV 文件能够由 VLC 正常播放并听到声音。因此，
麦克风、AudioCodec、AI 通道、用户态取帧、PCM 文件写入及退出清理均
已验证正常，阶段 6.1 正式完成。
